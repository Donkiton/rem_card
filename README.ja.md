## ひとつのワークフローに参加する役割

- **医師** — 入院と病床、勤務帯ごとの患者記録、指示とテンプレート、食事指示、処置、転帰、アーカイブ、レポート、計算ツール。
- **看護師** — 直近の指示、実施記録、実際の栄養摂取量、勤務帯ごとの推移、印刷、業務統計。
- **手術室** — 緊急・予定手術、簡易指示、薬剤、手術の段階とイベント、集中治療部門（РАО）と手術室の間の患者移動、症例の終了、レポート。
- **管理者** — 統合設定センター、現行・アーカイブデータベースの状態、バックアップ、マスターデータ、印刷、外観、診断。

## 現行バージョンの機能

### バージョン5.1の統合アプリケーション

医師、看護師、予定手術室、緊急手術室の各画面を共通のウィンドウから開けます。役割を切り替えると、アプリケーションは受け付け済みの書き込みを完了し、前のセッションのリソースを解放します。データベースの確認と端末の準備では進行状況が表示され、ログインを中止することもできます。起動診断は、アプリケーションや役割画面が開くまでの遅延を調べるために利用できます。

データフォルダーの設定はアプリケーションに組み込まれています。共有のメンテナンスモードが、各端末によるデータベースへのアクセスを調整します。中央データベースに接続できない場合、緊急ログインではローカルコピーの有無、使用可能性、経過時間を確認します。ネットワークモードへの復帰と変更の移送は、専用の手順で実行します。

### 患者記録と勤務帯の業務

患者記録には、指示と実施状況、バイタルサインとグラフ、水分投与量と排出量、人工呼吸、処置、臨床検査、臨床イベントがまとまっています。現在、前日、予定の記録への移動はそれぞれ区別され、患者の履歴はアーカイブから確認できます。指示では、薬剤・溶解液・投与経路のマスターデータ、テンプレート、勤務帯ごとのスケジュールを使用します。

**「食事」（Диета）**タブでは、医師が栄養計画を設定し、編集可能なテンプレートを適用できます。看護師は実際の摂取量を記録します。摂取を拒否した場合は**0 ml**として保存できます。実際の栄養摂取量は水分出納に反映され、自分の変更を順に取り消すことができます。レコードのバージョン確認によって、別の利用者の変更を上書きしないよう保護されています。

中心静脈カテーテル、腰椎穿刺、輸血などの処置文書と、患者記録および手術症例のPDFレポートを作成できます。

### 計算ツールと熱傷輸液のモニタリング

セクター8の**「計算」（Расчёт）**メニューには、輸液、電解質、熱傷の計算ツールがあります。熱傷計算ツールは、該当するICD診断が登録された患者記録から、医師と看護師が利用できます。

年齢、体重、熱傷面積、受傷時刻を考慮し、第1・第2・第3病日とショック離脱後の期間に対応しています。保存済みの患者記録から実際の投与量と尿量を読み込みます。小児の第1病日および第2〜3病日のモードでは、実際の経腸投与量も考慮します。ウィンドウには、計算対象期間、モニタリング時刻、残りの投与量、計算上の投与スケジュールからのずれが表示されます。記録上の日付と受傷からの経過日数は別々に扱われます。

データは計算ツールを開いた際に読み込まれます。**「記録から更新」（Обновить из карты）**コマンドでは、手動入力としてマークされた値を保持したまま再読み込みできます。読み取りエラーが投与量ゼロとして扱われることはなく、元データを変更すると以前の計算結果は消去されます。計算結果は説明付きでコピーできますが、指示が自動作成されることはありません。詳しい規則と制限は[計算ツールのドキュメント](docs/burn_infusion_calculator.md)を参照してください。

### 統合アーカイブと分析

アーカイブセンターは、医師、看護師、管理者がそれぞれの役割の権限に応じて利用できます。集中治療部門（РАО）の患者アーカイブ、手術症例アーカイブ、分析、グラフ、統計レポートが統合されています。アーカイブデータベースの患者記録を表示する際は、独立した読み取りサービスを使用します。

分析では、期間と患者群を選択し、フィルターを適用し、表示設定を保存して、期間や患者群を比較できます。各指標について、結果、算出方法、対象症例の一覧を確認できます。共通の指標レジストリが単位、データソース、組み入れ基準を定義し、データ品質チェックが重複や不整合な値を検出します。比較データが存在しない場合は、その旨が明示されます。計算とグラフ作成はバックグラウンドで実行され、レポートとグラフは整合した分析用スナップショットを使用します。

指標の定義と技術検証の範囲は、[分析の臨床契約](docs/analytics_clinical_contract.md)と[実装マトリクス](docs/analytics_implementation_matrix.md)に記載されています。

### 手術室、設定、診断

緊急手術と予定手術の業務画面では、チーム、麻酔管理、手術の段階、測定値、薬剤、簡易指示を含む手術症例を管理できます。集中治療部門（РАО）からの患者移動は、患者の所在管理と手術室での受け入れに連動します。ネットワーク障害時には、手術室専用の機能を制限したローカルモードを利用できます。そのデータは、接続復旧後に専用の移送手順を通じて取り込みます。

設定センターには、マスターデータ、手術室の設定、栄養テンプレート、検査カタログ、印刷、テーマ、背景、データベースのメンテナンスがまとまっています。利用者からの問い合わせには診断ログを添付できます。技術ログにはローテーション、保存期間、容量上限が設定されています。頻繁に記録される通常のメトリクスは1分単位の要約にまとめられ、繰り返すエラーは状況情報を含む簡潔な記録に集約されます。医療データ変更の監査記録は、技術ログや同期通知とは別に保存されます。

## 統合ワークフローの仕組み

<p align="center">
  <a href="https://donkiton.github.io/rem_card/codemap/codemap.html"><img src="docs/assets/readme/remcard-workflow.ja.svg" width="100%" alt="医師、看護師、手術室が、共通のデータフォルダー、医療データベース、設定、バックアップを使用"></a>
</p>

RemCardは、共通のデータフォルダーを使用する**PySide6**製のデスクトップアプリケーションです。端末での通常業務に、別途Webサーバーは必要ありません。基本的な処理の流れは、**インターフェース → サービス → DAO → SQLite**です。

1. **保存。** インターフェースは変更を書き込みキューに渡します。コントローラーはファイルロックを取得し、トランザクションを実行します。中央データベースでの`COMMIT`後に、保存の成功が確認されます。下書きやキューに入っただけでは、データが保存されたことにはなりません。
2. **別の端末への反映。** トリガーが同じトランザクション内で`change_log`に通知を記録します。`DataUpdateMonitor`が変更を検知し、`SyncCoordinator`が古いデータを無効化した後、端末が必要なスナップショットを再読み込みします。キャッシュファイルをコンピューター間で転送することはありません。
3. **高速な読み取り。** `ReadCoordinator`、スナップショット、ローカルキャッシュが表示を高速化します。最初のローカルレプリカはSQLite Backup APIで作成され、その後の小規模な変更は別のローカル候補コピーに適用されます。候補を検証してから既存コピーをアトミックに置き換えます。制限の超過や互換性の問題がある場合は完全コピーを行います。レプリカは読み取り専用です。必要なバージョンより古い場合は、読み取り先を中央データベースに切り替えます。臨床データの正本は、引き続き中央データベースで`COMMIT`された記録です。
4. **応答性。** スナップショットの読み込み、ネットワーク経由の書き込み、分析、PDF処理にはバックグラウンドタスクを使用します。遅れて届いた結果は、現在開いている患者や選択期間に適用する前に確認されます。

## ソースからのクイックスタート

開発と検証は、**WindowsとPython 3.11**で行っています。GitとPythonが必要です。`.env`ファイルは不要です。

```powershell
git clone https://github.com/Donkiton/rem_card.git
cd rem_card
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python run_remcard.py
```

`run_remcard.py`は、役割選択を備えた統合アプリケーションを開きます。

> [!CAUTION]
> 開発と試験には、本番データベースではなく、独立したデータフォルダーを使用してください。ロックやアクセス確認は、テスト環境の分離に代わるものではありません。統合シェルは、セッションへのアクセス許可に`SessionLease`を使用します。

<details>
<summary><strong>開発用データベースの選択と意図しない置き換えの防止</strong></summary>

ソース版はローカルの開発用データフォルダーを使用します。初回起動時には、不足している構造が作成される場合があります。選択したフォルダーの一覧と現在のパスは、チェックアウトごとに`.remcard/dev_database_paths.json`へ個別に保存されます。

選択した既存のデータベースは、検証した上で開かれます。見つからなくなったデータベースの代わりに、アプリケーションが通知なく空のデータベースを作成することは認められていません。旧パス`%LOCALAPPDATA%\RemCard\dev_database_paths.json`は、設定を一度だけ移行するために使用されます。

</details>

| --- | --- |
| `RemCard.exe` | 統合アプリケーション：役割選択、業務画面、データフォルダーの設定。 |
| `RemCardUpdater.exe` | 完全更新パッケージをインストールする補助プログラム。 |

**`RemCard.exe`**を起動し、初回起動時にデータフォルダーを選択してから、必要な役割を選びます。`_internal`を含む配布フォルダー全体を保持してください。EXEファイル単体では動作しません。プログラムと同じ場所に`remcard_data_path.json`が保存され、更新は`<папка данных>\UPD\releases`（選択したデータフォルダー内）から検索されます。

個別の`RemCardDoctor.exe`、`RemCardNurse.exe`、手術室用EXE、`RemCardPathSetup.exe`は旧配布方式のものです。バージョン5.1では統合ログインを使用します。このプロジェクトは**完全更新パッケージのみ**を配布します。SemVerの`PATCH`はバージョンの区分であり、独立したパッケージ形式を意味しません。

<details>
<summary><strong>テストビルドと安全な本番配布</strong></summary>

現在の作業ツリーから、配布を行わずにビルドするには次を実行します。

```powershell
.\.venv\Scripts\python.exe scripts\build_release.py --test-worktree
```

このコマンドは必須チェック、PyInstaller、両EXEのスモークテストを実行しますが、`VERSION`、`CHANGELOG.md`、`app/release_info.json`を変更せず、コミット作成、`git push`、パッケージの配布も行いません。生成物には`TEST_WORKTREE_ONLY.txt`の印が付き、本番環境へ誤って配布されないようになっています。

運用向けリリースでは、まずバージョンと対象の正確なコミットがGitHubの`main`に存在している必要があります。その後、リリース担当者が`--expected-version`と`--expected-commit`を指定して`scripts\build_release.py`を実行します。独立したテストデータベースでの受け入れ確認後、別のコマンド`scripts\publish_full_update.py`でパッケージを移送します。`ready.ok`は最後に作成され、このファイルが現れると、そのデータベースを使用するクライアントは直ちに当該バージョンを利用できるようになります。詳細は[ビルドと配布](docs/how_to_build_and_update.md)および[自動更新](docs/auto_update.md)を参照してください。

## 共有SQLiteデータベースとデータの安全性

医療データベースは`archiv/rao_journal.db`にあり、テーマや背景の設定を含むマスターデータと共通設定は`settings/remcard_settings.db`に保存されます。利用者が追加した背景画像は`settings/backgrounds`に保存されます。これらのパスは、選択したデータフォルダーからの相対パスです。リポジトリ内のマスターデータ用JSONファイルは、初期データと互換性のための層として使用され、インストール済み版の運用データの正本ではありません。詳細は[設定データベースの説明](docs/settings_db.md)を参照してください。

共有ネットワークデータベースには、次の規則が定められています。

- `journal_mode=DELETE`、`synchronous=EXTRA`、`mmap_size=0`を使用し、共有データベースでのWALは禁止しています。
- 書き込みはコントローラー、ファイルロック、トランザクションを通じて行います。
- 稼働中のデータベースのバックアップにはSQLite Backup APIのみを使用し、開いているファイルを単純にコピーしません。
- マイグレーション、復元、ローテーションには、検証済みバックアップ、`quick_check`、`integrity_check`を使用します。

これらの対策は既知のリスクを低減しますが、SQLiteを任意のネットワーク環境に配置しても自動的に安全になるわけではありません。アクセス権、遅延、バックアップ、復元については、運用環境での個別の受け入れ確認が必要です。[データベースの安全性](docs/db_safety_contract.md)と[正本と同期の契約](docs/source_of_truth_and_sync_contract.md)を参照してください。

## 開発者向けのチェック

ローカルのチェックとGitHub Actionsは、共通のエントリーポイントを使用します。依存関係をインストールし、仮想環境を有効にした状態で実行します。

```powershell
python scripts\run_ci_checks.py core
python scripts\run_ci_checks.py ui
python scripts\run_ci_checks.py quality
python scripts\run_ci_checks.py regression
git diff --check
```

`core`はロジックとデータ、`ui`はQtインターフェース、`quality`はコード品質とアーキテクチャ上の制約、`regression`は安全性シナリオの全登録項目を検証します。CIでは各グループが独立して実行され、最終ステータス`tests`が各グループの成功とレポートの完全性を確認します。pytestモジュールは、漏れや重複なく[`tests/groups.json`](tests/groups.json)に割り当てられています。

`python scripts\run_ci_checks.py all`は、すべてのpytestを単一プロセスで実行して全体の分離性を確認します。個別の`quality`と`regression`を置き換えるものではありません。ランナーはデータベースとQSettingsに一時パスを割り当て、レポートを`tmp/ci-reports/<группа>`に保存します。個別の確認には、通常の`python -m pytest tests -q`も使用できます。詳細は[テストとCI](docs/testing.md)を参照してください。

ネットワーク検証環境、復元訓練、緊急モード、オフラインモードは、選択したデータフォルダーを読み取るか変更します。[運用受け入れ手順](docs/operational_acceptance.md)と[バックアップ検証手順](docs/backup_restore_drill.md)に従い、意図的に指定したテストデータベースでのみ実行してください。
