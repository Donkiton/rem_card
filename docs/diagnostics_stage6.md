# Диагностика этапа 6

## Реализация 6.1–6.4

- **6.1. Измерения.** Локальные `startup_diagnostic` события разделяют открытие
  центральной БД, настройку соединения, `quick_check`, проверку снимков medical/settings,
  preflight, bootstrap и создание окна. Они содержат длительность, роль и ID попытки;
  ID передаётся также в дочерний процесс. Отдельно фиксируются отклонённые повторные
  нажатия, переход окна, готовность первых данных и шаги подготовки карты.
  Новые события не включают данные пациентов или пути к их файлам.
- **6.2. Подготовка карты.** Сектора создаются пятью группами в GUI-потоке,
  затем отдельными шагами собираются layout и дочерние виджеты. Между шагами Qt
  обрабатывает события. Готовые сектора передаются явно в конструктор layout.
  Открытие пациента завершает оставшиеся шаги, выход инвалидирует callbacks.
  Ошибка передачи подготовленных виджетов освобождает их.
- **6.3. Повторная проверка standby.** Успешная проверка используется повторно
  только внутри одной попытки центрального или аварийного входа. Проверяются путь,
  идентичность файла, размер, временные метки **и SHA-256 содержимого**: одних меток
  Windows недостаточно при быстрой записи. Повторное чтение для хэша сохраняется,
  а повторная SQLite/schema-проверка пропускается. Изменение во время проверки,
  замена файла, ошибка и новая попытка исключают reuse. Перед активацией повторно
  проверяется пригодность standby; локальная активация не импортирует центральные пути.
- **6.4. Отменяемая проверка.** Только read-only сканирование центральной SQLite
  выполняется в отдельном процессе. GUI продолжает обрабатывать события и кнопку
  «Отменить вход». Тайм-аут проверки — 90 секунд; отмена/тайм-аут не означают
  повреждение базы и не запускают восстановление. Новый вход допускается после
  подтверждённого завершения процесса; при неподтверждённой очистке сохраняется
  запрет входа. Подготовка профиля, восстановление, bootstrap и Qt остаются у владельца
  сессии. Отмена дополнительно проверяется перед изменением профиля и восстановлением.

Синхронное создание окна защищено от преждевременного shutdown при вложенной
обработке Qt-событий. Повторные входы и поздний результат отменённого допуска
проверяются тестами. Техработы отменяют незавершённый обычный вход; исключение
для локального администратора сохраняется.

## Границы результата

Этап 6.6 не реализован: частота полной проверки центральной базы не уменьшена.
Сетевые операции до/после read-only сканирования и оставшиеся синхронные операции
bootstrap могут задерживать GUI; это изменение не переносит весь запуск в фон.
Маленькая синтетическая база не воспроизводит размер рабочей базы и нагрузку
файлового сервера. Успешный прогон не доказывает причину прежних зависаний.
Холодный запуск после перезагрузки и одновременная работа с двух физических ПК
требуют отдельного эксплуатационного замера.

Для воспроизведения исходного GUI после `stage6_network_acceptance.py run`:

```powershell
.\.venv\Scripts\python.exe scripts\stage6_gui_acceptance.py --run-root "<полный путь созданного stage6_* внутри _etap6>" --roles doctor,nurse --platform windows --idle-prewarm
```

Harness проверяет успешный синтетический network-report в указанном корне и
изоляцию путей. Для EXE требуется тот же изолированный профиль, файл подключения
`{"baza_dir": "<полный синтетический путь>"}` и тестовый bootstrap из копии spec;
рабочий EXE этим сценарием запускать нельзя. Промежуточные неуспешные отчёты
подготовки harness сохранены отдельно; указанные выше два финальных EXE-отчёта
имеют `ok=true` и код завершения 0.
