# Итоговый отчёт по оптимизации updater

Дата: 2026-07-14

Проект: `C:\Project\remcard`

Результат: updater переведён на один full-only контур; patch-механизм удалён.

## Главный вывод

Удалять `RemCardUpdater.exe` нельзя. Он нужен не для patch-пакетов, а для безопасной замены полной сборки после закрытия основной программы, локального backup, rollback и повторного запуска той же роли. Удалена именно неиспользуемая patch-ветка: создание и проверка patch-пакетов, patch-runner и код их применения.

Уровень `PATCH` в номере `MAJOR.MINOR.PATCH` сохранён. Он обозначает тип изменения версии, а не формат обновления: любой релиз по-прежнему является полной сборкой.

## Что изменено

### Поиск и запуск обновления

- Папка установки определяется по каталогу реально запущенного EXE. Программа может находиться на любом локальном диске и в любой папке.
- `remcard_data_path.json` рядом с EXE содержит только точный путь к выбранной папке данных; обновление ищется только в `<папка данных>\UPD`.
- Убрана лишняя проверка соседнего `UPD`, а старые каталоги версий отфильтровываются по имени до чтения manifest. Это уменьшает число SMB-обращений.
- Проверка full-update выполняется при каждом compiled-запуске и после штатного закрытия.
- При обновлении на старте автоматически запускается тот же EXE: врач, медсестра либо соответствующая операционная.
- Уже выбранный offline-контекст оперблока не обращается к сетевому `UPD` до показа offline-интерфейса.

### Установка полной сборки

- Сетевой пакет копируется в локальный staging рядом с фактической папкой установки один раз.
- До изменения установленной программы локальная копия проверяется по manifest, размеру и SHA-256 каждого файла.
- Второе полное локальное копирование заменено перемещениями на одном диске: старая версия уходит в backup, новая — из staging в рабочую папку.
- `remcard_data_path.json` и разрешённые локальные данные сохраняются.
- Source и target не могут совпадать, быть вложенными или указывать на один каталог через junction/alias.
- При обычной ошибке выполняется rollback. При неполном rollback backup не удаляется, а пользователю сообщается его путь.
- Ошибка только автоматического запуска после уже успешной установки теперь является предупреждением, а не ложным сообщением «обновление не выполнено».

### Manifest и блокировки

- Новый full-manifest schema 2 содержит точный inventory `path`, `size`, `sha256` и attestation snapshot настроек.
- Старый full-manifest schema 1 принимается для совместимости. Явный `patch`, неизвестный тип и неизвестная будущая схема отклоняются до изменения установки.
- Lock привязан к конкретной локальной target-папке.
- Снятие lock использует ограниченные повторные попытки с backoff; при постоянной ошибке удаления записывается terminal-состояние `completed`, которое не блокирует новую версию на 30 минут.
- Мёртвый локальный процесс updater распознаётся без ожидания полного TTL.

### Сборка и публикация

- `RemCard.spec` только собирает `dist\Prog`; он не очищает и не публикует `UPD`, не создаёт production `ready.ok`.
- `build_release.py` выполняет обязательный порядок: release-коммит → architecture/полная fast regression/F821 → PyInstaller → проверка пакета → smoke всех шести EXE → точный git push → публикация только в локальный тестовый `UPD`.
- Пропуск production-сборки и snapshot настроек запрещён.
- Сетевая публикация вынесена в `publish_full_update.py`: возобновляемый staging, повтор сетевых операций, publish-lock, проверка SHA-256, атомарное завершение и `ready.ok` последним.
- Publisher требует явно указать `--source` принятой версии. Он больше не может молча выбрать текущий `VERSION` и случайно опубликовать следующую непроверенную сборку.
- Опубликованный каталог не перезаписывается. Возврат удалённого `ready.ok` требует явного `--reactivate-existing`.

## Как теперь выпускать обновление

Подробная пошаговая инструкция: `docs/how_to_build_and_update.md`.

Коротко:

1. Завершить изменения рабочим git-коммитом и оставить worktree чистым.
2. В `C:\Project\remcard` запустить:

   ```powershell
   .\.venv\Scripts\python.exe scripts\build_release.py
   ```

3. Взять готовую папку из `C:\Project\RemCardTestData\UPD\releases\<версия>`.
4. Проверить её на отдельной тестовой программе и тестовой базе: обновление при старте, после штатного закрытия и запуск всех ролей.
5. Только принятую папку опубликовать в сеть:

   ```powershell
   .\.venv\Scripts\python.exe scripts\publish_full_update.py `
     --source "C:\Project\RemCardTestData\UPD\releases\<проверенная версия>" `
     --config "<папка production-программы>\remcard_data_path.json"
   ```

После появления сетевого `ready.ok` релиз сразу доступен всем клиентам этой базы. Поэтому functional/canary-проверка должна закончиться на тестовой базе до production-публикации.

## Существенный ожидаемый эффект

- Patch-путь с повторными полными SHA-проходами по сети исключён полностью.
- Для full-update устранён второй локальный проход копирования размером со всю сборку.
- Поиск меньше читает каталоги и manifest на сетевой папке.
- Release-сборка больше не может случайно сделать непроверенный пакет видимым пользователям.
- Обрыв сетевого копирования publisher не требует начинать заново: корректные файлы staging используются повторно.

Фактический выигрыш на production SMB не измерялся: сетевой диск в финальном цикле был недоступен. Измерено и подтверждено уменьшение числа полных I/O-проходов и работоспособность на изолированных fixture-сценариях.

## Что осталось в плане

1. Один эксплуатационный dry-run на реальном сетевом ресурсе без рабочих клиентов: время копирования и продолжение после искусственного обрыва.
2. Политика хранения: минимум три последних full-релиза не менее семи дней.
3. Регулярный просмотр update-логов: ошибки SHA, неполный rollback, длительность сетевого копирования и отставшие ПК.
4. При необходимости — цифровая подпись manifest/EXE после определения процедуры хранения ключа.
5. Если размер 452,7 МБ и 1 425 SMB-файлов станет главным ограничением, отдельно испытать единый архив полной сборки. Это следующий уровень оптимизации, а не обязательное условие текущего надёжного процесса.

## Известные ограничения

- SHA-256 и проверка source commit защищают от повреждения и несоответствия сборки, но не заменяют внешнюю цифровую подпись при компрометации build-машины или git-origin.
- При физическом отключении питания в момент многофайловой локальной замены остаётся аварийный риск; backup сохраняется для восстановления. Полностью атомарное переключение потребовало бы versioned install directories и отдельного стабильного launcher.
- Общий quality-аудит показывает два исторических F-complexity отклонения вне updater: `OrderService.commit_local_draft` и `OrdersWidget._apply_snapshot_data`. Новых F-блоков updater/release изменения не добавили.
