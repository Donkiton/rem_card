## Ошибки и краши

При сканировании 101 доступного `.log`-файла, включая вложенные папки,
ошибки уровня ERROR обнаружены только от watchdog зависаний.
Python traceback, отдельные исключения ERROR/CRITICAL и сообщения о фатальном
падении в этих файлах не найдены.

В `crashes\sent` находятся **два отчёта `ui_hang`** с признаком
`previous_session_unclean=true`. Это отчёты о незавершённых сессиях со стеками
зависаний, а не подтверждение двух нативных крашей:

- `2026-10-02_c07f8ead369f422f9ade5ac6c7a9144a.json`, обработан при запуске в 00:38.
  Главный поток находился в синхронном чтении пациента для окна управления
  пациентами: `management_widget._open_patient_form_safe` →
  `get_patient_with_current_admission` → `db_manager._fetch_one_central`.
  В отдельном потоке тоже выполнялось чтение центрального курсора изменений.
  Время обработки отчёта не является временем начала зависания предыдущей сессии.
- `2026-10-02_51a94d959df642c0b80208855b84497d.json`, обработан при запуске в 07:57.
  Содержит хвост дампа процесса 19540 и незавершённую сессию. В хвосте главный
  поток исполняет создание фонового потока проверки доступа во время модального
  сообщения об отказе создать план-карту. Это место захвата стека, а не
  доказанная первопричина всех предыдущих зависаний.

В Windows Application за 00:00–08:30 не найдено событий 1000/1001 с упоминанием
RemCard/rem_card/Python. Отсутствие таких записей не исключает принудительное
закрытие или иное завершение, которое Windows не зарегистрировала как краш.

## Отдельная причина отказа план-карты и выполненное исправление

При нажатии в общем списке `_plan_card_state_for_admission` возвращал пустой
словарь, если выбранный пациент не совпадал с `self.admission_id` ранее открытой
карты. Дополнительно доступность требовала сохранённую текущую карту.

Теперь доступность определяется последним часом смены (07:00–08:00), без
обязательной текущей карты. Состояние другого пациента не используется.
Проверки существования карты, исхода и нового поступления повторяются в фоновой
операции внутри транзакции. Синхронные запросы этих данных при нажатии удалены.

Если это первая карта пациента, поступившего в 07:00–08:00, поступление и
начальный ACTIVE переносятся на 08:00 вместе с созданием карты. Окно управления
пациентами читает обновлённое поле `admissions.admission_datetime`. Ранее созданные
карты и более ранние поступления сохраняются. Если уже оформлено настоящее
движение, перенос поступления отклоняется. Повторное создание существующей
план-карты не перезаписывает её показатели. Ошибка записи откатывает перенос.

## Что требуется для отдельного исправления зависаний

1. Учесть выход Windows из сна в watchdog, чтобы не считать сон временем зависания.
2. Убрать синхронное чтение сетевой базы при открытии формы управления пациентами:
   этот путь подтверждён стеком первого отчёта. Проверить прочие обращения к базе
   из главного потока на отдельной тестовой базе с искусственной блокировкой.
3. Разобрать повторные ожидания `BEGIN IMMEDIATE` после сна и жизненный цикл
   соединений. Для установления владельца блокировки нужны согласованные по
   времени данные других клиентов/сервера; локальные логи его не определяют.
4. Отдельно сверить содержимое трёх операций `pending`, прежде чем оценивать
   сохранность карты и назначений. Такая сверка рабочей базы в этой задаче
   не выполнялась.

Рабочие данные, блокировки, настройки SQLite и установленное приложение
не изменялись. Исправление план-карты находится в исходниках; новый EXE не собирался.
