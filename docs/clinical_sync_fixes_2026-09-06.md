# Исправления синхронизации витальных функций, назначений и баланса

Дата: 6 сентября 2026 года. Исходный коммит: `2d05378`, ветка `main`.

Работа выполнена по согласованным пунктам аудита. Исправления и тесты сначала подготовлены локально; отправка в GitHub отдельно разрешена пользователем после проверок. Изменения не требуют миграции схемы базы.

## Результат по согласованному плану

| Пункт аудита | Результат |
| --- | --- |
| 1. Изоляция отмены между пациентами | Истории и незавершённые записи разделены по сервису, пациенту и реанимационным суткам; для витальных функций оперблока учитывается операционный случай. Очередь использует контекст, захваченный при нажатии. |
| 2. Безопасная отмена витальных функций | Сохранение возвращает сведения о конкретной операции: ID записи, пациента, версию и предыдущие значения. Отмена вставки удаляет именно эту строку; отмена дополнения существующей строки восстанавливает прежние значения. Более новая чужая правка той же строки вызывает конфликт. |
| 3. Одновременное заполнение пустой минуты/ячейки | По решению пользователя политика оставлена прежней. Обязательная защита отсутствующей версии и приоритет врача не добавлялись. Это закреплено тестами. |
| 4. Версия выполнения назначения на экране | Врачебная и сестринская таблицы, панель текущих назначений и сектор W1 передают показанную пользователю версию. Сервис сравнивает её внутри транзакции. Устаревший экран не может молча изменить уже обновлённое выполнение. |
| 5. Ошибки чтения питания | Сбой чтения факта или плана питания прерывает формирование снимка баланса. Экран сохраняет последний принятый снимок с сообщением о необходимости обновления и повторяет чтение. Печать прерывается с ошибкой вместо баланса с нулевым питанием. |
| 6. Редактирование баланса и настройки витальных функций | Последовательные отмены получают версию, возникшую после предыдущей отмены. Чтение, объединение изменённых настроек и запись выполняются в одной транзакции. |
| 7. Ложные полные обновления | Проверка непрерывности журнала использует зафиксированную верхнюю границу. Строки, появившиеся после чтения этой границы, обрабатываются следующим опросом и не вызывают ложный разрыв журнала. |
| 8. Сетевые чтения в интерфейсе баланса | Контроллер запрашивает обновление через существующий фоновый `BalanceSnapshotSync`. Убраны синхронные перечитывания после записи, отмены и ошибки; проверки исхода при вводе выполняются в фоновой операции, определение текущих суток — без обращения к БД. |
| 9. Выборка ближайших назначений | Подзапрос выбора актуальных выполнений ограничен пациентом и нужными сутками. Группировка больше не запрашивает историю всех пациентов. |
| 10. Сохранение назначений и обновление реплик | Проекция трансфузий обновляется для затронутых назначений крови/плазмы. Неизменившиеся строки сохраняют ID и не создают лишние изменения журнала. Быстрые запросы обновления реплики объединяются с ограниченной паузой, зависящей от длительности предыдущего копирования; периодический опрос имеет небольшое смещение для разных рабочих мест. |

## Дополнительно исправлено при проверке

- Завершение старого сохранения после перехода к другому пациенту и обратно не очищает заново введённый текст. При смене контекста баланса сбрасываются версии и данные предыдущего пациента.
- Завершение записи одного пациента не снимает блокировку с другой, ещё незавершённой записи.
- Отказ постановки витальных функций в очередь освобождает состояние ожидания и показывает ошибку.
- Локальная проекция витальных функций получает ID и версию из подтверждения записи, включая путь повторного получения уже сохранённого результата.
- Отмена выполнения медсестрой после истечения установленного срока возвращает явную ошибку. Ранее сервис мог ничего не изменить, а интерфейс показывал успешную отмену.
- Архивные сутки не считаются текущими только потому, что в кэше находятся их временные границы. Минутный таймер баланса учитывает незавершённую запись и не включает быстрый ввод раньше времени.
- Сообщение о неполном балансе восстанавливается при первом открытии лениво создаваемой вкладки.

## Сохранённые правила совместной работы

Общая база остаётся в сетевой папке. Записи проходят через действующие очередь, транзакции и блокировки. Локальная реплика остаётся копией для чтения; механизм требуемого курсора и обращения к центральной базе при отставании сохранён. Фильтры видимости врача, медсестры и оперблока не менялись.

Параллельная работа с разными пациентами и разными записями одного пациента сохраняется. При конфликте изменения уже существующей записи пользователь получает ошибку, а актуальное содержимое БД остаётся целым. Отдельное правило приоритета врача не вводилось.

Профиль сетевой SQLite сохранён: `journal_mode=DELETE`, `synchronous=EXTRA`, `mmap=0`. Полное копирование реплики по безопасному механизму и проверки целостности сохранены. Объединение запросов обновления реплики не превращает её в самостоятельную базу для записи.

## Ограничения и дальнейшая работа

Дополнительная локальная проверка по запросу пользователя: единым процессом запущены 13 тематических тестовых модулей для клинических записей, Qt-интерфейса, баланса, назначений, оперблока, реплик и процесса записи. Результат: **162 теста и 3 подтеста прошли за 11,89 с**. Использованы отдельные временные БД и настройки. Это автоматический прогон компонентов и сервисов, без ручного обхода трёх полноценных приложений и без реального SMB. [Журнал локального прогона](C:/Project/remcard/tmp/local-clinical-smoke/pytest.log), [JUnit](C:/Project/remcard/tmp/local-clinical-smoke/junit.xml).

Согласованные изменения кода выполнены. Измерения на реальной SMB-папке и одновременный запуск трёх физических рабочих мест в этой задаче не проводились. Локальные многопоточные проверки подтверждают поведение транзакций и конфликтов, но не характеризуют задержки, отключения и настройки конкретной сети. Перед распространением сборки нужен приёмочный прогон на отдельной тестовой сетевой БД: общий пациент, разные пациенты, работа оперблока, чужая правка перед отменой, задержка/обрыв сети и повторное подключение.

История отмены хранится в памяти соответствующего открытого интерфейса, до 50 действий на контекст; после закрытия окна или приложения она не восстанавливается. Отмена затронутой другим сотрудником строки намеренно отклоняется. Постоянный журнал пользовательской отмены в объём этих исправлений не входил.

Полная копия БД для реплики по-прежнему выполняется. Уменьшены повторные запросы копирования, но выигрыш в миллисекундах на вашей базе не измерен. При дорогом копировании дополнительная пауза быстрого обновления ограничена обычным интервалом синхронизации; для актуального чтения остаётся существующий механизм обращения к центральной БД.

Для следующего этапа полезно собрать реальные длительности копирования, время ожидания записи и задержку появления чужих изменений. По этим данным можно подобрать интервалы и оценить дальнейшее уменьшение выборок. Переход к приращениям реплики требует отдельного проектирования: удаления, атомарность группы изменений, восстановление после пропуска журнала и смена базы должны оставаться корректными. Такой переход здесь не выполнялся.

В других участках приложения остаются прежние синхронные обращения к данным, например некоторые проверки статуса и времени во вкладке витальных функций. Они не переносились массово в рамках исправления контроллера баланса: следующий адресный перенос стоит делать по измерениям и с отдельными проверками переходов состояния пациента.
