# Надёжность единого входа: аудит и обязательные проверки

13.09.2026, исходный SHA `daeb814bccbcd02312f8814cbbd67f15697c3b84`. Дополнение к [плану](unified_entry_refactor_plan.md). Статус: статический аудит ключевых путей; не заключение о полной проверенности всех сценариев многопользовательского исполнения. Исходные автоматические результаты остаются в [baseline](unified_entry_baseline_2026-09-13.md).

## Принятый контракт пользователя

Одна рабочая копия RemCard на компьютере, одно окно, четыре сменяемые роли. Сетевые сеансы одной роли на других ПК допускаются. Кнопка назад в секторе 8 рабочего экрана ведёт к завершению роли и приветствию. Не открывать вторую роль, пока первая ещё завершает принятое сохранение или не установила его исход.

Техработы: 60 секунд на явное сохранение, после срока несохранённый ввод можно потерять. Не сохранять его автоматически и не восстанавливать автоматически после миграции. Принятое сохранение, подтверждённые данные и неизвестный результат записи не относятся к допустимым потерям. Свежий вход повторно читает данные и совместимость.

## Что подтверждено в коде

| Путь | Наблюдение | Обязательное следствие для рефакторинга |
|---|---|---|
| `services/data_service.py: enqueue_write` | Приём, выполнение и callback — разные стадии; при shutdown UI success callback пропускается | Не ждать закрытую форму как единственный источник подтверждения записи; регистрировать итог операции независимо от UI |
| `DataService.shutdown` | Останавливает планировщики/monitor, ждёт очередь, возвращает bool | Передавать наверх неполное завершение, не объявлять роль освобождённой по факту вызова метода |
| `app/sqlite_shared.py: LocalWriteQueue` | Записи сериализуются локальной очередью; предусмотрены повторения задач | Проверить классификацию retry и завершение принятых задач; повтор тела допустим лишь при доказанном отсутствии записи/идемпотентности |
| `SQLiteWriteController._commit_transaction` | Для интерактивной записи повторяется COMMIT с ограничением времени | Не заменять этот механизм повторным выполнением всего изменения |
| `data/dao/db_manager.py: run_write_operation` | Есть основной транзакционный путь и отдельный network worker по metadata | Проверка техработ должна охватить оба пути, а не только UI queue |
| `app/network_write_worker.py` | operation_id, receipts, already_committed, подтверждение после тайм-аута, outcome_unknown | Сохранить отличие «не выполнено» от «исход неизвестен»; повтор использует тот же логический id, не создаёт дубликат |
| `DatabaseManager.run_read_operation` | Связанные чтения выполняются в одном snapshot; есть чтение из write context | Сохранить согласованность чтения после собственной записи и нескольких таблиц |
| `services/read_coordinator.py` | Предусмотрена защита кэшей от устаревших состояний | Добавить границу жизненного цикла роли/базы; запоздавший callback не применяется в новой роли |
| `DatabaseManager.close` | Может вернуть False при занятости central IO; некоторые потоки имеют отдельные тайм-ауты; есть shutdown backup | Агрегировать результат всех ресурсов; учесть backup и отдельные потоки, не считать закрытие менеджера доказательством остановки всего приложения |
| `services/operblock_handoff_service.py: dispatch_from_rao` | Формирование передачи вызывается через одну run_write_operation; доступны ожидаемые версии события | Сохранить атомарность движения и handoff, проверить конкуренцию и повтор, не раздробить перенос между асинхронными шагами |
| `ui/doctor_view/doctor_remcard_widget.py`, `ui/nurse_view/nurse_main_widget.py` | Кнопка сектора 8 связана с существующим on_back_clicked | Пересмотреть контекст старого handler: рабочий экран → роли, вложенные страницы → свой уровень; не подключить второй обработчик поверх старого |

Это наблюдения и требования к новому поведению, а не утверждения о существующей потере данных. Путь с receipts не доказывает идемпотентность всех остальных операций. В коде обнаружены дополнительные прямые открытия SQLite; их инвентаризация приложена отдельно и должна быть классифицирована перед переносом владения ресурсами.

## Проверяемые инварианты

1. «Сохранено» появляется только после подтверждённого COMMIT. Ошибка обновления экрана после COMMIT не превращает сохранение в неудачное и не запускает дубль.
2. У операции есть конечный результат: rejected-before-submit, committed, rolled-back либо unknown. Unknown запрещает заявление «все данные сохранены / база свободна» до выяснения.
3. Запрет новых сохранений и регистрация принятого сохранения атомарны относительно выхода/техработ. Нажатие на границе секунды не проваливается между состояниями.
4. Принятая операция остаётся у владельца жизненного цикла до результата; уничтожение QWidget не отменяет её учёт. Отмена ожидания UI не равна rollback SQLite.
5. Перенос пациента/койки/исхода/операции либо меняет всё связанное состояние, либо откатывается целиком. Сохраняются идентичности госпитализации/карты и границы РАО/оперблока.
6. Каждая конфликтная запись сверяет прочитанную версию внутри транзакции; отсутствие expected_revision в вызове рассматривается отдельно, а не как автоматическое разрешение overwrite.
7. На новом входе читается актуальное состояние, старый snapshot/ответ/отложенный autosave не возвращает прежние данные. Нечитаемая БД не отображается как успешная пустая карта.
8. Техработы готовы только при доказанном освобождении всех затрагиваемых соединений/задач и получении исключительного доступа. Истечение тайм-аута и отсутствие heartbeat недостаточны.
9. Смена роли не меняет фактическую базу и не снимает защиту транзакций. Смена базы требует нового контекста/перезапуска; старые кэши и данные не перепривязываются по совпавшему admission_id.
10. Логи помогают установить исход, но журнал диагностики не заменяет транзакционное подтверждение и не является единственным хранилищем принятой записи.

## Полная карта ресурсов до реализации E1

Для каждого найденного открытия/фабрики заполнить: владелец, фактический путь и идентичность базы, read/write, процесс/поток, режим транзакций, срок жизни, способ отмены, способ join/close, подтверждение освобождения, поведение при неудаче. Отдельные группы: central write, thread-local/scoped reads, settings DB, архив/аналитика/PDF, monitor, replica/cache, worker-процессы, backup/quick_check/integrity, аварийное хранилище/merge/outbox.

Поиск `sqlite3.connect` в app/data/services/ui дал 65 текстовых вхождений, список сохранён в `tmp/unified-entry-baseline/sqlite-connect-inventory.txt`. Это лишь список кандидатов, не число одновременно открытых соединений: соединения через wrappers/aliases и вызовы других библиотек требуют просмотра фабрик. Каждый компонент, способный открыть соединение после начала drain, получает единый запрет и тест этого запрета. Различать освобождение клинической базы, настроек и всей папки: UI обязан точно отражать, какой объём обслуживания безопасен.

Ротация и миграция не запускаются автоматически от обычного перехода «Назад». Старый код полного закрытия нельзя механически вызвать целиком: он может запускать обновление/backup/ротацию и завершать QApplication. Не применять QThread.terminate к активному потоку записи для соблюдения 60 секунд.

## Матрица проверки надёжности

| Сценарий | Контрольный результат |
|---|---|
| Сохранение принято прямо перед выходом | Коммит или явный rollback; новая роль не стартует при unknown |
| COMMIT успешен, UI закрыт/ответ потерян | Данные присутствуют один раз; повтор не дублирует их |
| Сеть потеряна до начала / во время / после COMMIT | Разные исходы, никакого автоматического утверждения «не сохранилось» при unknown |
| Две роли/два ПК меняют одну запись | Вторая устаревшая версия конфликтует, первая не затирается |
| Два одновременных переноса на одну койку | Единственный допустимый победитель; полный откат другого переноса |
| Передача РАО → оперблок → возврат | Нет дубля пациента/госпитализации/статуса; проверяется исходная госпитализация и текущая койка |
| Удаление назначения одновременно с выполнением | Сохраняется согласованное состояние, выполнение не исчезает |
| Новый вход после техработ/миграции | Свежие чтения, проверка версии, старые формы/кэши не записываются автоматически |
| Поздний snapshot из старой роли/базы | Отвергнут по поколению контекста, актуальный экран не откатывается |
| Открытый архив/экспорт/реплика во время drain | Ресурс остановлен либо явно показан блокатор; нет ложной готовности |
| Зависший worker/close=False | Режим остаётся ожидающим/неподтверждённым; не скрывать соединение из реестра |
| Двойной запуск EXE в один момент | Один рабочий экземпляр, второй активирует первый; между ролями меняется только сеанс |
| Несохранённая форма после 60 секунд | Ввод отброшен после предупреждения, нет отложенного восстановления/записи |

Использовать отказ в определённой фазе, два независимых процесса и проверку финальных записей/версий/связей, а не только наличие QMessageBox. Проверки integrity_check/foreign_key_check тестовой базы дополняют бизнес-инварианты и не заменяют их. Полный набор запускать на изолированной локальной и затем тестовой SMB-базе.

## Логирование при реализации

Переиспользовать `app.local_metrics`, существующие структурированные события/audit и operation receipts. Новые события привязывать к действительным переходам, без бессмысленного дублирования каждой проверки таймера.

- Общий контекст: session_id, host/node_id, PID, роль, версия приложения, идентичность базы/поколение, transition_id, operation_id/request_id, source операции. Идентификатор медика/исполнителя сохраняет своё отдельное значение.
- Жизненный цикл: role_enter_requested/ready/failed, role_leave_requested/drained/blocked, maintenance_received, deadline_reached, resources_released; причина выхода, оставшиеся задачи и длительности.
- Запись: submitted, started, committed, rolled_back, rejected, outcome_unknown; версия записи до/после, change_id, ожидание очереди/замка/COMMIT, retries, подтверждение receipt. Не писать «committed» только по постановке в очередь.
- Чтение: request_id, generation, источник central/replica/cache, курсор, число строк, elapsed, результат applied/rejected-stale/failed. Успешные частые чтения агрегировать, ошибки/необычные задержки фиксировать подробно.
- Ресурсы: открытие/закрытие и оставшиеся владельцы при drain, queue depth, живые workers, close result. Ошибки завершения видны и на приветствии, а не только в файле.
- Отбрасывание: тип формы и число несохранённых форм, без содержимого и без маркировки принятой записи как discarded. Наличие отвергнутых callback/старых поколений учитывается отдельно.
- Запретить новые полные SQL params/ФИО/тексты назначений в диагностическом потоке. В `execute_remcard` уже есть DEBUG SQL/Params: отдельно проверить используемый уровень и редактирование чувствительных значений при внедрении диагностики. Для расследования достаточно технических id и фаз; их доступ/хранение также учитывать.
- Сохранить ротацию/ограничение размера и локальную запись логов при недоступности сети. Не создавать синхронный сетевой logging на UI-пути. Ошибка диагностики не должна менять итог клинической транзакции.

Критерий диагностической приёмки: по одной цепочке id восстановить «что пользователь отправил как тип операции → что принял сервис → был ли COMMIT → почему экран не обновился/роль не вышла». Не обещать exactly-once только за счёт логов.

## Реализовано и проверено 13.09.2026

- `MaintenanceStore` публикует состояния `open`, `draining`, `maintenance` под отдельной блокировкой состояния. `SessionLease` удерживает shared OS lock весь срок роли, а технические работы требуют exclusive lock того же файла. Локальные тесты двумя независимыми процессами проверяют взаимное исключение, поздний вход, несколько сеансов одной роли, malformed state и stale generation.
- Единое окно получает `SessionLease` до bootstrap, сохраняет все созданные runtime-контейнеры, включая заменённый сетевой контейнер оперблока, и освобождает lease только после успешного `DataService.shutdown()` и `DatabaseManager.close()` каждого владельца. Неуспешное закрытие сохраняет контейнер для повторной попытки. Список виджетов и worker-объектов снимается до начала shutdown; старые виджеты оперблока удерживаются до завершения drain.
- `DataService` регистрирует принятую синхронную или queued-запись с UUID, `session_id`, ролью и состоянием `pending`. Итог `committed`, `failed` либо `unknown` устанавливается до Qt-callback. После начала shutdown новые записи отвергаются, синхронные submissions ожидаются, а `pending`/`unknown` не позволяют объявить ресурсы освобождёнными.
- Тайм-аут drain сам по себе сохраняет `pending` и `queue_settled=false`; он не создаёт ложный `unknown`. Поздний доказанный `committed` или `failed` позволяет повторить drain. Настоящий неопределённый receipt остаётся липким `unknown` и продолжает блокировать освобождение роли.
- `LocalWriteQueue` отделяет результат транзакции от уведомления UI: исключение success/error callback логируется, не повторяет уже committed mutation и не завершает worker очереди.
- Фоновое освобождение коек в `PatientService` передаётся в lifecycle-managed очередь `DataService`, сохраняет debounce и больше не создаёт отдельный daemon thread. Ошибка DAO достигает accepted-write registry как `failed` либо `unknown`; `pending` операция удерживает shutdown до фактического завершения.
- `DatabaseManager.close()` сохраняет ссылки на неостановленные quick-check, integrity, outbox, replica и network-write workers, возвращает `False` и допускает повтор. Соединения закрываются только после получения central IO lock; принудительного завершения потока записи нет.
- Изолированные проверки `tests/test_unified_access.py`, `tests/test_unified_shutdown_resources.py`, `tests/test_unified_runtime.py`, `tests/test_unified_write_outcomes.py` и соседние проверки сетевых исходов подтверждают локальные контракты. Отдельный regression-сценарий проверяет `pending` после тайм-аута и успешный повторный drain после позднего commit. Это не заменяет полный набор CI/build, который фиксируется отдельно после его завершения.

Остаются проверяемые ограничения:

- Проверки выполнялись на локальной файловой системе и с тестовыми SQLite/fake-worker сценариями. Работа `LockFileEx`, атомарной публикации состояния и задержек на фактическом SMB не подтверждена; такую проверку нельзя объявлять выполненной по локальным тестам.
- Старые бинарные версии не получают новый shared gate и не читают состояние `draining`. Их существующий `.lock` является консервативным блокатором, но старый процесс может стартовать после проверки legacy-маркеров и до/во время технических работ. Полное исключение этой гонки возможно только после обязательного обновления всех клиентов либо внешней серверной блокировки доступа.
- Полный пооперационный fault injection, конкурентные бизнес-инварианты и проверка на тестовой SMB-базе остаются отдельными этапами приёмки. Нельзя обещать exactly-once для всех операций только на основании нового реестра и диагностических событий.
