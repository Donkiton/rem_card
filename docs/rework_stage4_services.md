# Rework: этап 4 — сервисы и доступ к данным

Дата: 28.09.2026. База: `2d020bf330b3080492810be60ec721bd6634a337`.
Декомпозиция карты врача и назначений сохранена этим коммитом в `origin/rework`
перед началом этапа. Исходная удалённая `main` остаётся на
`8394f34c82d5ffab51b9c3fa75c71cd909d7dfe6`.

## Изменения

| Область | Было | Стало |
|---|---|---|
| Создание DAO | Импорт через совместимый `data/dao/remcard_dao.py` | Прямые импорты конкретных DAO; файл переэкспорта удалён |
| Создание фасада карты | Импорт через `services/remcard_service.py` | Прямой импорт `RemCardService` из `remcard_facade`; файл переэкспорта удалён |
| Панели текущих назначений и W1a | Два имени для одной операции, проверка наличия метода | Один фасадный API `set_nurse_order_mark`, та же захваченная ссылка на сервис и та же `expected_version` |
| Фасад отметок | Четыре пары одинаковых методов | Только `set/cancel_nurse_order_mark` и `set/cancel_doctor_order_mark`; четыре compatibility alias удалены |
| Передача записи сервисом | Одинаковый код в трёх сервисах | Общая функция `enqueue_service_write` в `services/write_dispatch.py` |
| Границы чтения назначений | Собственная копия формулы суток в `OrderDomainService` | Оба метода чтения используют `ShiftService.get_day_period` |

Прямые импорты заменены в bootstrap, архивном сервисе и проверках UI/отчётов.
Импорты, которые были отложены до вызова функции, остаются отложенными.
Карта `docs/codemap/` переведена с удалённого DAO-модуля на `vitals_dao.py`.

Общая передача записи используется только в `PatientService`, `FluidService`
и `PatientBedManagementService`, где исходные тела были одинаковыми:

- При наличии `DataService` операция и исходные callbacks передаются в его
  очередь. Сервис не выполняет операцию сам и не начинает синхронный повтор
  при отказе или исключении очереди. Прежний результат метода — `None`.
- Без `DataService` операция выполняется один раз. Её исключение передаётся
  в `on_error`, если он задан, иначе поднимается вызывающему коду.
- `on_success` вызывается после успешной операции, вне обработки ошибок записи.
  Исключение callback не превращается в сообщение о неуспешной записи.

Фасад карты и сервис статусов намеренно не переведены на эту функцию: их
синхронные ветви обрабатывают исключения callbacks иначе. Изменение этой
политики потребовало бы отдельного изменения поведения, а не рефакторинга.

## Сохранённые границы

Рабочая цепочка отметки: UI → `RemCardService` → `OrderService` →
`OrderDomainService` → `DatabaseManager`. Эти слои сохраняют действующие
обязанности: API карты, координацию назначений, клиническую операцию и транзакцию.
UI не переведён на прямую запись через DAO.

`expected_version`, проверки ревизий, исключения конфликтов и SQL операций
отметок не изменены. Общая функция передачи записи не открывает соединения,
не создаёт транзакции и не реализует retry. Владение очередью, обработка
аварийного режима и результатами записи остаются в `DataService`.

Чтение назначений по-прежнему не запускает write-maintenance. Период остаётся
полуоткрытым: начало включительно, конец исключительно; медицинские сутки —
08:00–08:00. SQL, фильтрация пациентов и порядок строк сохранены.

SQLite/SMB, read replica, согласованные снимки, кэши, ленивые зависимости,
блокировки, архивное чтение и синхронизация исходов не перепроектировались.
Подозрительно тонкие фасадные методы не удалялись только по длине: действующие
границы UI и доменной логики сохранены. Дальнейшее удаление неиспользуемых
публичных методов требует отдельного решения об их контракте.

## Восстановление

Исходные файлы доступны через `git show 2d020bf:<путь>`, например:

```powershell
git show 2d020bf:services/remcard_facade.py
git show 2d020bf:services/patient_service.py
git show 2d020bf:data/dao/remcard_dao.py
```

После сохранения этапа отдельным коммитом отменять его целиком через
`git revert <SHA-коммита-этапа-4>` в `rework`: удаление обёрток и перевод их
потребителей связаны. Для внешних скриптов старые пути импорта и четыре
удалённых псевдонима нужно заменить каноническими API из таблицы выше.
Этап не включает слияние в `main`, выпуск EXE или изменение рабочей базы.
