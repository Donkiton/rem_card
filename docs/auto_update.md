# Автообновление РЕМКАРТА

РЕМКАРТА обновляется только полными сборками. Механизм patch-обновлений удалён: в эксплуатации он ни разу не использовался и больше не входит ни в runtime, ни в release-процесс. Слово `PATCH` осталось только как уровень номера SemVer, например `1.2.3`.

## Откуда берутся пути

Пользователь может установить программу на любой локальный диск и в любую папку. Рабочий каталог определяется по расположению запущенного EXE. Установленная программа передаёт updater точный путь, поэтому он не угадывает диск и не требует каталога с фиксированным именем.

Рядом с установленными EXE находится файл:

```text
<папка программы>\remcard_data_path.json
```

Его создаёт первый запуск ролевого EXE или `RemCardPathSetup.exe`. JSON хранит точный путь к выбранной папке данных. Обновления ищутся внутри неё:

```text
<выбранная сетевая папка данных>\UPD
```

`remcard_data_path.json`, локальные логи и пользовательские каталоги не входят в заменяемую часть программы и сохраняются при обновлении.

## Когда выполняется обновление

Compiled-версия проверяет готовый full-релиз в двух случаях:

1. При обычном запуске. Если найдена более новая версия, старая программа запускает updater и закрывается. После установки снова открывается тот же EXE из той же локальной папки.
2. После штатного закрытия. Проверка выполняется после освобождения БД и role-locks. Если обновление найдено, оно устанавливается без повторного открытия программы.

При обычном запуске проверка обновления начинается только после получения локальной single-instance-блокировки роли. Если эта роль уже открыта, новый запуск лишь показывает существующее окно и не может запустить updater поверх работающей программы.

После аварийного завершения обновление «на выходе» не запускается. При следующем обычном запуске проверка повторится. Dev-версия из Python автоматически не обновляется.

## Состав full-релиза

Релизы публикуются отдельными неизменяемыми каталогами:

```text
UPD\
  releases\
    1.2.3\
      RemCardDoctor.exe
      RemCardNurse.exe
      RemCardOperBlockEmergency.exe
      RemCardOperBlockPlanned.exe
      RemCardPathSetup.exe
      RemCardUpdater.exe
      _internal\
      manifest.json
      ready.ok
```

`manifest.json` содержит версию, точный git-коммит, release snapshot настроек и список файлов с размером и SHA-256. `ready.ok` является единственным marker готовности и создаётся последним. Каталог без `ready.ok` клиенты не считают доступным релизом.

## Локальная сборка и обязательные проверки

Production-сборка запускается менеджером релизов из чистой локальной ветки
`main`, синхронизированной с настроенным GitHub-репозиторием:

```powershell
.\.venv\Scripts\python.exe scripts\build_release.py `
  --expected-version <версия GitHub> `
  --expected-commit <коммит GitHub>
```

Release-скрипт:

1. Проверяет, что `HEAD`, `VERSION`, changelog и release-info уже подготовлены в GitHub.
2. Не изменяет исходники, не создаёт release-коммит и не выполняет `git push`.
3. Запускает обязательные `architecture_safety_check`, fast regression и `flake8 F821`.
4. Собирает полную PyInstaller-папку и проверяет manifest, inventory и release snapshot настроек.
5. Запускает compiled smoke для всех шести EXE.
6. Публикует готовый пакет в локальный тестовый `UPD`:

```text
C:\Project\RemCardTestData\UPD\releases\<версия>
```

Путь можно изменить переменной `REMCARD_BUILD_TARGET_DIR`, но он должен оставаться локальным. Release-сборка не публикует файлы напрямую в сетевую production-базу.

Если любая проверка, сборка или smoke завершается ошибкой, локальная публикация
останавливается. Исправьте причину в исходниках, отправьте изменения в GitHub и
повторите полную сборку; вручную обходить gate нельзя.

## Обязательная приёмка до production

Готовый локальный пакет проверяется на отдельной тестовой установке, которая указывает на локальную или изолированную тестовую папку данных. До сетевой публикации нужно проверить:

- обновление при запуске;
- обновление после штатного закрытия;
- запуск врача, медсестры и обеих ролей оперблока;
- сохранность `remcard_data_path.json` и правильный путь к тестовой базе;
- отказ на неполном или повреждённом пакете;
- миграции и основные рабочие сценарии, если релиз меняет БД.

Production-папка не используется как канареечная среда. После создания `ready.ok` в сетевом `UPD` новая версия сразу доступна всем клиентам, подключённым к этой базе. Поэтому вся функциональная и update-приёмка должна закончиться до production-публикации.

## Безопасная публикация в сетевую базу

Готовую папку нельзя переносить в production обычным копированием вместе с `ready.ok`: marker может оказаться на сервере раньше остальных файлов. Используйте только публикационный скрипт.

Через JSON рядом с установленной production-копией:

```powershell
.\.venv\Scripts\python.exe scripts\publish_full_update.py `
  --source "C:\Project\RemCardTestData\UPD\releases\<проверенная версия>" `
  --config "D:\RemCard\remcard_data_path.json"
```

Либо с явным путём к сетевой базе:

```powershell
.\.venv\Scripts\python.exe scripts\publish_full_update.py `
  --source "C:\Project\RemCardTestData\UPD\releases\<проверенная версия>" `
  --baza-dir "\\SERVER\Share\RemCardProductionData"
```

`--source` обязателен и должен указывать именно на принятую версию. Это исключает случайную публикацию следующей сборки, если файл `VERSION` уже изменился.

Publisher:

1. Обновляет сведения об `origin` и проверяет, что `source_commit` находится в удалённой ветке.
2. Проверяет версию, snapshot настроек, полный inventory и SHA-256 локального пакета.
3. Копирует файлы в сетевой `.staging-<версия>` без `ready.ok`; при повторном запуске продолжает корректный незавершённый staging.
4. Проверяет скопированные файлы, атомарно переименовывает staging в `releases\<версия>` и создаёт `ready.ok` последним.

По умолчанию publisher разрешает production-путь только через UNC или сетевой диск. Флаг `--allow-local-test` предназначен исключительно для изолированной проверки самого publisher.

После успешной команды работающие пользователи получат обновление при штатном закрытии, а пользователи с закрытой программой — при следующем запуске.

## Как остановить опубликованный релиз

Чтобы версия перестала предлагаться клиентам, удалите только:

```text
<сетевая база>\UPD\releases\<версия>\ready.ok
```

Это остановит новые обнаружения релиза, но не отменит обновление на компьютерах, где updater уже начался или версия уже установлена. Ошибочную установленную версию исправляют новым полным релизом с более высоким номером; опубликованные файлы старой версии не подменяют.

Publisher не восстановит удалённый marker молча. Для осознанного повторного включения уже существующего каталога требуется `--reactivate-existing` после повторной проверки причины остановки.

## Установка на новый компьютер

1. Скопируйте полную папку программы на любой локальный диск.
2. Запустите любой ролевой EXE и выберите общую сетевую папку данных; для последующей смены пути используйте `RemCardPathSetup.exe`.
3. Убедитесь, что рядом с EXE создан `remcard_data_path.json`.
4. Запустите нужную роль. Дальнейшие обновления будут устанавливаться в эту же локальную папку автоматически.

## Защита установки и rollback

Перед заменой updater копирует сетевой пакет в staging внутри текущей папки установки, сверяет manifest и SHA-256 и только затем резервирует старую версию. Staging, backup и рабочая программа находятся на одном локальном диске конкретного ПК, даже если на разных компьютерах используются разные пути.

Запуск updater защищён двумя блокировками: общей сетевой и атомарной локальной в папке установки. Перед резервированием updater отдельно проверяет процессы `RemCard*.exe`, запущенные из обновляемой папки, и ожидает их завершения. Рабочие EXE и `_internal` перемещаются только атомарным переименованием на том же диске; fallback через копирование с последующим удалением запрещён, поскольку заблокированная DLL могла бы оставить частично перенесённый каталог.

При ошибке установки updater удаляет новую часть и возвращает старую версию из backup. Если восстановление выполнено не полностью, ошибка прямо сообщает об этом и сохраняет путь к резервной папке для ручного восстановления.

Прямой запуск `RemCardUpdater.exe` из сетевого release-каталога не может безопасно определить произвольную папку установки. Штатный путь — запустить установленную программу, которая сама передаст updater свой каталог.
