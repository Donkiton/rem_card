# Хранение технических логов: этап 1

Этап меняет только запись и хранение файлов. Состав событий, уровень INFO,
частота синхронизации, блокировки БД и медицинский аудит остаются прежними.
Изменения не требуют этапов сокращения метрик или текстовых трассировок.

## Файлы и совместимость

Пример нового имени:

```text
doctor_20260831_p1234_s<32-символьный идентификатор>_000001_active.log
metrics_20260831_p1234_s<32-символьный идентификатор>_000002_closed.jsonl
audit_20260831_p1234_s<32-символьный идентификатор>_000001_active.jsonl
startup_20260831_p1234_s<32-символьный идентификатор>_000001_active.log
updater_20260831_p1234_s<32-символьный идентификатор>_000001_active.log
```

Каждый процесс и поток записи имеют собственный случайный идентификатор.
Основной процесс и worker реплики больше не дописывают один JSONL-файл.
Техническое audit-зеркало в сетевой папке также получает отдельные сегменты;
сетевые файлы **не включаются** в локальную очистку.

Сегмент закрывается при смене суток, достижении 20 МиБ или штатном завершении
свободного локального потока записи. Завершение программы не ожидает занятых
потоков и best-effort audit-зеркала и не переименовывает сетевые файлы:
оставшиеся `active`-сегменты доступны для чтения и после выхода PID подпадают
под обычные сроки хранения. Локальная очистка по-прежнему не удаляет сетевую историю.
Дата проверяется при записи: перезапуск для перехода через полночь не нужен.
Расширения `.log`/`.jsonl` сохраняются у всех частей. Действующие анализаторы
и сборщик логов пользовательского обращения находят их обычными шаблонами.
Старые файлы не переименовываются и остаются читаемыми.

JSON-запись не режется посередине. Если **одно событие** само больше лимита,
оно сохраняется целиком отдельным сегментом. При ошибке диска повреждённый
фрагмент не дополняется следующим событием: следующая попытка начинает новый
сегмент. Обработка ошибок файловой системы не должна прерывать работу с БД.

## Очистка

Независимый daemon `RemCardLogMaintenance` обслуживает логи при первом
использовании, смене сегмента и каждые 300 секунд, даже если новых событий нет.
Вызовы из UI только запускают/будят worker; обход каталогов не выполняется
на UI-потоке. Наличие ночного бэкапа, роль клиента и доступность БД не нужны.

| Категория | Правило |
| --- | --- |
| Известные текстовые логи RemCard | 30 дней после последнего изменения |
| `metrics_*.jsonl` | 7 дней после последнего изменения |
| Локальные `audit_*.jsonl` | 90 дней после последнего изменения |
| Доставленные crash-отчёты | Прежняя отдельная политика: 180 дней |
| Неотправленные crash-отчёты, native-дампы, session-маркеры | Общая очистка не удаляет |

Совместный бюджет обычных текстовых логов и метрик — **512 МиБ**. Учитываются
зарегистрированные локальные каталоги установки, её резервный TEMP-каталог и
известная вложенная копия `migrated-appdata/logs`. Старейшие закрытые файлы
удаляются до достижения бюджета, даже если срок хранения ещё не истёк.
Это максимальные сроки, а не гарантия хранения всех событий весь период.

Бюджет применяется при проходе очистки, а не как синхронный запрет записи.
Между проходами возможен временный рост. Текущие сегменты живых процессов,
файлы с неопределённым состоянием владельца и недоступные для удаления файлы
сохраняются; если их объём не позволяет уложиться в бюджет, фиксируется
`over_budget`. Нельзя одновременно гарантировать жёсткий размер всей папки
и никогда не удалять защищённые аварийные материалы.

Файлы с суффиксом `closed` неизменяемы. Суффикс `active` защищён, пока PID жив
или его состояние нельзя проверить. После аварийного завершения процесса
остаточные сегменты становятся кандидатами по общим правилам. Повторное
использование PID может консервативно задержать удаление старого сегмента.
Старые имена без PID не удаляются в течение минуты после записи; Windows
дополнительно отклоняет удаление открытого файла.

Очиститель работает только с явным перечнем имён RemCard. Произвольные `.txt`,
JSON, базы, резервные копии, пользовательские обращения и неизвестные папки
не удаляются. Символические ссылки, junction и пути через них пропускаются.
Автоматическая очистка не обходит UNC и сетевые диски. Перед удалением повторно
проверяются размер, время изменения и файловая идентичность.

Итог записывается в `log_maintenance_*.log`: число удалений, освобождённые байты,
число ошибок/пропусков, оставшийся объём и превышение бюджета. Объём crash-папок
учитывается отдельно; его превышение вызывает WARNING, без удаления отчётов.
Локальный audit не входит в бюджет 512 МиБ: наличие best-effort сетевого зеркала
не считается подтверждением доставки или разрешением раннего удаления.

## Управление и откат

| Переменная окружения | По умолчанию | Назначение |
| --- | --- | --- |
| `REMCARD_LOG_STORAGE_ENABLED` | `1` | `0` возвращает прежнюю запись и прежнюю очистку после перезапуска |
| `REMCARD_LOG_CLEANUP_DRY_RUN` | `0` | `1` оставляет новую запись, но автоматическая очистка только считает кандидатов |
| `REMCARD_LOG_MAX_FILE_BYTES` | `20971520` | Максимальный обычный сегмент, 20 МиБ |
| `REMCARD_LOG_TOTAL_BYTES` | `536870912` | Совместный бюджет текстовых логов и метрик, 512 МиБ |
| `REMCARD_LOG_CLEANUP_INTERVAL_SEC` | `300` | Интервал фонового прохода |

При отключении этапа новые существующие сегменты не удаляются специально и
остаются пригодными для анализа. Полный откат включает перезапуск основного
процесса и его workers. Откат **не восстанавливает удалённые файлы**.

## Старые AppData-копии: сначала перечень, затем применение

Первое внедрение рекомендуется провести с `REMCARD_LOG_CLEANUP_DRY_RUN=1`:
проверить перечень и сохранить отдельно материалы незакрытых расследований,
после чего выключить dry-run. Это режим приёмки, а не обязательная зависимость
этапа от ручной очистки.

Старые AppData-исходники автоматически не удаляются. Для разовой очистки
есть отдельная команда из исходного проекта. Пути ниже — примеры, необходимо
указать точную установку. Команда не читает конфигурацию медицинской БД.

```powershell
python scripts/manage_runtime_logs.py --logs-dir "C:\RemCard\logs" --include-legacy --preview "C:\Temp\remcard-log-preview.json"
```

Перечень содержит точные пути, размеры, время изменения и причину выбора.
Существующий файл предпросмотра не перезаписывается. После проверки:

```powershell
python scripts/manage_runtime_logs.py --logs-dir "C:\RemCard\logs" --include-legacy --apply "C:\Temp\remcard-log-preview.json"
```

Каталоги и флаг `--include-legacy` должны совпасть с предпросмотром. При
применении заново рассчитывается допустимый набор: изменённые и активные файлы
пропускаются, новые кандидаты без предварительного просмотра не удаляются.
Подмена пути в JSON не позволяет выйти за явные каталоги и правила очистки.
`--apply` — явная операция, она не подчиняется dry-run автоматического worker.

Crash-копии внутри `migrated-appdata/crash-outbox` эта команда не удаляет.
Сетевая история audit/crash и медицинский `medical_audit_log` не входят в этап.

## Приёмка

Автотесты проверяют границы суток и размера, целостность UTF-8/JSONL при записи
тремя процессами, независимые сроки хранения, общий бюджет нескольких каталогов,
сохранность активных и аварийных файлов, отказ удаления, ссылки/junction,
ошибку записи, периодическую очистку без бэкапа и безопасное применение перечня.
Также проверяются существующие сценарии crash-reporting, updater, fallback
и сборки логов пользовательских обращений. Рабочие логи и клинические БД при
этих проверках не используются.
