Актуализировано 30 октября 2026 года. Это постоянная инструкция для новых чатов
и последующих выпусков. Перед работой с установщиком читать её вместе с
[корневым AGENTS.md](../AGENTS.md).

## Текущее состояние и ближайшая задача

- Последний принятый установщик: **5.1.14**, интерфейс пока только русский.
- Для **5.1.15** реализованы русский и английский с переключателем с первого окна,
  русский по умолчанию. Других языков нет. Полная приёмка выпуска выполняется

  Для обычной работы не нужны старые чаты, временный checkout или `tmp/`.

## Что это за установщик

Это собственный фирменный мастер на WPF/.NET Framework 4.8, а не Inno Setup,
NSIS или MSI. Он создан для установки уже собранной Ремкарты с её общим
runtime, выбором каталога, лицензией, ярлыками, журналом и откатом.
В мастере используются ресурсы проекта, светлая/тёмная тема и ЭКГ-индикатор.

Есть два отдельных результата:

1. **Full-пакет программы** — `RemCard.exe`, `RemCardUpdater.exe`, `_internal`,
   release snapshot настроек, `manifest.json` и `ready.ok`. Его собирает
   [scripts/build_release.py](../scripts/build_release.py) из принятого коммита.
2. **Установщик** — `RemCard-Setup-<версия>.exe`. Он содержит готовый full ZIP
   без изменения байтов архива и не перекомпилирует приложение.

Для 5.1.14 использован коммит программы
`05ab7cae77f2a54e1c93f917c6984bacd0178e28`:
[приёмка программы](release_5_1_14_validation.md),
[GitHub Release](https://github.com/Donkiton/rem_card/releases/tag/v5.1.14).
Схема общей БД — 28, минимальный клиент — 5.1.11, обновление необязательное,
миграции отключены. Для будущего выпуска параметры берутся из его задания
и принятого manifest; версия установщика сама по себе не повышает схему БД.

## Инструменты и ресурсы

Сборка выполняется в Windows x64. Нужны Python с Pillow и .NET Framework 4.8.
На текущем компьютере Python: `C:\Project\remcard\.venv\Scripts\python.exe`.
Использовать Python проекта; наличие нужных библиотек проверять в выбранной среде.

Сборщик использует встроенный компилятор:

```text
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe
```

Из корня checkout читаются:

- `VERSION` — должна совпадать с версией full ZIP;
- `LICENSE` — исходный текст лицензии без изменения;
- `icon/remcardicon.png`, `icon/remcardicon.ico`;
- `icon/unified_welcome_background_v3.png`;
- `icon/unified_welcome_background_light_v3.png`.

`build_installer.py` вычисляет корень как `SOURCE.parents[1]`, где SOURCE —
`installer/windows`. Поэтому запускать канонический скрипт в структуре проекта,
а не копировать один Python-файл в произвольный каталог.

## Подготовить принятый full ZIP

Если для нужной версии уже есть принятый full-пакет, использовать его;
не пересобирать приложение только ради упаковки установщика.
Порядок получения нового full-пакета описан в
[how_to_build_and_update.md](how_to_build_and_update.md) и
[versioning.md](versioning.md).

Перед созданием ZIP проверить manifest, source commit, профиль миграций,
inventory и SHA-256 всех файлов штатной `validate_full_package` из
`scripts/build_release.py`. При подготовке необязательного выпуска подтвердить
`database_upgrades_disabled: true`, ожидаемый `min_client_version`
и smoke обоих EXE с запретом миграций.

ZIP должен содержать файлы **в корне**, без обёрточной папки:

```text
RemCard_<версия>_full.zip
  manifest.json
  ready.ok
  RemCard.exe
  RemCardUpdater.exe
  _internal/...
  ...остальные файлы принятого full-пакета
```

В ZIP входят ровно файлы из inventory, сам `manifest.json` и `ready.ok`.
Список файлов сверить полностью; после сжатия прочитать каждую запись ZIP
и проверить размер и SHA-256 относительно принятого пакета. Затем вычислить
SHA-256 всего ZIP и сохранить его вместе с результатом приёмки.

Не упаковывать рабочую установленную копию, пользовательские настройки
подключения, журналы, медицинскую БД или произвольный checkout.
Отслеживаемый словарь `_internal/rem_card/data/mkb/mkb10.db` — штатный ресурс
программы; он допустим при совпадении с принятым inventory.

Builder принимает full-manifest schema 2. Версия сверяется с `VERSION`, а
`min_client_version` и булев `database_upgrades_disabled` — с явно переданным
принятым профилем. Для обязательного 5.1.15 это минимальный клиент **5.1.15**
и `database_upgrades_disabled: false`; схема медицинской БД **29** проверяется
приёмкой приложения (отдельного поля схемы БД в full-manifest нет).
Для необязательных выпусков явно передавать `disabled` и согласованный минимум.
Не менять поля принятого manifest, чтобы обойти отказ сборщика. Builder читает
каждый файл ZIP и сверяет размер/SHA-256; проверяет также состав, повторяющиеся
имена, пути и ссылки. Исходные байты ZIP и manifest сохраняются.

## Собрать установщик

Пример из корня проекта; пути и версию заменить на принятый выпуск:

```powershell
$python = '.\.venv\Scripts\python.exe'
$package = 'C:\path\to\accepted\RemCard_5.1.15_full.zip'
$zipSha = (Get-FileHash -LiteralPath $package -Algorithm SHA256).Hash.ToLowerInvariant()
$runId = Get-Date -Format 'yyyyMMdd-HHmmss'
$output = Join-Path (Get-Location) ("tmp\installer-5.1.15-build-" + $runId)

& $python installer\windows\build_installer.py `
  --package $package `
  --expected-sha256 $zipSha `
  --expected-min-client-version 5.1.15 `
  --expected-database-upgrades enabled `
  --output-dir $output
```

Самостоятельное вычисление SHA не заменяет проверку происхождения и приёмку
ZIP: он должен совпасть с сохранённой контрольной суммой принятого архива.
Выбирать новый output-каталог, чтобы не перезаписать предыдущую сборку.

В output появятся финальный `RemCard-Setup-<версия>.exe`, `build-report.json`
и вспомогательные ресурсы/stub/деинсталлятор. Пользователю передаётся финальный
Setup EXE. Вспомогательные файлы output не являются отдельной полной поставкой.
Сохранить SHA установщика, SHA исходного ZIP, source commit программы и отчёт.

Сборка не повышает версию приложения, не создаёт коммит и не публикует файлы.
Версия assembly, интерфейса и payload берётся из принятого выпуска.

## Обязательная изолированная приёмка

```powershell
$installer = Join-Path $output 'RemCard-Setup-5.1.15.exe'
$packageDirectory = 'C:\path\to\accepted\full-package-5.1.15'
$qaRoot = Join-Path $env:LOCALAPPDATA `
  ("Temp\RemCard-installer-QA-5.1.15-" + $runId)

& $python installer\windows\verify_installer.py `
  --installer $installer `
  --package-directory $packageDirectory `
  --expected-min-client-version 5.1.15 `
  --expected-database-upgrades enabled `
  --qa-root $qaRoot
```

Каталог должен быть новым, иметь префикс `RemCard-installer-QA-` и находиться
в `%LOCALAPPDATA%\Temp`. Verifier проверяет эти границы и не использует живую
установку. Перед любым ручным рекурсивным удалением/перемещением проверить
разрешённые абсолютные пути и принадлежность конкретному QA-каталогу.

Verifier проверяет:

1. Полную проверку встроенного payload и отказ установки в корень диска.
2. Первую установку и SHA-256 всех программных файлов по manifest.
3. Отсутствие установленного `ready.ok`, наличие деинсталлятора и метаданных.
4. Запуск обоих установленных EXE в `--compiled-smoke`, ожидая профиль миграций
   из проверенного manifest (`REMCARD_SMOKE_EXPECT_NO_DATABASE_UPGRADES=0`
   для 5.1.15). Сам compiled smoke общую медицинскую БД не открывает.
5. Переустановку с сохранением подключения, журналов и неизвестного root-файла.
6. Контролируемую ошибку после первого атомарного переноса (`--fail-after 0`),
   откат и повторную сверку inventory.
7. Удаление управляемой программной части с сохранением пользовательских файлов.
8. Неизменность регистрации приложения в HKCU.

Test-режимы не регистрируют программу, не создают ярлыки, не запускают обычную
работу приложения и не открывают центральную медицинскую БД.
Успешный результат — `reports/acceptance-summary.json` с `ok: true`,
`user_files_preserved: true`, `registry_unchanged: true` и ожидаемым SHA EXE.
Отчёт и связанные JSON/logs сохранить отдельно от программного пакета.

Обычная регистрация, ярлыки и интерактивная отмена не проверяются CLI verifier;
при изменении соответствующего кода нужны отдельные изолированные проверки.

## Проверка экранов

В готовом EXE есть режим рендера без установки:

```powershell
& $installer --ui-smoke --preview welcome `
  --language en `
  --target 'C:\isolated\preview-target' `
  --render-preview 'C:\isolated\welcome.png' `
  --report 'C:\isolated\welcome.json' --auto-close-ms 15000
```

Доступны `welcome`, `license`, `location`, `review`, `progress`, `error`,
`uninstall`. `--language ru|en` выбирает язык; без параметра используется русский.
Выбирать явные новые пути отчётов.
`error` — искусственный экран для визуальной проверки, не реальная ошибка установки.
Проверить `ok` в JSON и просмотреть PNG: номер версии, читаемость, кнопки,
длинные пути, отсутствие обрезания и наложений.

Полный UI smoke (14 рендеров, два переключения состояния и русский по умолчанию):

```powershell
$uiRoot = Join-Path $env:LOCALAPPDATA ("Temp\RemCard-installer-QA-ui-" + $runId)
& $python installer\windows\verify_ui_languages.py --installer $installer --output-dir $uiRoot
& $python -m unittest discover -s installer\windows -p test_installer_localization.py -v
```

До появления принятого full ZIP можно использовать `--build-preview-fixture`
вместо `--installer`: он компилирует ясно обозначенный `RemCard-PREVIEW-ONLY.exe`
с искусственными байтами приложения, только для UI. Его нельзя распространять
или использовать для compiled-smoke/приёмки настоящей установки.
Отдельный `--ui-smoke --language-state-smoke --report <JSON>` проверяет сохранение
папки, режима выбора, параметров, согласия, темы, текущего прогресса, журнала,
ошибки и режима удаления при RU → EN → RU. Тесты не устанавливают приложение,
не создают выбранный target и не меняют реестр.

## Поведение установленной копии

Обычная установка персональная: `%LOCALAPPDATA%\Programs\RemCard`, без
повышения прав; можно выбрать другой каталог. Регистрация — в HKCU текущего
пользователя, ярлыки создаются по выбранным параметрам.

При установке `ready.ok` пропускается. `RemCardUninstall.exe` и
`remcard_installation.json` создаются в конечной папке; они не добавляются
в исходный ZIP и его full-manifest. Root-конфигурация подключения, журналы
и неизвестные пользовательские root-файлы сохраняются при переустановке
и удалении. `_internal` относится к управляемой программной части.
Внешняя папка общей базы не является целью установки или удаления.

## Два языка в следующем установщике

**Статус: реализовано в исходниках 5.1.15; в 5.1.14 отсутствует.**
Поручение пользователя от 29 октября 2026 года:

- Первый следующий новый выпуск установщика после 5.1.14 и дальнейшие
  выпуски должны предлагать русский и английский, без других языков.
- Переключатель должен быть доступен с начала мастера. По умолчанию сохранять
  русский; переключение должно обновлять видимые строки без потери выбранной
  папки, параметров, согласия с условиями и состояния установки.
- Локализовать шаги, кнопки, подписи, подсказки, диалоги, прогресс,
  ошибки, завершение и интерфейс деинсталлятора. Исходный `LICENSE`
  продолжает браться из репозитория без автоматического переписывания.
- CLI-параметры, машинные JSON-ключи и диагностические коды остаются стабильными.
- Это локализация WPF-установщика; существующие переводы Qt-приложения
  не означают, что WPF уже поддерживает эти языки.
- При реализации проверить оба языка, переходы между шагами, смену языка
  и отсутствие обрезания длинных надписей. Сохранить прежние проверки
  payload, установки, переустановки, отката, удаления и обоих EXE.

Переключатель доступен также при ошибке и в деинсталляторе. Смена языка
перерисовывает строки, сохраняя выбранные параметры, согласие, тему, прогресс,
журнал и открытый диалог. Каталог переводит только представление; исходный
LICENSE, пути, идентичность ярлыков/регистрации и диагностические коды не меняются.
Сообщения Windows могут содержать исходный системный текст, который сохраняется
как техническая подробность. Не пересобирать EXE 5.1.14 и не заменять его assets.

## Передача на рабочий стол и GitHub

После приёмки копировать финальный Setup на рабочий стол и сравнить SHA-256
копии с `build-report.json`. Подготовка установщика сама по себе не разрешает
публикацию: учитывать явное поручение и уже выданные разрешения пользователя.
Изменения исходников в GitHub отправляются через PR, если не указано иное.

При разрешённой публикации подготовить установщик, полный ZIP и `SHA256SUMS.txt`.
Tag/Release должен соответствовать точному коммиту программы. Сначала загрузить
assets в draft, сверить удалённые размеры и SHA с локальными, затем опубликовать
и проверить публичные ссылки. Не удалять предыдущие Releases автоматически.
Если удаление поручено, отдельно учитывать заданную пользователем судьбу тегов.
Удаление Release и удаление Git-тега — разные операции.
