# Источник истины и межкомпьютерная синхронизация

## Область действия

Контракт описывает штатный `network`-режим врача и медсестры. Аварийная БД
оперблока, архивные БД и восстановление имеют отдельные правила.

## Источник истины

Единственный источник клинической истины — центральная `archiv/rao_journal.db`
после успешного `COMMIT`.

- `change_log` — индекс уведомлений об уже зафиксированных изменениях, а не
  журнал повторного применения операций;
- local replica — read-only копия центральной БД; первая/полная копия создаётся
  SQLite Backup API, последующие поколения могут собираться из локального
  кандидата и согласованного набора изменённых строк;
- `ReadCoordinator`, оперативные snapshots и persistent cache — производные
  read-модели;
- локальный черновик и очередь записи не считаются сохранёнными данными.

Ни snapshot, ни cache, ни replica не могут подтверждать успешность записи.

## Путь записи

```text
кнопка UI
  -> локальная валидация/черновик
  -> DataService/очередь записи
  -> FileWriteLock + BEGIN IMMEDIATE
  -> изменение клинических таблиц
  -> trigger добавляет строки change_log в той же транзакции
  -> COMMIT
  -> success callback на исходном ПК
```

До `COMMIT` UI обязан показывать pending/несохранённое состояние. Ошибка или
`ROLLBACK` не должны оставлять визуальное подтверждение сохранения. Ошибка
построения post-commit snapshot не отменяет уже завершившийся `COMMIT`.

## Появление записи на втором компьютере

Второй компьютер не получает snapshot первого компьютера:

```text
central change_log
  -> DataUpdateMonitor
  -> SyncCoordinator
  -> invalidation ReadCoordinator/widget cache
  -> чтение central DB или достаточно свежей local replica
  -> применение snapshot/read-модели в UI
```

При здоровой сети monitor опрашивает курсор примерно раз в две секунды. Если
replica не достигла обязательного cursor, чтение должно перейти на central DB.

## Контракт snapshot

Один snapshot обязан выбрать источник только один раз:

- `local_replica`: все SELECT выполняются на одной генерации файла; atomic swap
  реплики ждёт завершения snapshot;
- `central`: используется одно короткоживущее read-only connection без длинной
  read-транзакции, чтобы не задерживать клинический `COMMIT` в
  `journal_mode=DELETE`;
- cursor фиксируется до чтения payload и относится к выбранному источнику;
- позднее обращение за cursor внутри той же сборки возвращает зафиксированное
  значение.

Центральные данные могут измениться во время многозапросной сборки. В этом
случае ранний cursor делает snapshot консервативно устаревшим: monitor/cache
validation обязаны запросить следующую версию. Запрещена обратная ситуация —
старые строки реплики не могут быть помечены более новым central cursor.

Post-commit snapshot строится после транзакции. После локальной записи действует
central-read grace period, поэтому post-commit UI не ждёт отстающую реплику.

## Контракт cache

- cache применяется только как ускорение первого отображения;
- версия cache берётся из того же snapshot/read-scope, что и payload;
- отдельный более новый monitor cursor нельзя присваивать старым строкам;
- snapshot с версией ниже подтверждённого monitor cursor считается устаревшим;
- generation и tombstone запрещают поздней async-записи воскресить удалённый
  cache.

## Неизменяемые ограничения SQLite

- shared DB остаётся в `journal_mode=DELETE`, `synchronous=EXTRA`, `mmap_size=0`;
- WAL для сетевой БД запрещён;
- live DB нельзя копировать обычной файловой операцией;
- snapshot/cache failure не переводит local replica в источник истины;
- проверки выполняются только на синтетической или изолированной тестовой БД.

## Обновление локальной реплики с 5.1.8

Журнал уведомлений определяет затронутые строки. Их текущее содержимое и верхний
cursor читаются в одной ограниченной read-транзакции центральной БД. Повторные
уведомления объединяются; отсутствующая строка означает удаление. Настройки
витальных показателей и operating_tables сверяются по логическим ключам:
журнальные rowid могут измениться после VACUUM. Неотслеживаемые таблицы, включая
аудит и служебные квитанции, сверяются целиком в пределах лимитов.

При неизменной центральной БД повторная сверка пропускается по физическому
признаку изменения: идентичность файла, SHA-256 его 100-байтового заголовка,
размер и mtime. Заголовок читается под настоящим SQLite SHARED lock; допустим
только DELETE-профиль, формат rollback и совпадающие change counter и
version-valid-for. Соединение закрывается после запроса, поэтому не удерживает
файл между опросами. Это проверка метаданных, а не файловая копия live DB.
Правило счётчика определено в [формате SQLite](https://www.sqlite.org/fileformat.html#file_change_counter).
Отсутствующий/неподходящий признак запрещает ускоренный пропуск.

Приватный кандидат клонируется с локальной реплики, никогда с live shared-файла.
Изменения применяются одной локальной транзакцией со снятием и точным
восстановлением триггеров. После foreign_key_check, quick_check, checkpoint и
fsync действует существующая атомарная подмена с rollback. Cursor публикуется
только с соответствующими строками. При ошибке прежняя реплика сохраняется.

Полная копия обязательна при смене источника/цикла/схемы, пробеле истории,
неподдерживаемом протоколе или превышении лимитов: 5000 событий/операций,
4 MiB пакета либо 30% размера БД. В локальном исправлении после 5.1.9 бюджет
сверки отделён от размера изменений: до 250000 просмотренных строк и 32 MiB
логического содержимого суммарно на центральной и локальной стороне. Потоковая
сверка проверяет и старые строки истории, включая изменения и удаления; лимиты
5000 операций и 4 MiB передаваемого пакета сохранены. При превышении бюджета
в диагностике остаются имя таблицы и число строк обеих сторон. Неизменный файл
повторно целиком не копируется. REMCARD_INCREMENTAL_REPLICA=0 возвращает прежний режим.

Проверенный startup master сохраняется локально между процессами с SHA-256 и
квитанцией Windows DPAPI. При повторном входе проверяются источник, схема,
цикл, recovery/quarantine и актуальность реплики. Исходный срок допуска 30 минут
не продлевается переиспользованием или дельтой. Это ограниченный по времени
допуск по предыдущей проверке здоровья, а не новая полная проверка live-файла.
Повреждение, подмена, истечение срока или недоступность DPAPI возвращают полный
путь проверки. Локальная копия не даёт права записи и сама не подтверждает
свежесть: после её установки обязательна обычная синхронизация.

## Защита интерфейса и повторов записи в локальном исправлении

Кэш назначений проверяет актуальную версию один раз перед ранним возвратом.
Запоздавший cache/delta результат проверяется по поколению кэша и версии, а
полная загрузка после неудачной дельты — также по минимальной уже прочитанной
версии. Подтверждённый более новый snapshot нельзя заменить более старым.
Объединённая загрузка (coalesced) тоже не возвращает cache/stale ниже уже
прочитанной минимальной версии; завершение другого refresh не отменяет эту проверку.
Поколение и нижняя граница версии сохраняются при LRU-вытеснении, пока
загрузка этого контекста выполняется; после завершения последнего чтения
служебное состояние вытесненного ключа освобождается.
Полный refresh перед публикацией проверяет и захваченное поколение кэша,
и принадлежность активного запроса. Проверка запроса и запись кэша выполняются
атомарно в порядке cache lock → refresh lock; отменённый, заменённый другим
запросом или помеченный как непригодный refresh не публикуется после внешнего guard.
Сохранение продолжает проверять expected_version / expected_revision в
центральной транзакции: скорость доставки уведомления не заменяет эту защиту.

Обработчик уведомлений медсестры использует только статус из snapshot того же
пациента, даты и открытия карточки. Неизвестный статус запрашивается асинхронно.
Смена статуса всегда запускает обновление, даже если предыдущий snapshot
содержал исход. Ответ предыдущего открытия карточки отбрасывается.

Автоматическое создание начального статуса допускает максимум два повтора
после commit timeout с подтверждённой SQLite busy/locked причиной. Контроллер
завершает rollback до возврата этой ошибки. Ошибки ожидания блокировки или
начала транзакции (`before commit`) этот повтор не запускают. Неопределённый исход сетевой записи
и постоянные ошибки повторять нельзя; общий срок операции — 15 секунд.
Для этой операции generic LocalWriteQueue имеет queue_retryable=False и
queue_retries_left=0: единственный владелец повторов — ограниченный цикл сервиса.

SQLite BUSY/LOCKED на известных этапах чтения центрального источника считается ожидаемой конкуренцией и
оставляет обычный интервал синхронизации. Прочие ошибки, включая READONLY,
ошибки локального кандидата и ошибки неизвестного этапа,
сохраняют защитный backoff; через IPC передаются исходный этап и расширенный
SQLite-код. Само переименование ошибки не считается исправлением READONLY.

## Ночная копия в локальном исправлении

SQLite Backup API сначала создаёт снимок на локальном диске. Общий db.lock и
reader lease ротации удерживаются только во время чтения живой БД. После этого
проверка, SHA-256, загрузка в сетевой `.publishing`, проверка SHA-256 загрузки и
атомарная публикация выполняются без блокировки клинического писателя.

Бюджет чтения остаётся 8 секунд, общий worker имеет жёсткий тайм-аут. Пока
идёт само чтение, клиническая запись ещё может ждать db.lock; автоматического
прерывания копирования по появлению ожидающего писателя нет. Долгая загрузка
готового файла больше не удерживает этот lock. При ошибке старая дневная копия
сохраняется; публикация файла и его JSON-метаданных — две отдельные атомарные
операции, незавершённая пара не считается подтверждённой копией.

## Проверяемые инварианты

1. Успешный `COMMIT` остаётся успешным при отказе snapshot/cache.
2. `ROLLBACK` не создаёт видимой сохранённой записи.
3. Payload и его cursor никогда не происходят из разных генераций replica.
4. Replica ниже required cursor не используется для нового snapshot.
5. Клинические уведомления между ПК идут через `change_log`; изменения таблиц
   без уведомлений обнаруживаются по физическому признаку и полной сверке либо
   backup. Файлы cache между компьютерами не передаются.
