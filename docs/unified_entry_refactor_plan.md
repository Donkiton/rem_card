# Единый вход RemCard — план рефакторинга

Дата: 13.09.2026. Ветка: `codex/unified-entry`. Исходный код: `daeb814bccbcd02312f8814cbbd67f15697c3b84`.

Статус: проектирование и исходные проверки. Реализация приложения ещё не начата. Пользователь разрешил отдельную ветку, аудит, план, исходные тесты и использование подходящих инструментов дизайна. Этот документ не является разрешением на слияние, релиз или публикацию обновлений.

## 1. Результат и границы

В поставке два EXE: `RemCard.exe` с единым входом и `RemCardUpdater.exe` для обслуживания обновлений. Один EXE не означает onefile-упаковку: сохраняем возможность общей папки зависимостей, чтобы распаковка не замедляла запуск.

Четыре доступные роли: врач, медсестра, экстренный оперблок, плановый оперблок. Архив остаётся доступным из врача. Существующие клинические интерфейсы и разграничение РАО/оперблока сохраняют своё назначение.

Новый сценарий: запуск → при необходимости выбор базы → информативная загрузка → приветствие → роль. На одном ПК допускается одно окно RemCard независимо от выбранной роли; повторный EXE поднимает существующее окно, не создаёт второй рабочий процесс. Кнопка «Назад» сектора 8 завершает сеанс роли и возвращает к выбору ролей. Для вложенных страниц проверить сохранение их собственной навигации; выход из рабочего экрана не должен останавливаться на старой промежуточной странице. Центр управления открывается из приветствия в той же оболочке, с кнопкой назад, без нового пароля. Изолированные тестовые экземпляры остаются в отдельном namespace и не взаимодействуют с рабочим приложением.

Параллельные сеансы одной роли на разных ПК разрешаются после проверки конфликтов записей. Технические работы запрещают новые входы и возвращают активные роли к приветствию после предупреждения. Несовместимый клиент должен обновиться перед входом.

Не включаем в этот рефакторинг переход на серверную СУБД, новую систему назначения лечения, массовый редизайн рабочих карт или автоматическое подтверждение клинических черновиков.

## 3. Проектируемые компоненты

Названия ниже предварительные; это новые ответственности, а не утверждение о наличии таких файлов.

| Компонент | Ответственность |
|---|---|
| AppShell | Загрузка, приветствие, настройки, геометрия, обновление, переходы |
| StartupCoordinator | Последовательность реальных этапов, прогресс, отмена и ошибки |
| RoleSessionController | Вход, состояние активной роли, завершение, смена, отбрасывание запоздавших ответов |
| SessionRegistry | Уникальные сеансы, компьютер, роль, версия, поколение состояния и подтверждение освобождения ресурсов |
| MaintenanceCoordinator | Запрет входов/новых записей, предупреждение, ожидание освобождения, эксклюзивная работа |
| MaintenanceNotifier | Подписка на события служебной папки, повторное чтение, восстановление после потерь связи |
| CompatibilityService | Чтение требований базы без запуска миграций, решение о допустимости входа |
| UpdateCoordinator | Существующее обнаружение пакета, кнопка, завершение и передача управления updater |

Состояния оболочки: CONFIGURING, LOADING, WELCOME, ENTERING_ROLE, ROLE_ACTIVE, LEAVING_ROLE, UPDATE_REQUIRED, ERROR. Настройки — отдельная страница оболочки, а не клиническая роль. Отказ и повторный запуск этапа не должны создавать второй QApplication или дублировать сервисы.

Ресурсы принадлежат либо оболочке, либо конкретному сеансу. Все задачи роли получают идентификатор поколения: ответ старой роли/базы после выхода не применяется. На приветствии после техработ не остаются фоновые обращения к клинической БД, включая реплики, резервирование, аналитику и обновление экранов.

## 4. Путь базы и учреждение

### Выбор базы

- Первый запуск без настроенного пути: кастомный диалог до клинического bootstrap. Проверка пути выполняется вне UI-потока.
- Сохранённая корректная настройка подхватывается без повторного вопроса. Повреждённая настройка объясняется пользователю; недоступная сеть не трактуется как пустая новая база.
- «Обслуживание → Путь к базе»: текущий путь, выбор, проверка, сохранить, перезапустить. До перезапуска активные сервисы продолжают ссылаться на прежний контекст; смешение баз запрещено.
- Разделить подключение существующей базы и её создание. Не создавать пустую БД по ошибочно введённому сетевому пути.
- Учитывать запрет записи рядом с EXE. Если потребуется перенос конфигурации в пользовательский каталог, разработать совместимую миграцию отдельно, не менять путь хранения молча.
- Изолировать кэши, черновики, настройки контекста и идентификаторы экземпляров по базе; один лишь выбранный путь не должен позволять применить черновик к другой базе.
- При активной аварийной сессии смена базы проходит через существующее разрешение аварийного состояния.

### Название учреждения

- «Интерфейс → Учреждение»: полное и краткое названия, оба пустые по умолчанию. Краткое название вводится явно.
- Общие настройки выбранной базы; локальный кэш нужен только для раннего показа и привязан к идентичности базы. При другой базе чужое название не показывается.
- На загрузке полное название и постоянное «Отделение реанимации и интенсивной терапии». Без названия остаётся только отделение.
- На приветствии краткое название, «ОРИТ», текущие дата/время. При пустом названии отсутствует лишний разделитель.
- Длинный текст не перекрывает прогресс и кнопки. Обновление настройки отражается при следующем запуске; можно обновить открытую оболочку по событию сохранения.

## 5. Внешний вид и подготовка данных

Два пользовательских изображения — визуальные ориентиры; роли и подписи определяются запросом. Нижние презентационные подписи за границами окон не входят в приложение. Версию `v4.3.7` из картинки не фиксируем: используем версию сборки. Нижний левый дубль версии убирается.

UI/UX Pro Max используется для обратной связи, читаемости, фокуса и адаптации размеров с учётом Qt/PySide6. Проверенный поиск `loading progress feedback` дал рекомендации показывать этапы, сохранять стабильный layout и избегать мерцания индикаторов. Web/CSS-примеры не переносим буквально в Qt.

Dreamloop при необходимости используется для итераций «целевой вид → реальный скриншот → исправление». До применения читается его входной скилл; это не замена функциональной проверке. Генератор изображений допустим для фоновой иллюстрации, растровых значков и других нужных ассетов. Не требуется переводить всё в SVG. Текст, интерактивные элементы и прогресс остаются живыми Qt-компонентами, не вшиваются в фон. Используется доступный инструмент генерации; конкретная модель подтверждается инструментом, не названием в плане.

Ассеты: отдельный медицинский фон без узнаваемых пациентов и встроенных надписей, достаточное разрешение для HiDPI, контролируемый размер файлов, прозрачность при необходимости. Размытие/затемнение лучше подготовить заранее, без тяжёлой обработки каждого кадра. Иконка EXE — существующая RemCard. Временные результаты генерации не включать в сборку автоматически.

Пять стадий: локальная конфигурация → доступность/совместимость → настройки/справочники → общие службы → готовность приветствия. Галочка появляется только после успеха. Неизмеримый подэтап может иметь неопределённый индикатор внутри своего диапазона; проценты не изображают завершённую работу при зависшей операции. Ошибка останавливает этап и даёт осмысленное повторение/смену пути.

Появление оболочки требует минимальных импортов. В фоне готовятся безопасные общие данные; объекты QWidget создаются только в UI-потоке. Не начинать клиническую запись и миграцию как побочный эффект прогрева. Подготовка роли отменяема при техработах. Не загружать четыре полные роли ради предполагаемой экономии секунды.

Геометрия оболочки и каждой роли хранится раздельно и локально. Начальный размер оболочки выбирается после проверки 1366×768; фиксированного размера нет. Четыре карточки в ряд при достаточной ширине, компактный вариант 2×2 при уменьшении. Первый вход в роль — развёрнутое окно, не безрамочный киоск; дальнейший вход восстанавливает её состояние. После отключения монитора окно возвращается в доступную область.

Проверки внешнего вида: 1366×768 и 1920×1080, масштаб 100/125/150/200% при достаточном логическом размере, длинные названия, пустое учреждение, смена монитора. Tab/Shift+Tab, Enter/Space, явный фокус, статусы с текстом, отсутствие мигающих отвлекающих эффектов. Существующие локальные темы рабочих ролей не должны случайно сбрасываться стилем оболочки.

## 6. Несколько одинаковых ролей

- Заменить эксклюзивную роль уникальной регистрацией сеанса. Различать идентичность компьютера, процесса, сессии, базы и роли; «doctor» не является уникальным автором изменений.
- Проверить авторство в журнале действий и `last_modified_by`: компьютер и сессия дополняют существующего пользователя, а не подменяют медицинского исполнителя.
- Сохранить `db.lock`, транзакции и общий snapshot gate. Не ослаблять правила захвата чужого замка и не включать local-first/outbox в рамках задачи.
- Реестр сеансов должен обслуживать ротацию, восстановление, updater и техработы; поиск старых `doctor.lock`/`nurse.lock` заменить во всех потребителях.
- Для каждой операции составить таблицу: что показано пользователю, какая версия прочитана, что проверяется внутри транзакции, что происходит при конфликте.
- Начать с назначений/финализации/удаления и отметок медсестры; затем показатели, питание/баланс, процедуры, анализы, перемещения/исходы, операции/переводы оперблока, настройки справочников.
- Предотвращать не только перезапись поля, но и конфликт множества: два перевода на одну койку, двойное завершение карты, удаление уже выполненного назначения, повторную отметку после тайм-аута ответа.
- При конфликте не терять ввод; обновить актуальное состояние и предложить явное повторное действие. Не делать автоматическое объединение назначения с иным клиническим смыслом.
- Локальные черновики и кэши изолировать по контексту; повторное открытие после миграции проверяет применимость черновика.

Приёмка: два независимых процесса одной роли работают одновременно, видят подтверждённые изменения друг друга, конфликт одной записи не проходит молча. Dev-проверки дополняются compiled-проверками, так как текущий запрет зависит от режима запуска.

## 7. Технические работы

### Протокол

Состояния: OPEN → DRAINING → MAINTENANCE → OPEN. Отдельное состояние UNKNOWN для нечитаемого/недостоверного управления. Служебное состояние хранится вне клинической БД, чтобы приветствие могло оставаться открытым при её закрытии/замене. Документ содержит версию формата, уникальный идентификатор операции, поколение, состояние, инициатора, причину и время публикации. Изменения сериализуются и публикуются атомарно; устаревший клиент не может выключить более новые техработы.

1. При включении DRAINING новые входы сразу запрещены, включая гонку уже начатого входа. Управляющий компьютер тоже завершает свою клиническую роль.
2. Получивший команду клиент показывает 60 секунд и сохраняет идентификатор операции. Дубликат уведомления не перезапускает отсчёт. Длительность отсчитывается монотонным временем; после сна перечитывается состояние.
3. До срока пользователь завершает работу и сохраняет нужный ввод. Предупреждение явно сообщает: «Через 60 секунд начнутся технические работы. Сохраните изменения: несохранённый ввод будет потерян». В срок блокируются новые действия, несохранённый ввод отбрасывается, оболочка показывает приветствие. Автоматическое сохранение/восстановление формы при этом не запускается. Нельзя заставить Qt обработать событие ровно в срок при зависшем UI; такой клиент остаётся неподтверждённым.
4. Принятые записи завершаются или безопасно откатываются. Не прерывать поток SQLite принудительно. Остановить workers/мониторы, освободить все соединения и файловые ресурсы роли. Подтверждение означает именно освобождение, не скрытие окна.
5. Только после подтверждений и получения исключительного доступа перейти в MAINTENANCE. Показать инициатору список: ожидает, отсчёт, завершает, освобождён, недоступен, старая версия.
6. При отмене DRAINING повторный вход доступен после проверки; уничтоженная роль создаётся заново. При выключении MAINTENANCE проверяются база/поколение/совместимость перед входом.

Не считать отсутствие heartbeat доказательством закрытой базы. Зависший или отключившийся компьютер нельзя «забыть» исключительно по возрасту записи. Требуется проверяемое исключительное владение ресурсами; если его нет, интерфейс не объявляет базу свободной. Новая запись и изменение режима согласуются в одном протоколе допуска, без окна между проверкой и началом записи. Миграции, ротация, восстановление, настройки и фоновые записи также участвуют в этом протоколе.

При работе с клинической БД ограничить Центр управления безопасными страницами: статус техработ, путь, сведения об обновлении. Страницы, держащие БД/настройки, не должны мешать заявленному объёму обслуживания. Режим сохраняется после закрытия инициатора; другая оболочка может прочитать его и выключить. Это не новый пароль: используются существующие права файловой системы.

### Уведомления

Основной канал — ожидание изменения служебного каталога Windows/SMB, не опрос таблицы SQLite. Наблюдать каталог, поскольку атомарная замена файла меняет его объект. Событие является сигналом перечитать долговечное состояние, а не единственным носителем команды. Учитывать дубликаты, пропуски, замену каталога, переполнение и реконнект.

Дополнить редкой контрольной сверкой (предварительно 30 секунд) и чтением при входе/восстановлении связи. Это компромисс для восстановления, а не гарантия освобождения базы. При отсутствии поддержки SMB notifications проверить на тестовой сетевой папке и явно выбрать резервную стратегию; отдельный сервер сообщений сейчас не требуется.

Windows документирует поддержку SMB 3.0 и возможность потери уведомлений при переполнении: https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw . Qt прекращает наблюдение отдельного файла после удаления/переименования: https://doc.qt.io/qt-6/qfilesystemwatcher.html . Поддержка на реальном сервере пока не проверена.

### Черновики, сеть и старые клиенты

Уточнение пользователя: потери несохранённого ввода после минуты предупреждения допустимы. Не создавать механизм автоматического восстановления форм после техработ и не подтверждать лечение ради выхода. Инвалидировать также отложенные autosave/callback и локальные временные состояния закрытого сеанса, чтобы они не вернули отброшенный ввод. Ранее явно сохранённые данные и самостоятельные сохранённые черновики не удалять под видом очистки незавершённой формы; никакой их автоматической записи поверх актуальной базы при следующем входе.

Различать: (а) ввод не отправлен — допускается отбросить; (б) сохранение принято в очередь/началась транзакция — требуется завершить и установить исход; (в) COMMIT подтверждён — данные сохранены независимо от доставки callback; (г) исход неизвестен — это блокатор объявления базы свободной, а не несохранённая форма. После техработ создаётся свежий контекст роли, заново читается актуальная база и проверяется совместимость. Если нужен новый клиент/схема, выполняется обновление и перезапуск; старый набор объектов роли не оживляется.

Плановое обслуживание не трактуется как авария сети и не запускает автономную запись в обход режима. Для уже работающей аварийной сессии отдельно согласовать остановку и последующее объединение; нельзя утверждать освобождение общей базы на основании недоставленного сигнала. Возврат аварийных данных проверяет текущую совместимость и режим обслуживания.

Первое внедрение требует закрытия старых клиентов и обновления всех рабочих мест: они не умеют получать новую команду. После внедрения протокол не гарантирует контроль произвольных старых/внешних SQLite-программ; для ручных операций учитывается фактический исключительный доступ.

## 8. Обновления и совместимость

- Сохранить обнаружение обновлений при запуске и полном выходе. На входе в роль делать дешёвую проверку совместимости, а не каждый раз полный поиск пакетов.
- Разделить версию формата full-manifest, версию приложения, схему клинической базы, схему настроек и поколение протокола. Это разные значения.
- Развить `client_policy.json`: минимальный клиент/требования совместимости повышаются по реальному несовместимому изменению. Не каждое добавление колонки автоматически означает несовместимость, но совместимость должна быть явно доказана.
- Проверять требования до writable bootstrap и до автоматической миграции, включая вход из давно открытого приветствия. После ротации инвалидировать старые токены и кэши.
- Миграция выполняется одним владельцем при эксклюзивном доступе с резервной копией/проверкой. При частичном сбое не оставлять OPEN и ложную совместимость. Отдельно определить порядок публикации требований, миграции и успешного завершения.
- Доступный необязательный пакет даёт кнопку «Обновить», вход остаётся доступным. Обязательный пакет блокирует роли и объясняет причину. Отсутствие/повреждение обязательного пакета даёт ошибку, не обход блокировки.
- «Обновить» завершает сеансы этой установки, закрывает оболочку, запускает updater, проверяет пакет/установку и возвращает единый вход. Сбой не выдаётся за успешное обновление; используются существующие механизмы восстановления обновлятора.
- Обновить списки EXE, restart arguments, обнаружение процессов, smoke-проверки и шаблоны сборки. Старые роли удалять только как известные компоненты прежней поставки; чужие файлы сохранять.
- Проверить переход старый пакет → новый пакет реальным старым updater: возможен промежуточный совместимый выпуск, если старый updater отвергает новую структуру. Это обязательное исследование до выбора способа доставки.
- Проверить старые ярлыки и технический updater. Миграцию ярлыков ограничить точно известными ярлыками RemCard; решение о переходном периоде не должно незаметно вернуть шесть EXE в окончательную поставку.
- При включённых техработах полное закрытие приложения не запускает неподходящую ротацию/аварийный переход как побочное действие. Обновление остаётся доступно из заблокированного приветствия.

## 9. Рабочие этапы и критерии завершения

| Этап | Изменения/результат | Проверка выхода с этапа |
|---|---|---|
| E0 | Исходные тесты, протокол измерений, фиксация известных ограничений | Отчёт привязан к SHA; ошибки исходной версии отделены от будущих регрессий |
| E1 | Карта владения ресурсами и контроллер завершения роли | Вход/выход/повторный вход каждой роли; нет оставшихся соединений и старых callback |
| E2 | Лёгкая оболочка, путь, учреждение, геометрия | Первый/повторный запуск, отмена, сеть недоступна, смена базы, 4 роли и настройки |
| E3 | Загрузка, ассеты, карточки, фоновая подготовка | Реальный прогресс и скриншоты Qt; измерения появления и полной готовности |
| E4 | Полный аудит записи и реестр сеансов | Таблица операций, конфликты в двух процессах, учёт ротации/восстановления/updater |
| E5 | Снятие эксклюзивности сетевой роли | Два клиента каждой роли; совместное РАО/оперблок без смешения данных |
| E6 | Протокол обслуживания и уведомления | Таймер, открытые формы, принятые записи, потеря сети/сна/события; реальное освобождение БД |
| E7 | Совместимость, новый состав поставки и обновление | Старый → новый пакет, обязательный/необязательный пакет, сбой установки и повторный вход |
| E8 | Итоговое сравнение и пользовательская приёмка | Повтор E0, функциональная матрица, Windows/SMB и packaged-проверки, список ограничений |

Изменения делаются небольшими законченными блоками в экспериментальной ветке. При переносе кода сохраняются старые рабочие пути до прохождения соответствующих проверок. Не открывать сеть для нескольких одинаковых ролей раньше E4. Не публиковать пробную сборку в рабочую папку UPD. Коммиты/отправка документа и реализации — по отдельному поручению пользователя; PR/слияние/релиз также отдельно.

## 10. Протокол сравнения «до / после»

### Исходная среда

Исходники не изменяются. Используем текущий `.venv`, фиксируем Python/PySide6, версию Windows, SHA и результаты. Группы quality/core/ui/regression запускаются последовательно существующим `scripts/run_ci_checks.py`, чтобы не смешивать конкурирующие измерения. Полный pytest `all` поверх уже прошедших core/ui не повторяем.

База, profile, AppData, ProgramData, emergency root, логи, config и Qt-настройки перенаправляются в `tmp/unified-entry-baseline`. Дополнительный запусковой hook использует существующий `app.isolated_test_runtime.isolate_qsettings()`, потому что overload `QSettings(organization, application)` иначе может писать NativeFormat. Hook находится только в игнорируемом tmp и не изменяет приложение. Тесты переключения dev-пути используют собственные временные каталоги/подмены.

Текущая рабочая БД не используется и не копируется. Для компонентного benchmark создаётся синтетическая база штатным тестовым seed-builder. Результаты локального диска не объявляются результатами SMB.

### Что измеряем

| Метрика | Метод и смысл |
|---|---|
| Первый видимый кадр | От запуска процесса до подтверждённой отрисовки оболочки; отдельно от времени импортов |
| Готовность приветствия | Все кнопки доступны, проверка статуса закончена; отдельно первый запуск с настройкой |
| Готовность роли | От нажатия роли до завершённого первого снимка и доступного рабочего экрана; человеческая пауза выбора исключается |
| Полное время | Запуск → реально готовая роль при одинаковом искусственном моменте выбора |
| Первое открытие карты | От выбора пациента до полного набора нужных блоков; пустой или устаревший экран не считается готовым |
| Сохранение | Нажатие → подтверждённый commit, отдельно → обновлённый экран; одинаковые операции и данные |
| Доставка изменений | Commit клиента A → применение актуального состояния клиентом B |
| UI-задержки | Максимальные паузы event loop, длительные зависания, зависимость от прогрева |
| Ресурсы | Память, CPU в простое/загрузке, число потоков/соединений; после 10 переключений ролей |
| Сеть | Запросы монитора, события и чтения control-файла, объём снимков, восстановление после разрыва |
| Техработы | Публикация → получение, получение → запрет действий, срок → освобождение; отдельно каждый клиент |
| Поставка | Размер/число файлов, запуск EXE, длительность обновления и корректный restart |

Существующий `scripts/startup_benchmark.py` — компонентный benchmark. Врач/медсестра измеряют импорты/bootstrap/создание виджетов и не доказывают готовность первой карты. Оперблок содержит более подробные метрики, но общий legacy-role `operblock` не заменяет отдельные проверки planned/emergency. Не выдавать сумму фаз за полноценный запуск EXE. Если скрипт не соответствует текущему API, зафиксировать ошибку, не исправлять приложение ради baseline.

Для предварительного компонентного измерения достаточно 3 независимых процессов на роль, с сырыми значениями и медианой. Это не p95 и не статистически надёжное доказательство ускорения. Полное сравнение перед приёмкой: минимум 10 прогретых запусков на каждую роль, 3 запуска с очищенным только тестовым кэшем; порядок/настройки/данные совпадают. Холодный процесс, пустой кэш приложения и холодный дисковый кэш ОС — разные режимы; последний не обещаем без отдельной процедуры.

Для рабочих задержек — серия одинаковых операций на синтетических пациентах с достаточным числом повторений для распределения; сначала один клиент, затем 2 и 3, затем 5 при необходимости. На SMB измерять отдельно, без переносов цифр локального диска. Сохранить исходный seed, описание заполнения, размер/числа записей, версии и сырые отчёты. Производственный размер набора потребует отдельного репрезентативного синтетического fixture до реализации; один пациент не моделирует нагруженную базу.

Предварительный критерий производительности: сопоставимые медианы полной готовности роли, открытия карты и сохранения не должны ухудшиться более чем на max(10%, 100 мс) без объяснённой причины. Порог предварительный, проверяется относительно разброса baseline до кодовых изменений. Безусловные критерии: нет потери/дублирования записи, ложной готовности, неограниченного роста ресурсов и новых зависаний. Улучшение первого кадра при ухудшении полной готовности показывается прямо, а не объединяется в одну «скорость».

Тесты после реализации запускаются в той же изоляции. Сравнить набор тестов: проверки старых шести EXE и эксклюзивности роли должны быть явно заменены новыми контрактами, не просто удалены ради зелёного результата. Время pytest не является скоростью приложения. Скриншоты offscreen не заменяют реальную проверку Windows, HiDPI и сети.

## 12. Согласованные уточнения и надёжность

Ответы получены: одно окно на ПК, перемещение между ролями через «Назад» сектора 8; при техработах минута на сохранение и допустимое отбрасывание оставшегося несохранённого ввода. Автоматическое восстановление форм после техработ не требуется. Это разрешение не распространяется на потерю уже принятого сохранения или подтверждённых данных. При обычном выходе кнопкой «Назад» допускается предупреждение о несохранённом вводе; автоматический отсчёт и принудительное отбрасывание относятся именно к техработам.

Пользователь отдельно потребовал проверить соединения, сохранения, переносы, получение актуальных данных и достаточность логирования. В E1/E4/E6/E8 обязательны требования и матрица из [аудита надёжности](unified_entry_reliability_audit.md). Полный тестовый baseline уже выполнен; его исходные результаты и ограничения приведены в [отчёте](unified_entry_baseline_2026-09-13.md). Не повторять весь набор при правке документов.

До реализации составить полную карту владельцев ресурсов, а не ограничиваться главным DatabaseManager. Результат сохранения учитывается на уровне сеанса/операции независимо от жизни формы. Дополнить существующие структурированные метрики сквозными идентификаторами роли/сеанса/базы/операции, переходами и итогами освобождения; не вводить постоянный шум и SQL с клиническими значениями. Изменения логирования внедряются вместе с соответствующим механизмом и тестом, чтобы название события точно отражало реальный результат.
