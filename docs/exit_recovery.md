# Завершение RemCard при сбое сети

Штатный выход сначала останавливает приём новых записей и фоновые задачи,
завершает принятые записи, закрывает соединения БД и затем освобождает
блокировку сессии. Освобождение сетевой сессии и доступа обслуживания
выполняется в фоне: ожидание SMB не должно блокировать интерфейс.

Ошибка освобождения блокировки (например, Windows `WinError 59` после потери
сети) регистрируется как `session_release_failed`. Такой процесс завершает
работу без повторного входа в роль, автоматического обновления или перезапуска.
Ошибка не считается подтверждением успешного освобождения сетевой блокировки.

## Крестик и предельное время выхода

- После запроса закрытия окно остаётся видимым, доступен крестик заголовка.
- Повторный крестик предлагает принудительное завершение. По умолчанию
  выбрано продолжение штатного завершения.
- На завершение процесса отведено 30 секунд с момента принятого запроса
  выхода. Повторные попытки закрытия ресурсов не продлевают этот срок.
- Таймер работает в отдельном потоке и не зависит от обработки событий Qt.
  Он остаётся активным после выхода из цикла Qt, чтобы ограничить зависание
  при завершении процесса. Пока пользователь отвечает на предложение
  обновления, таймер отключён; после ответа начинается новый срок.
- При неудаче запуска обновления или перезапуска таймер отключается,
  приложение остаётся открытым.

Принудительное завершение вызывает `os._exit(2)` только для текущего процесса.
Оно не подтверждает сохранение находившихся в работе записей: неподтверждённые
изменения после повторного входа необходимо проверить. Общие файлы блокировок
и журналы SQLite при этом не удаляются.

## Диагностика и проверки

Перед принудительным завершением предпринимается попытка сохранить локальный
`exit_watchdog_<pid>_<time>.json` с причиной, этапом и длительностью выхода.
Ожидание диагностической записи ограничено 0,1 секунды; неисправность
хранилища журналов не отменяет завершение.

Регрессионные проверки находятся в `tests/test_unified_window_lifecycle.py`,
`tests/test_unified_access.py` и `tests/test_exit_watchdog.py`. Используются
подставные ресурсы и отдельные временные БД. Принудительное завершение
проверяется в дочерних процессах, включая зависший главный поток и
заблокированную запись диагностики.
