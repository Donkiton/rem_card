# Автоматическое обновление сайта и README

Автоматизация работает на GitHub, независимо от компьютера разработчика и
запущенного Codex. Локальные Git hooks устанавливать не нужно.

## Что запускает обновление

Основной workflow — `.github/workflows/sync-public-release.yml`. Он запускается
после публикации стабильного GitHub Release в `Donkiton/rem_card`. Черновики и
предварительные версии не обновляют публичные материалы. Публикация только в
сетевой `UPD` без GitHub Release этот процесс не запускает.

Последовательность:

1. Найти последний опубликованный стабильный релиз.
2. Дождаться установщика, полного ZIP и `SHA256SUMS.txt` — до десяти минут.
3. Сверить имена и URL файлов, размер, статус загрузки и SHA-256 из файла сумм
   с digest соответствующих GitHub assets.
4. Прочитать `app/release_info.json` именно из коммита опубликованного тега.
   Описание незавершённого следующего выпуска из `main` не используется.
5. Создать подписанный сервером GitHub коммит и PR для README и руководств.
6. Дождаться обычных проверок PR, включая обязательный `tests`, и слить PR.
7. Подтвердить данные в `main`, обновить JSON сайта отдельным подписанным PR,
   дождаться проверки сборки сайта и слить этот PR.
8. Обычный workflow GitHub Pages публикует сайт после слияния.

Все коммиты и заголовки PR автоматизации — на русском. Административный обход
правил `main` не используется. Изменение исходного SHA, чужие правки в ветке
бота, продвижение `main` или неуспешные проверки останавливают слияние.

`retry-public-release.yml` раз в сутки повторно запускает основной workflow.
Это отдельный резервный workflow: возможное отключение его расписания после
длительного отсутствия активности не отключает основной release-trigger.
Оба workflow также можно запустить вручную через вкладку **Actions**.

Повторная синхронизация тех же данных идемпотентна: при отсутствии изменений
новые коммиты и PR не создаются. Устаревшее событие публикации, которое уже
заменено более новым стабильным релизом, пропускается.

## Одноразовая настройка GitHub App

Нужно одно частное GitHub App, принадлежащее владельцу репозиториев.
Установить его только в `Donkiton/rem_card` и `Donkiton/rem_site`.

Минимальные repository permissions:

| Разрешение | Уровень | Назначение |
| --- | --- | --- |
| Contents | Read and write | Подписанные коммиты только разрешённых файлов |
| Pull requests | Read and write | Создание и слияние PR |
| Actions | Read-only | Подтверждение штатного PR-CI |
| Checks | Read-only | Проверка результатов CI |
| Commit statuses | Read-only | Проверка дополнительных статусов |
| Metadata | Read-only | Служебные сведения репозиториев |

Административные права, право изменять workflows и доступ к другим
репозиториям приложению не нужны. Webhook приложения можно отключить:
release-trigger обслуживает сам GitHub Actions.

В **Settings → Secrets and variables → Actions** репозитория `rem_card`
сохранить:

- **Variable** `PUBLIC_RELEASE_APP_ID` — числовой ID приложения.
- **Secret** `PUBLIC_RELEASE_APP_PRIVATE_KEY` — приватный PEM-ключ приложения.

В `rem_site` ключ хранить не требуется. Нельзя помещать ключ в Git,
передавать его в описаниях PR или печатать в логах. Персональный OAuth-токен
локального `gh` для автоматизации не копируется.

Workflow получает временный installation token, ограниченный этими двумя
репозиториями. Ключ не передаётся дочернему генератору сайта. Стандартный
`GITHUB_TOKEN` не используется для создания PR: это позволяет обычному CI
запускаться без дополнительного ручного одобрения каждого PR бота.

После настройки один раз запустить **Actions → Обновление сайта и README
после релиза → Run workflow**. Можно использовать уже опубликованный выпуск:
пересборка установщика, замена файлов релиза и создание фиктивного выпуска
для проверки не нужны.

## Какие данные обновляются

`scripts/public_release_docs.py` обновляет пять README и десять руководств
`features.*.md` / `setup.*.md` только внутри явных HTML-маркеров. Отдельно
создаётся `docs/public_release.json` — проверенное описание опубликованного
выпуска с версиями, URL, исходным коммитом и списком изменений.

Маркеры `remcard:release:start/end` выделяют автоматически обновляемые блоки,
а `remcard:version:start/end` — текущую версию в подписях руководств.
Отсутствие или дублирование маркера приводит к ошибке до записи файлов.
Авторство, общие инструкции, демонстрационные изображения и исторические
документы не переписываются. Снимки 5.1.0 сохраняют свою настоящую версию.

На сайте `scripts/sync-public-release.mjs` проверяет тот же контракт и
обновляет только `content/public-release.json`. Поле `documentation_commit`
указывает на коммит подтверждённых публичных данных в `rem_card`.
Версия, ссылки, резервные данные и описание сайта читаются из JSON.

Русское описание берётся из `changes` опубликованного `release_info.json`.
При наличии в том же файле `changes_i18n` используются готовые переводы:

```json
{
  "changes_i18n": {
    "en": ["Description of a change"],
    "de": ["Beschreibung einer Änderung"]
  }
}
```

Поддерживаются только `ru`, `en`, `de`, `ja`, `zh-CN`. Не следует переносить
переводы предыдущего выпуска в новый. Если перевода нет, вместо выдуманного
описания выводится локализованная ссылка на полные изменения и требования
релиза. Старая политика схемы БД и минимального клиента не выдаётся за
политику нового выпуска.

`bump_version.py` формирует обычные `version/date/changes`; необязательные
переводы добавляются при подготовке конкретного выпуска после смены версии.
Автоматизация не использует внешние переводчики или платные API.

## Если синхронизация остановилась

Открыть последний запуск в **Actions → Обновление сайта и README после релиза**.
Сводка успешного запуска содержит ссылки на оба PR либо сообщение, что
материалы уже актуальны. Ошибка загрузки файлов не рекламирует неполный
дистрибутив. Ошибка CI оставляет PR открытым для диагностики.

После устранения причины повторить запуск. Если в ветку бота внесены ручные
изменения или изменился `main`, нельзя обходить защиту или принудительно
перезаписывать ветку: сначала нужно проверить открытый PR и актуальную базу.

Обновление сайта — отдельный workflow `rem_site`, поэтому его публикация может
закончиться позже слияния PR. Проверка результата: версия на главной странице,
рабочие ссылки EXE/ZIP и успешный запуск **Публикация сайта на GitHub Pages**.
