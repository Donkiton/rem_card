# План оптимизации обновлений

Цель — оставить один понятный full-only процесс: собрать и полностью проверить релиз локально, испытать автообновление на тестовой базе и только затем атомарно открыть версию всем production-клиентам. Главный оставшийся выигрыш даёт не усложнение формата пакета, а строгая приёмка, наблюдаемость и обслуживание сетевого `UPD`.

## Объём

- Входит: runtime updater, full-manifest, локальная release-сборка, обязательные тесты и git push, тестовая приёмка, безопасная сетевая публикация, остановка релиза и эксплуатационное обслуживание.
- Не входит: возврат patch-пакетов, фоновое обновление при открытой программе, автоматическая публикация прямо в production и скрытая замена файлов уже опубликованной версии.

## Шаги

- [x] Удалить неиспользуемый patch-updater, patch-builder, patch-проверки и старую документацию; оставить `PATCH` только как уровень SemVer.
- [x] Определять папку установки по запущенному EXE, чтобы программа могла находиться на любом диске и по любому локальному пути.
- [x] Хранить рядом с EXE только `remcard_data_path.json`, а релизы искать в `UPD` указанной сетевой папки данных.
- [x] Проверять full-update при каждом compiled-запуске и после штатного закрытия, сохраняя роль и локальную папку программы.
- [x] Копировать сетевой пакет один раз в локальный staging, до backup сверять manifest/SHA-256 и устанавливать подготовленные файлы локальными перемещениями.
- [x] Сделать обязательными architecture, fast regression, F821, проверку полного пакета, compiled smoke всех EXE и точный git push до локальной публикации.
- [x] Разделить локальную сборку и production-публикацию: `build_release.py` создаёт релиз в тестовом `UPD`, а `publish_full_update.py` проверяет и переносит его в сеть через возобновляемый staging с `ready.ok` последним.
- [x] Зафиксировать безопасную границу приёмки: все роли и оба сценария автообновления проверяются на тестовой базе до production; после production `ready.ok` версия видна всем.
- [ ] Провести один эксплуатационный dry-run на реальном сетевом ресурсе без рабочих клиентов: измерить время копирования, проверить возобновление после искусственного обрыва и сохранить контрольные времена для будущих релизов.
- [ ] Утвердить простую политику хранения: минимум три последних релиза не менее семи дней, периодическая очистка только старых каталогов без затрагивания активного `ready.ok` и `.staging-*` текущей публикации.
- [ ] Добавить регулярный просмотр update-логов: ошибки SHA-256, неполный rollback, длительность сетевого копирования и компьютеры, которые долго остаются на старой версии.
- [ ] Рассмотреть подпись release manifest и EXE как отдельное усиление доверия; внедрять только после выбора способа хранения ключа и процедуры восстановления.

## Риски и проверки

- Недоступная сеть не должна менять текущую локальную версию: проверка и staging завершаются до backup.
- Удаление production `ready.ok` останавливает только новые обнаружения и не откатывает уже обновлённые ПК.
- Несовместимая миграция требует backup, закрытия всех production-клиентов и корректного `min_client_version`.
- Любое изменение release-процесса повторно проходит regression, реальную PyInstaller-сборку и compiled smoke.

## Открытые вопросы

- Какой фактический срок хранения старых релизов удобен при доступном объёме сетевого диска?
- Где лучше собирать сводку update-ошибок: в существующих сетевых логах или в отдельном локальном отчёте администратора?
- Нужна ли в будущем цифровая подпись, если доступ к production `UPD` уже ограничен правами сетевой папки?
