# Приёмка 5.1.14 без обновления общей базы

Дата подготовки: 2026-10-28.

## Совместимость и состав

- Версия приложения: 5.1.14; обновление необязательное.
- Схема общей медицинской базы остаётся 28; новых DDL, индексов и миграций нет.
- Минимальный клиент остаётся 5.1.11.
- Готовый пакет собирается с `REMCARD_BUILD_NO_DATABASE_UPGRADES=1`.
- Full-manifest должен содержать `database_upgrades_disabled: true`
  и `min_client_version: "5.1.11"`.
- Включены все изменения 5.1.13, новые исправления чтения и дополнительная
  диагностика записи, backup и открытия общей базы.

`test_compatible_database_and_policy_are_unchanged` проверяет также клиент
5.1.14: полный SQL dump совместимой базы и политика доступа не меняются,
миграционная резервная копия не создаётся.

Сборка выполняется штатным `scripts/build_release.py` из точного слитого
коммита `main` после зелёных GitHub Actions. Готовый пакет проверяется по
inventory/SHA-256, затем повторно проверяется после переноса на рабочий стол.
Публикацию GitHub Release и распространение выполняет владелец проекта.

## Повтор загрузки назначений

Раньше ошибка полного построения могла повторить тот же дорогой снимок
независимо от причины. Теперь вторая попытка допускается только для
`sqlite3.OperationalError` с BUSY/LOCKED. Ошибки схемы, доступа, программирования,
повреждения базы и отмена повторного полного построения не вызывают.

Проверка кеша, версии, change_log, административной дельты, ожидание очереди
и обе попытки полного построения используют один общий бюджет. Проверки
выполняются между этапами и перед публикацией результата, в том числе после
получения блокировки кеша. Истёкший или отменённый запрос не заменяет кеш,
не становится успешным delta и не переходит в полное построение.

Сохраняются cursor floor, epoch, объединение одновременных запросов и прежний
watchdog для запоздалого полного результата. Бюджет кооперативный: он не может
принудительно прервать уже выполняющийся синхронный SQLite/Windows вызов.

Профильные проверки используют настоящий SQLite, включая BUSY при чтении,
успешную вторую попытку после снятия блокировки, отмену/истечение бюджета
на каждом раннем этапе, сохранение старого кеша и поздний совместный результат.

## Сверка исторических таблиц

История по-прежнему сверяется целиком: старые UPDATE и DELETE не заменены
чтением хвоста. Для таблиц с доказанным целочисленным rowid два крайних ключа
дают безопасную верхнюю границу числа строк. Если суммарная граница источника
и локальной копии укладывается в оставшийся бюджет, COUNT и расчёт логического
объёма выполняются одним проходом SQLite вместо двух. На две базы получается
четыре прохода вместо шести, включая неизменённое сравнение содержимого.

Разреженные ключи с большой числовой дистанцией, составные/текстовые ключи,
`WITHOUT ROWID` и неподтверждённые INTEGER PRIMARY KEY используют прежний COUNT
перед оценкой объёма. Ошибочная форма `INTEGER PRIMARY KEY DESC` не считается
алиасом rowid. Ограничения числа строк и логического объёма по-прежнему
проверяются до извлечения содержимого в Python; большие TEXT/BLOB не попадают
в память Python при отказе по бюджету.

Число строк сверки в метриках продолжает означать логические строки источника
и локальной копии. Оно не уменьшается из-за объединения SQL-проходов.
Ускорение зависит от индексов, кеша SQLite и сетевого ввода-вывода;
сокращение двух проходов не означает ускорения всей синхронизации в полтора раза.

На синтетической истории из 19 тысяч строк с ранними UPDATE/DELETE проверена
побайтовая эквивалентность полного результата старого и нового алгоритма.
Python 3.11, APSW/SQLite 3.40.1, read-транзакции, кеш 8 MiB, mmap отключён.
VFS считает чтения источника, включая повторные чтения вытесненных страниц:

| История | xRead до → после | Прочитано байт до → после |
|---|---:|---:|
| Три индекса, значения 440 байт | 4813 → 4759 | 19 714 048 → 19 492 864 |
| Три индекса, значения 600 байт | 6406 → 6352 | 26 238 976 → 26 017 792 |
| Без дополнительных индексов, 440 байт | 7131 → 4757 | 29 208 576 → 19 484 672 |

На индексированной истории снижение чтения меньше 1,2%, без индексов — около
33%. Добавлены небольшие запросы крайних ключей и метаданных индекса: число SQL
в одном замере выросло с 6 до 7, хотя полных проходов стало меньше.
Это измерение локального стенда, не прогноз задержки рабочего места в SMB.

## Проверки выпуска

Штатный `scripts/run_ci_checks.py` использует тот же состав групп, что и CI,
и изолирует профиль Windows, настройки, данные и журналы установленной программы.

| Группа | Локальный результат |
|---|---|
| quality | 3/3, архитектура 10/10 |
| core | 1665 passed, 1 skipped, 60 subtests passed |
| ui с AntV smoke | 1146 passed, 17 subtests passed |
| regression, fast | 538/538, без native crashes и повторов после них |

Пропущен только сценарий symlink: процесс не имеет соответствующей привилегии
Windows. Профиль без миграций проверен для клиентов вплоть до 5.1.14.
Независимый итоговый review обеих performance-правок не оставил открытых
дефектов; дополнительно пройдены 110 профильных тестов.

Отдельно проверяются старые UPDATE/DELETE, огромные TEXT/BLOB и отказ до payload,
разреженные/отрицательные/составные/нестандартные ключи, отмена, освобождение
read-транзакций и работа оптимизации при большой посторонней таблице в базе.

Проверка backoff синхронизации не зависит от короткого замера часов Windows:
она требует передать полный интервал ожидания в stop event, запрещает
ожидание fast event и сетевые проверки, затем проверяет объединение fast-запросов.
После этой правки весь модуль синхронизации прошёл: 59 tests, 10 subtests.

## Дополнительная диагностика

Подробный формат и правила интерпретации:
[database_operation_diagnostics.md](database_operation_diagnostics.md).

Ошибки и медленные операции связываются существующими безопасными ID.
Новые поля не содержат данных пациента, сырого SQL, параметров, полного пути
или текста исключения. Ради диагностики не добавлены SQL, ping, stat
и сетевые проверки lock-файлов. Сбой диагностического обработчика не меняет
исход операции, её бюджет и освобождение ресурсов.

Диагностика различает подтверждённый COMMIT, подтверждённый откат,
восстановленное штатное подтверждение и неизвестный исход. Автоматический
повтор записи при неизвестном исходе не добавлен.

## Наблюдение после установки

Для сравнения нужны журналы обоих рабочих мест за несколько обычных смен
с указанием версии и времени установки. При эпизоде задержки полезно записать
точное время и действие пользователя. Не удалять текущие журналы перед сбором.

- Назначения: сравнивать медиану и p95 `orders_tab_click_to_data`, число полных
  построений и `orders_snapshot_retry_decision`. Второй полный снимок должен
  соответствовать BUSY/LOCKED и оставшемуся общему бюджету.
- Синхронизация: сравнивать длительность delta и full, объём/число сверяемых
  строк, причины перехода в full и сетевые `coordination_probe_*` из 5.1.13.
- Сохранение: связать `accepted_write_id` с очередью, транзакцией и обработчиком;
  определить, ушло ли время в ожидание, блокировку, BEGIN, тело или COMMIT.
- Backup: собрать события одного `attempt_id`; проверить исходную стадию
  сбоя, последний прогресс, результат копии и отдельный результат cleanup.
- Первый вход: сопоставить `central_connection_summary` и DB_WAIT,
  различить connect, внутренний mutex, PRAGMA и чтение metadata.

Большое время при малом CPU означает ожидание, но само по себе не доказывает
влияние сети или антивируса. Если задержка остаётся внутри одного системного
вызова, для окончательного различения причин понадобится трассировка Windows.
