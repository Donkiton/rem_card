Дата: 28.09.2026. Исходная версия клиентов: 5.1.2.
База этапа: `1297f7f922ff8ed89c8e0bcca5d8762c5723095e` — завершённая
очистка legacy, сохранённая в `origin/rework`.
Работа выполняется в `rework`. Контрольный исходный снимок до рефакторинга:
`8394f34c82d5ffab51b9c3fa75c71cd909d7dfe6` (исходная удалённая `main`).

## Объём и способ разделения

Этот шаг разбирает монолиты операционного блока. Последующие части общего
этапа декомпозиции — рабочее место врача и назначения — здесь не изменяются.
AntV уже включён в исходное состояние; клинические возможности не добавляются.

Методы разделены по функциональным примесям (mixin). Они продолжают работать
на том же экземпляре `OperBlockMainWidget` или `OperBlockService`. Виджет
остаётся одним `QWidget`, а сервис использует прежний `db_manager`, контекст
транзакций и экземпляр сервиса передачи пациента. Прокси-объекты, динамическая
подмена глобальных имён и дополнительное состояние не вводятся.

Это разделение файлов по ответственности, а не полное устранение связности:
примеси используют общие атрибуты и методы координатора. Их нельзя создавать
как самостоятельные виджеты/сервисы. Изменение контракта общей переменной
по-прежнему требует проверки всех её потребителей.

## Карта реализации

Публичные входные классы `OperBlockMainWidget` и `OperBlockService` остаются
доступны по прежним путям:

- `ui/operblock_view/operblock_main_widget.py`: сборка виджета, жизненный цикл,
  навигация, настройки и запуск PDF-отчётов.
- `services/operblock_service.py`: сборка сервиса и публичные контракты.

Главный файл UI сократился с 20 918 до 862 строк, входной файл сервиса —
с 8 085 до 73 строк. Это перенос реализации, а не удаление соответствующего
объёма логики. Все 449 методов виджета и 172 метода сервиса сохранены.

В `ui/operblock_view/features/` перенесены методы виджета:

| Модули | Ответственность |
|---|---|
| `refresh`, `local_updates` | Загрузка снимков, обновление экрана и локальные изменения |
| `board_cards`, `board_details` | Карточки доски и их содержимое |
| `protocol_layout`, `protocol_state` | Компоновка протокола, состояние и диапазон графика |
| `case_actions`, `stages` | Действия со случаем и этапами |
| `orders_layout`, `orders_rendering`, `quick_orders` | Компоновка назначений, отображение и быстрый поиск |
| `medication_groups`, `order_history`, `order_actions` | Группировка препаратов, история и редактирование |
| `infusion_cards`, `infusion_actions` | Карточки инфузий и действия с ними |
| `archive` | Интерфейс архива |
| `write_coordinator` | Очередь записи, диагностика, завершение действий и тайм-ауты |

Диалоги и вспомогательные элементы находятся рядом с координатором в
`operblock_*_dialogs.py`, `operblock_dialog_base.py`, `operblock_helpers.py`,
`operblock_visual_primitives.py`, `operblock_vitals_adapter.py`.
Их потребители, в том числе административное окно, импортируют канонические
модули. Прежние импорты внутренних диалогов и вспомогательных функций через
монолитные файлы не являются сохраняемым контрактом; при подключении внешнего
скрипта его импорты также нужно перевести на новые модули.
Два крупных диалога (наборы препаратов и занятие стола) пока сохранены
целиком, чтобы не совмещать перенос с изменением их внутреннего поведения.

В `services/operblock/` находятся части сервиса:

| Модули | Ответственность |
|---|---|
| `common`, `helpers`, `core` | Контракты и нормализация, вспомогательные методы, инициализация и чтение |
| `archive_sources`, `archive` | Источники архива и операции с архивными случаями |
| `board`, `snapshots`, `reporting` | Доска, снимки протокола и данные отчётов |
| `case_context`, `case_lifecycle` | Контекст случая, создание и изменение |
| `stages`, `protocol`, `handoff` | Этапы, завершение протокола и передача пациента |
| `vitals`, `orders`, `infusions`, `medications` | Показатели, назначения, инфузии и история препаратов |

В тестах изменены импорты перенесённых символов и места подмены зависимостей.
Регрессионные проверки исходного кода читают `features/write_coordinator.py`,
где теперь реализована запись; проверяемые требования сохранены.
Карта `docs/codemap/` указывает на новые реализации.

Независимая проверка изменений не выявила блокирующих дефектов: проверены
состав и порядок наследования, единственный Qt-объект и сигнал возврата,
сохранение транзакционных контекстов и импорт всех 47 новых модулей.

Пропущен опциональный smoke-тест реального AntV/QtWebEngine; он требует
отдельного opt-in запуска. Выпуск EXE и ручная проверка на рабочей базе не
выполнялись. Время тестовых наборов не является замером скорости приложения:
сравнимый пользовательский performance-бенчмарк здесь не проводился.

Сравнение AST подтвердило сохранение всех 449 методов виджета; при сравнении
исключены только добавленные локальные импорты координатора в семи методах,
которые сохраняют прежнее обращение к `OperBlockMainWidget` без цикла импортов.
Для 208 вынесенных символов префикса также подтверждено совпадение AST.
Все 172 метода сервиса совпали после исключения локального импорта
`OperBlockService` в четырёх архивных статических методах. Ссылки этих методов
на исходный класс сохранены. Также без изменений перенесены 53 функции
и класса верхнего уровня сервиса (контракты и вспомогательная логика).

Проверки запускаются через `scripts/run_ci_checks.py` на временных данных.
Кроме штатной изоляции BAZA и QSettings, используется отдельный профиль:
`LOCALAPPDATA`, `APPDATA`, `ProgramData`, `USERPROFILE`, `HOME`, `TEMP`, `TMP`,
пути конфигурации базы и журналов направлены в `tmp/rework-stage3-checks/`.
Рабочая база и установленная программа не используются. Локальные подробные
отчёты находятся в этом каталоге и не включаются в Git.

## Восстановление и дальнейшая работа

Для просмотра исходного файла без изменения рабочего дерева:

```powershell
git show 1297f7f922ff8ed89c8e0bcca5d8762c5723095e:ui/operblock_view/operblock_main_widget.py
git show 1297f7f922ff8ed89c8e0bcca5d8762c5723095e:services/operblock_service.py
```

После сохранения этапа отдельным коммитом его можно отменить через
`git revert <SHA-коммита-этапа-3>` в `rework`, сохранив историю. Не следует
восстанавливать один старый монолит поверх новых модулей и потребителей:
перенос и обновление импортов составляют одну согласованную единицу изменения.
Коммит и отправка этого этапа выполняются по отдельному поручению владельца.
Слияние в `main`, выпуск сборки и изменение рабочей базы в этот этап не входят.
