# Проверки выпуска 5.1.18

## Цель и профиль

Выпуск включает 5.1.17 и исправляет оставшиеся программные пути задержек
после изменения статуса пациента и отмены загрузки назначений. Обновление
с 5.1.16 выполняется сразу до 5.1.18. Схема общей БД остаётся 29,
минимальный клиент — 5.1.15; сборка выполняется без миграций.
Сетевой профиль SQLite DELETE/EXTRA/mmap=0 сохраняется.

Приёмка использует синтетические БД и отдельные профили. Сетевые испытания
проводятся только в разрешённом QA-подкаталоге test; рабочая БД и UPD
не участвуют. Справочники сохраняются из принятого выпуска 5.1.17.

## Исправляемые механизмы

- Положительное авторитетное покрытие смены возвращается без write BEGIN,
  COMMIT и повторной инвалидации. Создание, bridge и repair сохраняют
  сериализованную повторную проверку; локальная реплика не доказывает no-op.
  Preflight использует уже открытое центральное соединение под прежними
  mutex/connection guards; чтение и необходимая запись расходуют один
  абсолютный deadline. Временный busy_timeout восстанавливается в finally.
- Отмена или watchdog пользовательского запроса запускают ограниченное
  восстановление актуального видимого контекста. Новый запрос ждёт
  фактического завершения старого worker; защищены черновики, закрытие,
  смена пациента/сервиса и поздние callback.
- Progress handler на собственных source/local соединениях worker позволяет
  существующей проверке writer/rotation/cancel прервать длинный SQL-скан.
  Согласованная read-транзакция, все исторические строки, лимиты и fences
  публикации сохранены. При отмене обработчики не мешают rollback,
  исходная классификация ошибки восстанавливается, кандидат не публикуется.

## Контролируемые измерения

В фиксированном тесте SQLite другой writer удерживал RESERVED, а смена
ACTIVE/DEAD уже была покрыта. Принятый DAO 5.1.17, извлечённый из Git,
пять раз исчерпал тестовый бюджет 150 мс; финальный новый DAO
пять раз завершил no-op без write за 0,5–1,7 мс. Это проверка отсутствия
лишней резервации, а не обещание такого времени на рабочем SMB.

При искусственном ожидании 1 мс на строку внутри native SUM реальный
конкурентный writer завершил сохранение за 1774,936 мс на прежнем пути
и за 174,880 мс с VM cancellation. Сканирование остановилось после 99
из 1000 строк; целостность БД, прежняя реплика и освобождение lock проверены.
Искусственная задержка не является производственным измерением.

На здоровой локальной истории из 12000 строк, 30 чередующихся пар:
медиана сбора без VM callback — 53,961 мс, с ним — 54,710 мс;
p95 — 55,176 и 60,256 мс. Стоимость проверки ненулевая; этот замер
не доказывает полного отсутствия накладных расходов.

В реальной SMB-папке обе версии выполнили по 48 сохранений. Проверены
integrity central/doctor/nurse, логическая эквивалентность и readonly реплик.
Для повторного контрольного 5.1.17 p95 COMMIT врача/медсестры составил
1140,431/1026,208 мс, для 5.1.18 — 685,291/708,396 мс.
P95 обнаружения изменений: 10120,205/10120,247 и 6673,861/6669,520 мс.
В более раннем прогоне 5.1.17 обнаружение занимало около 6469 мс:
сетевые хвосты изменчивы, проценты ускорения на рабочих местах из этих
коротких прогонов не выводятся. Это два процесса на одном ПК,
а не два физических рабочих места.

## Границы доказательства и поставка

SQLite вызывает progress handler между VM-инструкциями. Он не может
прервать отдельный зависший файловый I/O; существующая защита killable
worker и его таймаут сохраняются. Успех тестов не гарантирует отсутствия
всех сетевых задержек в рабочей среде.

Профильные тесты проверяют гонки, исторический ремонт, no-op сигналы,
отмены, ограничения повторов и сохранность контекста. Итоговый неизменяемый
коммит проходит полный CI, quality/architecture и safety-регрессии.
Сборка, full ZIP, compiled updater, установщик RU/EN и Desktop-копии
принимаются по docs/windows_installer.md с проверкой inventory/SHA-256.
Точные отчёты измерений и поставки сохранены в локальном каталоге workflow
выпуска; исходные логи пациентов в дистрибутив и GitHub не включаются.
