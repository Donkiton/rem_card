# Бенчмарк стартового снимка SQLite

Скрипт `scripts/startup_snapshot_benchmark.py` сравнивает два сценария на одной
детерминированной синтетической базе размером около 15 МиБ:

1. прежний путь: полный `PRAGMA quick_check` центральной базы для допуска, затем
   независимый SQLite backup и локальный `quick_check` для первой реплики;
2. новый путь: один согласованный SQLite backup через
   `_sync_snapshot_with_network_lease`, локальный `quick_check` снимка и повторное
   использование уже проверенного локального файла. Затем реальный
   `copy_for_replica` и `LocalReplicaSync.install_startup_snapshot` публикуют
   копию, а первый `sync_once` дешёво сверяет её состояние с источником.

Это алгоритмический бенчмарк, а не замер всего GUI и не тест настоящего SMB.
Он вызывает реальные функции стартового guard, snapshot worker и
`LocalReplicaSync`, временно подставляя только адаптеры соединений и локальный
in-process worker client. APSW VFS считает реальные вызовы SQLite `xRead`, объём
запрошенных байтов и добавляет заданную задержку каждому чтению источника.
Подмены ограничены контекстом одного вызова и не изменяют приложение.

## Подготовка

APSW нужен только бенчмарку и не добавляется в `requirements.txt`. Версия ниже
использует тот же SQLite 3.40.1, что и Python 3.10 в проекте:

```powershell
python -m pip install --target tmp\startup-benchmark-deps apsw==3.40.1.0
```

## Запуск

```powershell
python scripts\startup_snapshot_benchmark.py
```

Параметры по умолчанию: три запуска, база 15 МиБ и задержка 1,75 мс на каждый
`xRead`. Порядок old/new чередуется, каждая фаза открывает новое соединение,
а задержка VFS делает результат независимым от файлового кеша Windows.
Для задержек меньше 10 мс скрипт использует ограниченное активное ожидание:
обычный `sleep` на Windows имеет слишком грубую дискретность и завышает время в
несколько раз. JSON сохраняет как заданную, так и реально накопленную задержку.

Результат записывается в игнорируемый Git каталог
`tmp/bench-results/startup_snapshot_benchmark.json`. JSON содержит все запуски,
медианы, длительность чистой backup-фазы, число `xRead`, байты, накопленную
искусственную задержку, файловые и логические SHA-256, `quick_check` каждой
копии и проверку логической эквивалентности.

## Контрольный результат

17 октября 2026 года три чередующихся запуска на Python 3.10.11, SQLite 3.40.1
и APSW 3.40.1.0 дали следующие медианы:

| Метрика | Прежний путь | Новый путь |
|---|---:|---:|
| Первый допуск | 6,953 с | 7,086 с |
| Допуск и подтверждённо готовая первая локальная реплика | 14,022 с | 7,141 с |
| Чтения центрального источника | 7 882 `xRead` | 3 960 `xRead` |
| Запрошено у центрального источника | 32 178 844 байт | 16 090 020 байт |

Новый первый допуск оказался на 0,133 с (1,91%) медленнее прежнего: снимок до
допуска выполняет дополнительные проверки согласованности. Основной выигрыш —
в устранении второго полного чтения источника. К моменту готовности первой
локальной реплики новый путь быстрее на 6,880 с (49,07%). Результаты отдельных
запусков устойчивы: старый полный путь занял 13,988–14,022 с, новый путь до
готовой реплики — 7,109–7,159 с.

После публикации нового снимка первый `sync_once` во всех трёх запусках вернул
согласованное состояние без второго backup: только 8 дополнительных `xRead` и
16 532 запрошенных байта. Обе ветки завершились
`LocalReplicaSync.is_ready() == True` с одинаковыми `db_cycle`, `change_cursor`
и `schema_revision`.

Медиана чистой backup-фазы составила 6,966 с, поэтому в этом моделируемом
сценарии 6-секундный бюджет не проходит, а 30-секундный проходит. Это вывод
только для указанной искусственной задержки 1,75 мс на `xRead`.

Полезные варианты:

```powershell
# Быстрая проверка механики без искусственной задержки
python scripts\startup_snapshot_benchmark.py --runs 1 --database-mib 2 --read-delay-ms 0

# Сохранить промежуточные копии баз для ручной проверки
python scripts\startup_snapshot_benchmark.py --keep-copies
```

Свидетельство о бюджетах 6 и 30 секунд появляется только тогда, когда измеренная
медиана самой backup-фазы действительно превышает 6 секунд. Оно всегда помечено
как результат с имитацией SMB-задержки. Скрипт не обращается к `Z:/medical` и не
использует производственные данные.

## Границы вывода

Задержка на `xRead` воспроизводима, но не моделирует джиттер SMB, переподключения,
oplock, антивирус и параллельную запись. Локальные `quick_check`, копирование,
хеширование, lock-файлы и `fsync` выполняются реально. Для решения о рабочем
тайм-ауте этот результат нужно рассматривать вместе с телеметрией настоящих
рабочих мест, а не как замену сетевому приёмочному тесту.

Worker subprocess не запускается: небольшой локальный client вызывает реальную
`_sync_snapshot_with_network_lease` в текущем процессе. Так VFS может измерять
каждое чтение источника, но в результат не входит стоимость запуска процесса и
IPC.

Контрольный артефакт получен в среде Python 3.10. Проект также
собирается и тестируется интерпретатором Python 3.11 с SQLite 3.38.4; точной
версии APSW 3.38.4 нет в доступных пакетах (ближайшая — 3.38.5.post1), поэтому
этот бенчмарк не заявляет побайтовую сопоставимость разных версий SQLite.
