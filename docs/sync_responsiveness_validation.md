# Проверка локальных исправлений синхронизации, 20 октября 2026

Исправления подготовлены поверх `1243dc8` (5.1.9), без выпуска новой версии и
отправки в GitHub. Производственная БД и исходные логи не изменялись. Основные
прогоны используют изолированные профили. Параллельные изменения
oral_nutrition_widget / test_oral_nutrition_style / oral_nutrition_styles
не относятся к этому исправлению и сохранены.

## Что проверяется

- Большая неотслеживаемая история не запрещает небольшую дельту. Проверяются
  исторические изменения, удаления, составные ключи, границы сканирования и
  сохранение предыдущей реплики при отказе.
- Одновременная запись двух ролей использует отдельные SQLite-соединения,
  реальные OrderDomainService / OrderService и штатный SQLiteWriteController с
  общим FileWriteLock. Одинаковая ожидаемая версия одной записи даёт одного
  победителя и один конфликт. Изменения разных записей сохраняются оба.
- Правка/финализация и удаление/финализация назначения врачом пересекаются с
  commit отметки медсестры. Сохранённая отметка выполнения остаётся в истории.
- Две read-only реплики догоняют центральную БД. Проверяется содержимое,
  query_only и отсутствие изменений файла источника во время синхронизации.
- Запоздавшие cached/delta ответы не заменяют более новый подтверждённый кэш.
  Полная загрузка ниже уже прочитанного required cursor отвергается. Если
  события дельты новее первого version probe, их cursor тоже сохраняется как
  нижняя граница при отказе дельты и переходе к полной загрузке. При вытеснении
  карточки по общему LRU или лимиту вкладок активное чтение сохраняет свой
  fence до завершения; служебные ключи затем освобождаются. При объединении
  загрузок cache/stale и результат завершившегося refresh проверяются по
  минимальной версии, уже известной именно этому запросу.
  Полный refresh проверяет поколение и активный request непосредственно при
  сохранении кэша под общим порядком блокировок; отмена, poison, expire или
  supersede между внешним guard и store не позволяют опубликовать старый ответ.
- Уведомление медсестры не вызывает синхронный запрос статуса из GUI-потока.
  Qt heartbeat остаётся быстрее 250 мс при подставленном запросе на 500 мс.
  Ответы другого пациента, даты и предыдущего открытия карточки отвергаются.
- Готовая ночная копия загружается при одновременном успешном commit писателя.
  Проверяются отказ публикации, сохранение старой копии и остановка worker.
- Начальный статус проверяется с настоящим блокирующим SQLite reader: первая
  попытка COMMIT откатывается, reader освобождается, вторая попытка оставляет
  ровно одну запись. Неопределённый исход записи и тайм-аут до COMMIT не
  повторяются. Локальные BUSY/LOCKED кандидата не маскируются под занятость
  центрального источника.
  Повторы внешней LocalWriteQueue отключены для начального статуса; проверка
  через настоящий DataService и LocalWriteQueue подтверждает единственного
  владельца повторов и один terminal callback при ошибке или commit.

## Замеры реплики до и после

Один и тот же benchmark harness применён к исходному runtime и исправленному.
В архивную копию исходников перенесён только обновлённый harness с параметром
history-rows; исходный код приложения там остался от `1243dc8`.

Синтетическая unified-БД 16,961 MiB, 6000 добавленных строк medical_audit_log,
три повтора, задержка 1,75 мс на SQLite source xRead. Python 3.11.0, stdlib
SQLite 3.38.4, source VFS APSW 3.40.1.0 / SQLite 3.40.1.

| После небольшого изменения | Исходный runtime | Исправленный runtime |
|---|---:|---:|
| Медиана обновления worker | 8,317 с | 1,130 с |
| Прочитано байт source VFS | 18 838 532 | 1 065 396 |
| Вызовов source xRead | 4637 | 282 |
| Режим | full: untracked_table_too_large | delta |

Это ускорение в 7,36 раза относительно исходного runtime, снижение чтений на
94,34%. Защитные fallback event_limit и change_log_gap сохранены. Все
кандидаты проверены по logical digest и quick_check; SHA-256 источника не
изменился. При неизменном источнике reuse остался около 0,12 с.

Это модель задержки SQLite-чтений, а не замер SMB в больнице. Она не моделирует
антивирус, реальную полосу сети и отказы файлового сервера.

## Совместная работа двух ролей

`scripts/concurrent_clinical_sync_benchmark.py --workstation-layout separate`:
20 итераций, по две параллельные записи, 6000 строк неотслеживаемой истории,
два штатных LocalReplicaSync с worker-процессами. Обычный интервал — 2 секунды,
trigger_fast_sync после commit не вызывается. Записи используют
SQLiteWriteController и FileWriteLock по тому же пути db.lock, который
проверяет worker реплики. Разные snapshot gates имитируют разные
имена рабочих ПК; процессы и файлы физически находятся на одном компьютере.

| Измерение, p95 | Врач | Медсестра |
|---|---:|---:|
| Commit, включая ожидание блокировки | 19,198 мс | 18,990 мс |
| Последний commit пары → данные в реплике | 2279,490 мс | 2122,349 мс |
| SQL-чтение локальной реплики | 0,070 мс | 0,072 мс |

Максимальное ожидание реплики — 2,364 с. Итоговые состояния обеих реплик совпали
с центральным, integrity_check всех трёх баз = ok, обе реплики read-only.
Разница между ролями зависит от фазы опроса. Дополнительный сценарий с двумя
ролями на одном ПК и общим snapshot gate дал p95 2,419 / 2,574 с и максимум
4,479 с: конкуренция снимков иногда требует следующего цикла опроса. Он также
завершился без потери данных. В приложении scope штатного gate не изменён;
отдельные gates задаёт только синтетический режим separate этого скрипта.

Измерение заканчивается появлением данных в реплике. Настоящий
DataUpdateMonitor и применение QWidget не входят в этот benchmark;
state_projection_application в JSON — только создание неизменяемой проекции.

## Отзывчивость кликов

Существующий orders_click_latency_benchmark запущен на 40 действиях в
изолированном профиле с синтетической БД, настоящим DoctorMainWidget и
QApplication offscreen. Все 40 UI-изменений и 40 commit подтверждены.
Измеряются клик по ячейке назначения и отдельное сохранение; загрузка вкладки
назначений целиком в эти цифры не входит.

| Измерение | p95 | Максимум |
|---|---:|---:|
| Клик → model.dataChanged | 0,752 мс | 0,885 мс |
| Явное сохранение → новое состояние БД | 29,076 мс | 31,953 мс |

Отдельное штатное ожидание защиты повторного клика: в среднем 413,881 мс,
максимум 429,644 мс. model.dataChanged означает уведомление модели, не измеряет
физическое появление пикселей на экране. В этом сценарии фоновые реплики
отключены самим benchmark; одновременная синхронизация проверена выше.

Первый цельный прогон изменений: 2485 passed и один timeout окна обслуживания
служебных файлов (ожидание worker 3 секунды). Изолированный повтор окна вместе
с replica/concurrency тестами: 67 passed. Следующий цельный прогон до последних
дополнительных регрессионных сценариев: 2486 passed, 2 skipped, 77 subtests.
Два пропуска: ручной opt-in QtWebEngine и недоступность Windows symlink privilege.
QtWebEngine затем отдельно включён и прошёл; права ОС для symlink не менялись.

Первое независимое ревью обнаружило три дополнительных пробела: потерю fence
при LRU-вытеснении, слишком широкое распознавание commit timeout и смешение
локальных ошибок кандидата с занятостью source. Родитель исправил их и добавил
17 регрессионных случаев. До исправлений 16 из них падали; после исправлений
весь целевой набор прошёл. При сверке нагрузочного стенда исправлен также путь
его FileWriteLock; после этого отдельно повторены 62 теста, включая пять
сценариев конкурентной записи, и замеры совместной работы.

Второе независимое ревью подтвердило ещё один обход минимальной версии:
coalesced-запрос мог получить старый cache/stale во время другого full refresh.
Родитель передал required_version и в эту ветку; снимки ниже неё не возвращаются.
Восемь новых случаев проверяют cache/stale, незавершённый refresh и завершение
ниже, на уровне или выше минимальной версии. После этой правки полный набор,
regression safety и статические проверки повторно прошли.

Третье ревью обнаружило окно между последним guard полного refresh и store,
включая supersede без invalidation, и независимые raw-BUSY повторы внешней очереди.
Родитель закрыл публикацию атомарной проверкой активного request вместе с epoch
и отключил внешний retry для начального статуса. Двенадцать случаев проверяют
invalidation, poison, expire, supersede и cancel в обычном и force-refresh режиме;
ещё пять проверяют реальный DataService/LocalWriteQueue. Полный набор и gates
после этих исправлений повторно прошли. Замер 40 кликов/commit в Qt-виджете
и opt-in QtWebEngine smoke также повторно прошли на окончательном runtime.

Предыдущие concurrent-separate-workstations.json и concurrent-production-poll.json
относятся к раннему стенду с другим путём writer lock и не являются итоговыми
замерами штатного приоритета писателя.

Исходный полный pytest: 2445 passed, 2 skipped, 77 subtests; два первоначальных
отказа были связаны с запуском из git archive (нет индекса git и пути модуля в
подпроцессе). После восстановления только окружения оба теста прошли.

## Что ещё должно подтвердиться на рабочих ПК

Нельзя обещать отсутствие всех задержек на рабочем SMB по локальным замерам.
Для следующих логов добавлены фазы orders_load_time_ms: cache_lookup,
version_probe, delta_attempt, load_slot_wait, full_build, finalize,
apply_handoff. У резервной копии различаются ожидание чтения, SQLite copy,
проверка локальной копии, upload, проверка upload и публикация.

Предыдущая ошибка READONLY не воспроизведена на синтетических базах. Теперь
сохраняются исходный этап и расширенный SQLite-код; generic READONLY не
маскируется под обычную блокировку. Логи врача на 5.1.6 не доказывают наличие
той же GC-проблемы после его обновления; для этого нужны новые рабочие логи.

Ночное чтение живой БД по-прежнему может удерживать db.lock до бюджета 8 секунд.
Сетевая загрузка готовой копии этот lock больше не удерживает. Нельзя считать
всё время ночной копии временем блокировки интерфейса.
