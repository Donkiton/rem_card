# Проверки выпуска 5.1.19

## Профиль и ограничения

Выпуск включает исправления 5.1.17 и 5.1.18 и четыре оставшихся пути,
найденных при повторном аудите. Схема медицинской БД — 29, минимальный
клиент — 5.1.15, сборка без миграций. Профиль сетевого SQLite сохраняется.
Рабочие медицинские БД и сетевая production-папка обновлений не участвуют
в тестировании и сборке. Исходные журналы пациентов не входят в GitHub
или дистрибутив.

## Сохранение назначений

Собственная отметка возвращает подтверждённые значения до и после записи
из той же транзакции. Подтверждение запрашивается только врачом; путь
отметок медсестры не получает дополнительного SELECT. Интерфейс обновляет исходные версии только для
подтверждённой ячейки при совпадении прежней версии; локальные изменения
формы назначения сохраняются. Снимок, начатый до подтверждения отметки,
не должен понизить подтверждённую версию. Отдельная нижняя граница принятия
снимков не продвигает cursor опроса и не пропускает чужие события.
Сохранение до подтверждения
собственной отметки защищено существующим состоянием операции.

Фактическое отсутствие изменения формы не должно записывать строку или
вызывать конфликт только из-за версии. Запрет удаления отмеченного
выполнения и сравнение версий перед реальным изменением сохраняются.
Проверки включают собственные mark/clear, локальный черновик, чужие
отметки, устаревший результат, совпавший no-op и атомарный rollback.

## Обновление назначений

Изменения vitals, fluids, oral_intake_events и lab_orders сами по себе
не меняют orders/admin_rows снимка. Их обработка может продвинуть cursor
без полной пересборки только при доказанной полноте окна изменений.
События orders и неизвестные сущности, потерянная история, смена эпохи
или контекста сохраняют полный reload. Administrations обрабатываются
прежним delta-путём. Срок допустимого возраста снимка не увеличивается.

## Аварийная локальная копия

Повторное использование настроек требует проверенного предыдущего
поколения и доказательства неизменности источника. В Windows используются
реальная идентичность файла, состояние SQLite DELETE и заголовок
под короткой read-транзакцией; неизвестное или изменившееся состояние
возвращает обычный backup. Локальная копия проверяется по содержимому.
Атомарная публикация медицинской БД и настроек, свежесть медицинской БД,
защита writer/rotation и отмена сохраняются. На других ОС используется
полное копирование, чтобы не ослаблять платформенную семантику lock.
Произвольная запись в файл БД в обход SQLite не является поддерживаемым
способом изменения настроек.

На синтетическом источнике 60 198 912 байт в разрешённой SMB QA-папке
подтверждены file identity, реальная SHARED-блокировка и идентичность
локальной копии. Три чередующихся замера полного backup/повторного
использования дали медианы 217,50/225,38 мс на прогретом кеше: новый путь
здесь дороже примерно на 8 мс. Первый полный backup занял 5,81 с, но
сравнивать его с прогретой локальной копией как гарантированный процент
ускорения нельзя. При reuse полный payload источника больше не читается;
SHA и проверка полных байтов выполняются локально. На локальном источнике
медианы — 184,15/136,37 мс. Это короткие контролируемые замеры, не рабочая
статистика врача и медсестры.

## Настройки интерфейса

Полный снимок app_settings подтверждает также отсутствие ключей; каждый
вызывающий метод сохраняет свой default. При включённом штатном опросе
настроек monitor читает change-log и app_settings в одной read-транзакции
перед уведомлением GUI. Счётчик локальных изменений запрещает установку
снимка поверх более новой записи. GUI не очищает уже подготовленный снимок.
Кеши остальных каталогов, включая диеты, очищаются также при доставке
уведомления в GUI: старое чтение, закончившееся после фоновой подготовки,
не должно остаться в памяти.
Сохранение одного ключа после COMMIT не очищает остальные значения.
Поздний результат отложенного применения справочников также проверяет
исходный счётчик кеша. При конфликте существующий управляемый worker
повторно читает значения без повторной записи справочников; даже при
отключённом опросе кеш не остаётся с устаревшим результатом. Одиночная
гонка при обычном monitor-чтении обрабатывается одним повтором в фоне.
Явная инвалидация по-прежнему требует актуального чтения. Частота опроса
не увеличивается; дополнительные периодические сетевые запросы не вводятся.

Проверки используют два клиента, медленное фоновое чтение, отсутствующий
print_config, разные default, изоляцию возвращённых значений, сетевую
ошибку и гонку локального сохранения с публикацией снимка.

## Приёмка поставки

Перед слиянием выполняются профильные тесты, полный CI, quality/architecture,
safety-регрессии и независимый обзор diff. Принятый коммит main собирается
с точными зависимостями. Manifest, inventory, SHA-256, встроенный профиль
обоих EXE, обновление предыдущей изолированной установки и установщик RU/EN
проверяются по docs/windows_installer.md.

Точные отчёты сохраняются локально в workflow выпуска. Контролируемые
замеры и отсутствие лишнего чтения/копирования доказывают устранение
конкретных операций; они не являются обещанием фиксированного ускорения
на рабочей сети или отсутствия всех возможных сетевых задержек.
