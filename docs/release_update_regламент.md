# Регламент обновлений

РЕМКАРТА публикуется только полными сборками. Patch-updater и patch-пакеты удалены как неиспользуемая ветка. Уровень `PATCH` в `MAJOR.MINOR.PATCH` по-прежнему применяется для номера версии, но не меняет формат пакета.

Главный риск обновления — открыть production-релиз до завершения приёмки или допустить работу старого клиента после несовместимой миграции БД. Клиенты — врач, медсестра, экстренная и плановая операционные.

## Инварианты

- Программа может быть установлена на любом локальном диске и в любой папке.
- Updater получает фактическую папку от запущенного EXE и не угадывает путь.
- `remcard_data_path.json` рядом с EXE указывает на общую `Baza_rao3_jurnal`.
- Релизы находятся в `<Baza_rao3_jurnal>\UPD\releases\<version>`.
- Git push точного release-коммита обязателен до любой готовой публикации.
- Production `ready.ok` создаётся последним и сразу открывает релиз всем клиентам этой базы.
- Каталог опубликованной версии неизменяем; исправление выпускается только новой версией выше.

## Этап 1. Подготовить локальный релиз

1. Завершить изменения, сделать рабочий commit и оставить git-worktree чистым.
2. Запустить `.\.venv\Scripts\python.exe scripts\build_release.py`.
3. Дождаться обязательных architecture, fast regression и F821-проверок.
4. Дождаться PyInstaller-сборки, проверки manifest/inventory/settings snapshot и compiled smoke всех шести EXE.
5. Убедиться, что release-коммит отправлен в `origin` и локальный пакет появился в `C:\Test\Baza_rao3_jurnal\UPD\releases\<версия>`.

Если любой gate завершился ошибкой, релиз остановлен. Переходить к production-публикации запрещено.

## Этап 2. Выполнить приёмку на тестовой базе

Тестовая установленная копия должна через свой `remcard_data_path.json` указывать на отдельную локальную или изолированную тестовую `Baza_rao3_jurnal`.

До production нужно:

1. Проверить автоматическое обновление старой тестовой копии при запуске.
2. Отдельно проверить автоматическое обновление после штатного закрытия.
3. Проверить запуск врача, медсестры и обеих операционных.
4. Проверить сохранность JSON пути и работу именно с тестовой базой.
5. Проверить основные изменённые сценарии и отказ на повреждённом пакете.
6. Для изменения схемы выполнить test backup, миграцию, `quick_check`, `integrity_check` и проверку совместимости ролей.

Production share не является канареечной средой. Нельзя сначала создать там `ready.ok`, обновить один компьютер и затем «оставить marker для остальных»: с момента создания marker релиз уже доступен всем клиентам.

## Этап 3. Опубликовать проверенный релиз

Использовать один из вариантов:

```powershell
.\.venv\Scripts\python.exe scripts\publish_full_update.py `
  --source "C:\Test\Baza_rao3_jurnal\UPD\releases\<проверенная версия>" `
  --config "<папка production-программы>\remcard_data_path.json"
```

```powershell
.\.venv\Scripts\python.exe scripts\publish_full_update.py `
  --source "C:\Test\Baza_rao3_jurnal\UPD\releases\<проверенная версия>" `
  --baza-dir "\\SERVER\Share\Baza_rao3_jurnal"
```

Явный `--source` должен указывать именно на папку версии, которая прошла этап 2. Publisher проверяет актуальные ветки `origin`, manifest, snapshot настроек и SHA-256, копирует пакет в возобновляемый `.staging-*`, затем атомарно завершает каталог и создаёт `ready.ok` последним. Ручное копирование готовой папки вместе с marker запрещено.

После успешной команды нужно проверить наличие полного набора файлов и `ready.ok`, а затем наблюдать update-логи. Функциональная приёмка к этому моменту уже должна быть завершена на тестовой базе.

## Порядок обновления рабочих мест

Для релиза без несовместимой миграции пользователи получают версию автоматически:

- работающая программа — после штатного закрытия;
- закрытая программа — при следующем запуске с автоматическим перезапуском того же EXE.

Для релиза с несовместимой миграцией:

1. Завершить полную тестовую приёмку миграции.
2. Сделать valid backup обеих production-БД.
3. Закрыть все production-клиенты.
4. Проверить `client_policy.json.min_client_version`, чтобы старые клиенты не открыли новую схему.
5. Опубликовать готовый full-релиз.
6. Запустить первый новый клиент и выполнить миграцию.
7. Проверить `quick_check` и `integrity_check`.
8. Запустить остальные новые клиенты и проверить синхронизацию врач → медсестра, медсестра → врач и обе операционные, если они затронуты.

Если update-пакет временно недоступен после несовместимой миграции, старая программа должна остаться заблокированной, а не продолжить запись в новую схему.

## Остановка и исправление релиза

Для остановки новых установок удалить:

```text
<production Baza_rao3_jurnal>\UPD\releases\<версия>\ready.ok
```

Удаление marker:

- не откатывает уже обновлённые компьютеры;
- не гарантирует остановку updater, который уже начал работу;
- не разрешает изменять остальные файлы опубликованной версии.

Для уже обновлённых ПК выпускается новая исправленная full-версия выше. Повторное включение отключённого каталога допускается только после выяснения причины и явной команды publisher с `--reactivate-existing`.

Рекомендуется хранить не менее трёх последних full-релизов минимум семь дней. На каждом ПК updater делает локальный backup перед заменой и автоматически восстанавливает старую версию при обычной ошибке установки; при неполном rollback он сохраняет резервную папку и показывает её путь.
