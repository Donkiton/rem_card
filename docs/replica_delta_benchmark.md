# Синтетический benchmark дельта-реплики

## Что измеряется

`scripts/replica_delta_benchmark.py` запускает реальные функции конвейера:

- прежний полный путь `local_replica_worker._sync_snapshot()` без ожидаемого состояния;
- новый worker `local_replica_worker._sync_snapshot_with_network_lease()`;
- `replica_refresh.try_incremental_snapshot()`;
- `replica_delta.collect_delta()` и `replica_delta.apply_delta()`.

Источник — полностью синтетическая база с актуальной unified-схемой RemCard. В ней
240 синтетических строк `patients` с историческим текстовым payload, одна госпитализация,
несколько показателей и клиническое событие, а также небольшие исходные наборы
`lab_data`, `medical_audit_log` и `drugs`. Фактический размер базы — 15,871 МиБ.
Индекс `full_name` намеренно отражает большой patient payload во втором B-tree и
делает физический объём близким к заданным 16 МиБ. Производственные данные и диск
`Z:` не используются.

Для исходной базы регистрируется отдельный APSW VFS. Каждый SQLite `xRead` в этом
VFS получает задержку 1,75 мс и учитывается вместе с запрошенным числом байт.
Клонирование прежнего локального cache, применение дельты, `quick_check`, fsync и
вычисления выполняются на обычном локальном диске без искусственной задержки.
Измеряемая длительность охватывает весь вызов worker до готового результата.

Physical stamp читает заголовок файла напрямую, в обход SQLite VFS. В каждом
успешном запуске нового worker это два чтения по 100 байт. Они явно указаны в JSON
как `raw_header_bytes_excluded=200`. В счётчики VFS также не входят операции
метаданных файловой системы и lock-файлы.

## Воспроизведение

Запуск выполнен из корня репозитория:

```powershell
python scripts/replica_delta_benchmark.py `
  --database-mib 16 `
  --delay-ms 1.75 `
  --repeats 3 `
  --output tmp/bench-results/replica_delta_benchmark.json
```

APSW используется только бенчмарком и загружается из
`tmp/startup-benchmark-deps`. Зафиксированный прогон выполнен на Python 3.10.11,
stdlib SQLite 3.40.1 и APSW 3.40.1.0 / SQLite 3.40.1. Текущие проверки и сборка
приложения используют Python 3.11 / SQLite 3.38.4. Поэтому абсолютные времена
описывают именно среду benchmark; они не являются замером времени сборочного
runtime.

Основные сравнения повторяются три раза. Порядок полного и нового путей
чередуется между повторами. Логический digest, `quick_check` и SHA-256 источника
проверяются после остановки таймера.

## Результаты

Медианы трёх повторов:

| Сценарий | Путь | Готовность, с | `xRead` | Байты SQLite VFS |
|---|---|---:|---:|---:|
| Небольшое изменение | Полный snapshot | 7,430 | 4 160 | 16 941 608 |
| Небольшое изменение | Delta | 0,277 | 86 | 262 580 |
| Источник не изменился | Принудительный полный snapshot | 7,417 | 4 160 | 16 941 608 |
| Источник не изменился | Physical-stamp reuse | 0,111 | 57 | 172 356 |

При одном обновлении `vitals` и одном обновлении `clinical_events` существующие
триггеры создали два события. Медианный delta-пакет содержал 2 793 байта и 24
строковые операции. Фактические чтения страниц источника составили 262 580 байт:
логический wire payload и прочитанные SQLite страницы — разные величины.

Для небольшого изменения delta была в 26,78 раза быстрее полного snapshot в
этой latency-модели, уменьшила объём source `xRead` на 98,45% и число вызовов
`xRead` на 97,93%. Physical-stamp reuse относительно принудительного полного
копирования дал 66,73 раза по времени, 98,98% по байтам и 98,63% по числу
`xRead`.

Первый запуск без локальной основы ускорения не получает. Полный старый путь
занял 7,411 с, новый worker с полным fallback — 7,561 с; он прочитал 16 941 608
и 17 261 328 байт соответственно. Дополнительные дешёвые проверки нового пути
слегка увеличивают первую полную синхронизацию.

Два защитных сценария запускались без искусственной задержки и действительно
завершились полным snapshot:

- 5 001 новых событий: `full_reason=event_limit`;
- удалённое событие сразу после cursor локальной основы: `full_reason=change_log_gap`.

Все кандидаты, включая оба fallback, прошли `quick_check` и совпали с источником
по логическому digest. SHA-256 файла источника до и после каждого измеряемого
чтения совпал.

Полный машинный результат со всеми повторами, этапами worker, delta-метриками и
валидацией сохранён в `tmp/bench-results/replica_delta_benchmark.json`.

## Границы интерпретации

Это алгоритмический benchmark с реальными SQLite page reads и синтетической
задержкой, а не SMB-тест. Он не моделирует сетевую пропускную способность,
повторные передачи, антивирус, конкурирующего писателя, lease-сервер или сбои
сети. Busy-spin делает задержку менее зависимой от Windows timer resolution,
но использует CPU.

Сценарий `unchanged` измеряет обычный worker refresh с `require_snapshot=false`
и показывает верхнюю границу выигрыша повторного использования источника по
сравнению с принудительным полным копированием. Это не end-to-end время входа в
приложение и не сравнение с уже существовавшим cursor-skip внутри одного процесса.
Startup-путь с `require_snapshot=true` дополнительно клонирует локальный cache,
проверяет его и выполняет операции persistence, которых в этом сценарии нет.
