# Диагностика первого запуска — 5.0.1

Собирать локальную папку logs с каждого проверяемого ПК за 2–3 рабочих дня.
Новые события `startup_diagnostic` попадают в существующие metrics JSONL,
асинхронно, с обычной ротацией. SQL, параметры и данные пациентов не записываются.

`run_id` объединяет запуск, `session_id` — попытку входа; `first_role`
означает первую попытку в данном процессе, а не первый запуск после включения ПК.
`boot_uptime_ms` показывает время работы Windows, но не подтверждает холодность кэша.

Этапы: application_start, chooser_ready, role_requested, role_ready,
startup_database_open, startup_connection_configure, startup_database_check,
sqlite_quick_check, startup_lock_acquire, role_bootstrap, role_window_create.
Пары begin/end связываются через span_id. Исключения сохраняют исходное поведение;
в лог попадает только класс ошибки. Незавершённый begin позволяет видеть оборванный этап.

Времена монотонные. request_to_ready_ms исключает ожидание выбора пользователем.
Процессорное время и IO-счётчики — всего процесса, включая параллельную работу.
Счётчики Windows не равны физическому дисковому или SMB-трафику: кэш и другие
операции влияют на значения. Вложенные длительности нельзя складывать.
Стартовый маркер находится после разбора аргументов: загрузка EXE до Python не учтена.

Проверка SQLite, тайм-ауты, блокировки, повторы и политика восстановления не меняются.
Новые замеры не выполняют дополнительных SQL-запросов или сканирования базы.
Если CPU/IO не объясняют задержку, потребуется отдельная системная трассировка.
