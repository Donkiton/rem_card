# Планирование служебного освобождения коек

Общий монитор раньше отправлял `auto_release_outcome_beds` примерно раз в
16 секунд, даже при отсутствии исходов. Теперь `PatientService` хранит ближайший
срок: время активного перевода/смерти плюс прежние 30 минут. До этого срока
обычный tick не читает базу и не отправляет задачу в очередь.

Первая проверка выполняется при входе. Изменения `beds`, `admissions`,
`patient_status_events`, адресные сигналы статусов/коек, восстановление и разрывы
журнала изменений сбрасывают расписание. Проверка нового состояния сохраняет
прежний debounce (15 секунд) и единственную активную задачу. Поколение расписания
не позволяет позднему ответу затереть полученный во время запроса сигнал изменения.
Видимые строки с наступившим сроком могут принудительно запросить проверку.

Раз в 60 секунд остаётся контрольная сверка. Без изменений и исходов это
60 задач в час вместо примерно 223 по исходным журналам: около 73% меньше.
Это модель числа задач, а не замер скорости на рабочей сети. При пропущенном
уведомлении новый исход обнаруживается на контрольной сверке; к минуте добавляются
интервал polling, ожидание очереди и доступность источника чтения. Изменения с
уведомлениями и известные сроки обрабатываются чаще. Замена/отмена исхода не
может привести к освобождению по устаревшему расписанию: прежняя DAO-операция
повторяет проверку статуса и принадлежности койки внутри транзакции.

План читается через прежний `fetch_all_remcard`: готовая локальная реплика,
центральная база при необходимости либо активная аварийная база. Оптимизация
не добавляет обязательное сетевое открытие соединения для каждой сверки.
Срок нормализуется SQLite `DATETIME`, как в существующей проверке освобождения;
правила суток карты 08:00–08:00 и записи исхода не изменяются.

Задачи остаются в управляемой очереди DataService: shutdown ждёт принятые записи,
а обнаруженный сетевой обрыв запрещает новые проверки. Ошибка чтения оставляет
расписание неподтверждённым. После наступившего срока следующая проверка пересчитывает
план; дополнительное чтение после успешной записи не создаёт ложную ошибку её исхода.

Метрика `outcome_bed_release_check_ms` содержит время фактической проверки,
`status`, `released_count`, `next_due_in_sec`. Tick без задачи не создаёт лог.
Число принятых задач можно сопоставить с прежними метриками очереди; медицинские
тексты и идентификаторы пациентов в новой метрике отсутствуют.

Проверки используют синтетические SQLite-базы: граница 30 минут, гонки отмены,
переноса и замены пациента, второй клиент, пропущенные уведомления, сбой чтения,
очередь и shutdown. Сценарий реального аварийного bootstrap дополнен освобождением
локальной койки при запрещённом доступе к центральной базе.
