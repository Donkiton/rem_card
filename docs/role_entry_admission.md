# Повторный вход в роль

При первом входе в центральную базу в одном процессе RemCard выполняется прежний
`PRAGMA quick_check`. Успешный результат допускается повторно использовать **30 минут**:
при переключении роли выполняется короткое открытие SQLite только для чтения и
проверка идентичности файла, версии схемы, миграций, ревизии fastpath, режима журнала
и маркеров восстановления/карантина. Клинические INSERT/UPDATE и рост размера файла
сами по себе не требуют нового полного сканирования.

Допуск существует только в памяти текущего процесса. Время отсчитывается монотонно
от последней успешной полной проверки и не продлевается повторными входами. Первый
вход после перезапуска, истечение 30 минут, изменение пути/файла/схемы, ошибка доступа,
повреждение, восстановление или отмена подготовки сбрасывают допуск. Если файловая
система не предоставляет идентификатор файла, каждый вход использует полную проверку.

Проверки политики клиента, допуска SessionLease, блокировки ротации и настройки
сетевого SQLite-профиля сохраняются при каждом входе. Новый режим применяется только
в едином окне с поддерживающим его runner; старые точки входа выполняют полную проверку.
Локальные аварийные базы проходят собственный путь допуска.

Обе проверки выполняются в отменяемом дочернем процессе. Qt продолжает обрабатывать
события, а перед возвратом/отменой дочерний процесс завершается и освобождает дескрипторы.
Неуспех короткой проверки требует прежней полной проверки; сам по себе он не разрешает
автовосстановление. Передача результата в DatabaseManager привязана к текущему PID,
точному размеру/mtime файла и ещё действующему допуску в памяти. Время полной проверки
передаётся отдельно от времени текущего подтверждения доступности.

Это уменьшение частоты полного сканирования: короткая проверка не обнаруживает всякое
новое повреждение страниц с клиническими данными. Необнаруженное другими операциями
повреждение таких страниц будет найдено следующей полной проверкой, а не обязательно
при ближайшем переключении роли. Первый вход не ускоряется этим изменением.

## Диагностика и проверка

Метрика `startup_admission_decision`: `check_mode=full/recent`, причина решения
(`no_full_scan`, `expired`, `database_path_changed`, `changed_identity`, `changed_schema`,
`changed_migration`, `changed_revision`, `changed_markers`, либо неуспех probe/сброс допуска),
возраст полной проверки. `startup_admission_probe` измеряет короткую проверку.
`db_guard_ok` различает `quick_check=ok/recent_ok` и сохраняет исходное время полной
проверки. SQL и сведения пациентов в эту диагностику не добавляются.

`tests/test_role_admission.py` проверяет реальные изолированные SQLite-файлы, сохранение
допуска после обычных записей, срок без продления, замену файла, схему/миграции/fastpath,
ротацию, карантин, восстановление, ошибки, отмену и передачу результата в DatabaseManager.
Отдельно проверяются настоящий дочерний процесс, освобождение файла при отмене/таймауте
и работа Qt-таймера при входе через новый runner. Рабочая сетевая база для тестов не нужна.
