# Повторный вход в роль

При первом входе из единого окна RemCard создаёт согласованный локальный снимок
через SQLite Backup API и выполняет `PRAGMA quick_check` на локальном диске.
Проверка содержимого сохраняется; повторное полное чтение общей базы для создания
первой реплики больше не требуется. Успешный результат допускается повторно использовать **30 минут**:
при переключении роли выполняется короткое открытие SQLite только для чтения и
проверка идентичности файла, версии схемы, миграций, ревизии fastpath, режима журнала
и маркеров восстановления/карантина. Клинические INSERT/UPDATE и рост размера файла
сами по себе не требуют нового полного сканирования.

Допуск существует только в памяти текущего процесса. Время отсчитывается монотонно
от последней успешной полной проверки и не продлевается повторными входами. Первый
вход после перезапуска, истечение 30 минут, изменение пути/файла/схемы, ошибка доступа,
повреждение, восстановление или отмена подготовки сбрасывают допуск. Если файловая
система не предоставляет идентификатор файла, каждый вход использует полную проверку.

Проверки политики клиента, допуска SessionLease, блокировки ротации и настройки
сетевого SQLite-профиля сохраняются при каждом входе. Новый режим применяется только
в едином окне с поддерживающим его runner; старые точки входа выполняют полную проверку.
Локальные аварийные базы проходят собственный путь допуска.

Обе проверки выполняются в отменяемом дочернем процессе. Qt продолжает обрабатывать
события, а перед возвратом/отменой дочерний процесс завершается и освобождает дескрипторы.
Неуспех короткой проверки требует прежней полной проверки; сам по себе он не разрешает
автовосстановление. Передача результата в DatabaseManager привязана к текущему PID,
точному размеру/mtime файла и ещё действующему допуску в памяти. Время полной проверки
передаётся отдельно от времени текущего подтверждения доступности.

Это уменьшение сетевого чтения и частоты полного сканирования: короткая проверка не обнаруживает всякое
новое повреждение страниц с клиническими данными. Необнаруженное другими операциями
повреждение таких страниц будет найдено следующей полной проверкой, а не обязательно
при ближайшем переключении роли. Первый вход всё ещё требует передачи всей базы;
выигрыш зависит от задержек файлового сервера и числа операций чтения.

## Проверенный снимок и реплика

Исходный файл открывается только для чтения. Перед и после Backup API проверяются
его идентичность, схема, цикл базы, ревизия и маркеры восстановления. Определения
схемы снимка сравниваются с источником; `schema_version` и `journal_mode` локального
назначения не используются как идентичность центральной базы, поскольку SQLite
может изменить их при backup. Обычные клинические записи допускаются; снимок
сохраняет собственный курсор `change_log`.

Во время копирования сохраняются reader lease, защита от ротации, отдельная очередь
копирования рабочего места и приоритет клинических записей между порциями страниц.
Прогресс показывает фактические страницы; он не продлевает общий срок операции.
После принудительной остановки дочернего процесса очистка его блокировок выполняется
с проверкой PID/владельца в отдельном процессе с ограниченным временем ожидания.

Снимок принадлежит допуску текущего процесса. Он удаляется при сбросе, истечении
срока, замене допуска и штатном завершении. Повторный вход не продлевает срок.
Для врача и медсестры создаются отдельные локальные кандидаты с проверкой SHA-256
и `quick_check`, затем применяется существующая публикация с rollback.
Более новая исправная реплика того же цикла не заменяется старым стартовым снимком.

Установка снимка **не отмечает реплику свежей**. Первый обычный worker подтверждает
цикл, ревизию и курсор центральной базы. При совпадении он обходится коротким чтением
метаданных; при новых записях создаёт актуальную реплику. Требования к свежести и
видимости собственных записей сохраняются. Сбой установки не отключает обычную
синхронизацию и не уничтожает предыдущую исправную копию.

Если снимок вытеснен клинической записью, очередь копирования рабочего места занята
или точно установлен сбой локального назначения, допускается исходная прямая
проверка центральной базы без стартовой реплики. Она выполняется в том же отменяемом
worker с исходным общим дедлайном, подтверждает неизменность источника и сохраняет
30-минутный допуск. Этот резервный путь может удерживать read-lock как прежняя
проверка и задерживать writer; приоритет записи между порциями сохраняется в основном
пути Backup API. Активные ротация/восстановление и смена идентичности/схемы/цикла
не разрешают такой переход. Сетевой сбой не классифицируется как локальная ошибка.

Фоновая реплика теперь имеет срок **30 секунд** по умолчанию вместо 6. Параметр
`REMCARD_LOCAL_REPLICA_SYNC_TIMEOUT_SEC` согласованно ограничивается 90 секундами
во всех слоях; это жёсткий предел, включая запуск worker и ожидания. Стартовая
проверка сохраняет отдельный предел 90 секунд. Нет изменений версии схемы или
минимальной версии клиента, необходимых для этого механизма.

## Диагностика и проверка

Метрика `startup_admission_decision`: `check_mode=full/recent`, причина решения
(`no_full_scan`, `expired`, `database_path_changed`, `changed_identity`, `changed_schema`,
`changed_migration`, `changed_revision`, `changed_markers`, либо неуспех probe/сброс допуска),
возраст полной проверки. `startup_admission_probe` измеряет короткую проверку.
`db_guard_ok` различает `quick_check=ok/recent_ok` и сохраняет исходное время полной
проверки. SQL и сведения пациентов в эту диагностику не добавляются.

`tests/test_role_admission.py` проверяет реальные изолированные SQLite-файлы, сохранение
допуска после обычных записей, срок без продления, замену файла, схему/миграции/fastpath,
ротацию, карантин, восстановление, ошибки, отмену и передачу результата в DatabaseManager.
Отдельно проверяются настоящий дочерний процесс, освобождение файла при отмене/таймауте
и работа Qt-таймера при входе через новый runner. Рабочая сетевая база для тестов не нужна.
