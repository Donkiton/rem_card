# Локальная работа оперблока

Изменения разрабатываются в `rework`. Публикация и слияние с `main` выполняются отдельно.

## Хранение

Плановый и экстренный оперблок используют базу этого компьютера:
`%ProgramData%\RemCard\operblock_offline\active\operblock_local.db`.
Активные операции других компьютеров сюда не загружаются. Незавершённый случай
остаётся локальным после выхода из программы и возобновляется на этом же ПК.

Каждый случай имеет постоянный UUID. UUID установки хранится в самой локальной
базе и не меняется при входе другого пользователя Windows. Печатный номер
протокола сохраняется при передаче; одинаковые номера разных случаев допустимы.

Рядом с базой находятся:

- `destination.json` — явно выбранный каталог общей базы;
- `delivery_status.json` — технический результат последней попытки отправки;
- `backups` — три поколения проверенных резервных копий SQLite;
- `reports` — локально сформированные PDF.

Локальная база хранит неотправленные случаи без ограничения по возрасту.
Подтверждённые случаи сохраняются как минимум 90 дней после доставки. Очистка
проверяет квитанцию и содержимое обеих копий; при несовпадении или недоступности
общей базы локальный случай сохраняется. Общий файл локальной базы не удаляется.
PDF не удаляются только на основании возраста: среди них могут быть документы
ещё не переданных случаев.

## Отправка

Освобождение стола делает завершённый случай доступным для отправки. Работа
со следующим пациентом не ждёт отправки предыдущего. Фоновый процесс передаёт
только закрытые случаи; другой активный случай на этом ПК не мешает передаче.

Повторные попытки выполняются с задержкой до пяти минут, при следующем запуске
и после освобождения стола. Попытка ограничена временем; при выходе ожидание
ограничено тремя секундами. После закрытия приложения отправка возобновляется
при следующем запуске RemCard.

Основная база открывается только по явно заданному пути и только если файл уже
существует. Перед первой передачей создаётся проверенная резервная копия.
Назначение привязывается к UUID центральной базы, чтобы случайно не отправить
очередь в другую базу при смене пути.

Один случай записывается в одной центральной транзакции. Квитанция содержит
UUID случая, UUID установки и хеш содержимого. Повтор после потери подтверждения
сверяет квитанцию и данные, а не создаёт новый протокол. Изменённый центральный
архив не перезаписывается старой локальной копией.

Закрытый локальный случай можно исправить до отправки. После подтверждения
исправления выполняются в общем архиве. Редактор реквизитов использует проверку
версии и хранит снимки до/после изменения; история локальных правок передаётся
вместе со случаем. Этот редактор меняет данные пациента, диагноз, состав бригады
и реквизиты операции; редактирование доз и временных событий не добавляется.

## Переводы

После доставки случая с переводом в РАО врач получает приглашение выбрать
койку, связать уже созданную карту или отклонить приглашение. Действие выполняется
в центральной транзакции; два врача не должны одновременно принять один случай.
Срок 30 минут считается от клинического времени перевода и повторно проверяется
при принятии. Просроченный случай сохраняется в архиве без создания новой карты.

Пациент, отправленный из РАО, выбирается из центральной очереди при наличии
связи. Принятие закрепляется за установкой и UUID заявки; локальный снимок
сохраняется для повторения после сбоя. Создание местной операции и потребление
заявки должны завершаться одной локальной транзакцией. Возврат пациента
связывается с исходной картой РАО.

## Проверка и восстановление

Автоматические проверки выполняются на отдельных временных базах. Рабочую
сетевую базу для тестов не используют. Основные сценарии: отсутствие сети до
старта, потеря сети, несколько завершённых случаев, повтор после потери
подтверждения, параллельная правка, занятая койка, повторное принятие очереди,
истечение 30 минут, очистка только подтверждённых случаев.

Повторяемые команды из корня репозитория:

```powershell
.\.venv\Scripts\python.exe scripts\run_ci_checks.py core
.\.venv\Scripts\python.exe scripts\run_ci_checks.py ui
.\.venv\Scripts\python.exe scripts\run_ci_checks.py quality
.\.venv\Scripts\python.exe scripts\run_ci_checks.py regression
```

Этот запуск изолирует также `ProgramData`, профиль пользователя и файлы выбора
базы: тесты не должны находить очередь операций установленной программы.

Повреждённый локальный файл нельзя заменять пустой базой. При восстановлении
используют проверенную резервную копию, сохраняют исходный файл в карантине и
показывают врачу дату копии. Резервная копия отражает момент её создания;
изменения после этого момента требуют проверки.

## Результаты проверки реализации (28.09.2026)

- Основной набор: 1095 тестов и 58 subtests прошли; последние точечные
  изменения дополнительно проверены отдельными наборами.
- Итоговый интерфейсный набор: 989 тестов и 15 subtests прошли, один тест
  пропущен по условию окружения.
- Регрессионный профиль `fast`: все 538 проверок прошли.
- Статический анализ: 3/3; архитектурные проверки: 10/10.

Это результаты изолированных автоматических проверок, а не испытание
на рабочей сетевой базе. Реальное отключение SMB на рабочих компьютерах
и ручной полный клинический сценарий после обновления требуют отдельной проверки.
