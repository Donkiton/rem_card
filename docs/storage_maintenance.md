# Ручное обслуживание служебных файлов

Этап 2 расследования от 13.09.2026. Не меняет транзакции, синхронизацию,
аварийный режим или медицинские данные (этап 1 выполняется отдельно).

## Запуск и будущая роль администратора

Сейчас: врач → Центр управления → Обслуживание → Служебные файлы.
Нажать «Инспектировать», проверить фактическую папку базы и список, затем
«Очистить перечисленные файлы». Не более 500 файлов за проход; для следующего
прохода требуется новая инспекция. Автоматического таймера нет.

Это **временная точка входа у врача**. При переходе к единому EXE перенести
проверку роли и карточку действия в администраторский вход
`AdminMainWidget.open_storage_maintenance`. Сервис `StorageMaintenanceService`
и окно `StorageMaintenanceDialog` не зависят от роли и не требуют изменений.
Сервис принимает явную папку из текущего `DbRuntimeContext`, не обращается
к глобальному сохранённому пути и не открывает SQLite. UI допускает только
режим `network`; локальные аварийные базы и архивные снимки сюда не передаются.

## Политика

Возраст определяется временем последней записи; будущие даты сохраняются.
Удаляются только обычные файлы с точными известными шаблонами имён:

| Каталог / вид | Дней |
| --- | ---: |
| `logs`: технические `.log` | 30 |
| `logs`: `metrics_*.jsonl` | 14 |
| `logs`: `audit_*.jsonl` | 90 |
| `backup_health`, `settings/backup_health`: исторические daily done/report | 90 |
| Старый временный файл `startup_quick_check_state.json.tmp_*` | 7 |
| `locks/replica_snapshots`: промежуточные `.lock.<host>.<pid>.<uuid>.tmp` | 7 |
| `quarantine/locks`: распознанные `.malformed` | 30 |
| `logs/diagnostics/crashes/processed/YYYY/MM`: обработанные JSON | 30 |
| `logs/diagnostics/crashes/summaries`: сводки | 30 |
| `logs/diagnostics/crashes/quarantine`: невалидные отчёты и причины | 30 |

Активные сегменты `_active`, неизвестные имена, incoming, processing,
необработанные review-материалы, текущие контрольные состояния и reserved-маркеры
сохраняются. Прямой просмотр скопированных логов вне основной папки базы и
очистка каталогов установленных релизов не входят в этот сервис.
Бэкапы, базы, карантин базы, снимки, медицинская документация, ожидающие действия,
сессии и материалы аварийного восстановления не обходятся и не удаляются.
Поэтому «сохранено» означает число сохранённых файлов в обследованных каталогах,
а не размер всей базы. Непонятные файлы нельзя считать мусором по возрасту.

## Безопасность и ограничения

- Инспекция ничего не записывает. При ошибке обхода или превышении 20 000
  записей / 30 секунд между операциями файловой системы очистка запрещается.
  Отдельный зависший вызов SMB не прерывается таймером, но выполняется вне UI.
- Перед удалением повторяются инспекция, проверка возраста и идентичности
  (размер, mtime, устройство, inode). Дубликаты и подменённые пути отбрасываются.
- В Windows файл открывается с эксклюзивным доступом и удаляется через
  проверенный дескриптор. Занятые файлы пропускаются. Символические ссылки и
  junction/reparse points исключаются. На других ОС доступна только инспекция.
- Между обслуживающими клиентами используется отдельный каталог
  `.service_cleanup.lock`, создаваемый атомарно. Он не блокирует SQLite и
  не связан с `db.lock`, `doctor.lock` или `nurse.lock`.
- После принудительного завершения каталог блокировки обслуживания может
  остаться. Не захватывать его по возрасту: администратор должен убедиться,
  что обслуживание остановлено на всех клиентах, и удалить только этот пустой
  каталог. Медицинские lock-файлы для этого трогать нельзя.
- Единственный перезаписываемый `service_cleanup_last.json` хранит начало или
  итог последнего прохода и причины пропусков. Ошибка записи начального отчёта
  запрещает удаление; ошибка итогового отчёта показывается отдельно от уже
  выполненных удалений. После обрыва может остаться один `.json.tmp` этого отчёта.
- Физического удаления нет в фоновом таймере и нет при открытии окна.
  На сети требуется проверка совместимости эксклюзивного удаления с конкретным
  SMB-сервером на отдельном искусственном каталоге, не на рабочей базе.

## Проверки

`tests/test_storage_maintenance.py`: allowlist, защищённые и свежие файлы,
изменение после инспекции, эксклюзивное удаление, занятый файл, junction,
поддельный план, конкурентное обслуживание, предел обхода, отказ отчёта.

`tests/test_storage_maintenance_dialog.py`: работа вне UI-потока, запрет очистки
при неполной инспекции, полный ручной проход, доступность только у врача.
Все операции удаления тестируются на искусственных временных файлах.

Перед выпуском на отдельном тестовом SMB-каталоге: одновременный запуск двумя
клиентами, открытый файл другим клиентом, пропадание сети, повторная инспекция.
Рабочую сетевую базу не очищали и не использовали для destructive-тестов.
