# Проверки RemCard

GitHub Actions и локальный запуск используют `scripts/run_ci_checks.py`.
Python 3.11 и зависимости из `requirements.txt` должны совпадать с CI.
Для отдельного локального окружения:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe scripts/run_ci_checks.py core
.\.venv\Scripts\python.exe scripts/run_ci_checks.py ui
.\.venv\Scripts\python.exe scripts/run_ci_checks.py quality
.\.venv\Scripts\python.exe scripts/run_ci_checks.py regression
```

Команда `all` вместо имени группы запускает весь pytest в одном процессе.
Она нужна для проверки общей изоляции и взаимодействий между тестовыми модулями.
Обычный `python -m pytest tests -q` также сохраняется.

## Состав и изоляция

`tests/groups.json` распределяет каждый тестовый модуль ровно в одну группу:

| Группа | Назначение |
|---|---|
| `core` | Логика, хранение данных и инфраструктура |
| `ui` | Qt, окна, диалоги и взаимодействия интерфейса |
| `quality` | Flake8, BOM, сложность кода и архитектурные ограничения |
| `regression` | Полный реестр safety-сценариев |

Новый тестовый файл нужно добавить в `groups.json`. Пропущенные, повторные и
удалённые модули приводят к ошибке. Разделение происходит **до импорта** тестовых
модулей. Qt-тесты остаются последовательными внутри своего процесса.

`tests/conftest.py` назначает маркеры `core`, `ui`, `database`, `clinical`,
`updates`, `infrastructure`. Например: `python -m pytest tests -m clinical`.
Тематический маркер помогает выбрать сценарии, но не заменяет полные проверки.

Runner задаёт отдельные временные пути БД и QSettings для каждого процесса.
Общая Qt-фикстура уничтожает созданные тестом окна в GUI-потоке, завершает
отложенное удаление и сборку циклических ссылок; окна общих фикстур сохраняются.
Тесты сами отвечают за завершение созданных фоновых работников.
Фикстура хранилища логов направляет фоновые метрики приложения в отдельный
каталог: их ротация не должна менять файлы, содержимое которых проверяет тест.
Отдельный сценарий воспроизводит запись между перечислением файлов и чтением
их размеров, подтверждая изоляцию без отключения самих метрик.

## GitHub Actions и обязательный результат

Качество, core, ui и regression выполняются независимо. Ошибка одной группы
не отменяет остальные. Общий статус **`tests`** сохраняет имя, указанное в
защите ветки. Он требует успеха всех групп и проверяет отчёты:

- каждый модуль pytest присутствует ровно в своей группе;
- идентификаторы тестов не повторяются;
- safety-реестр выполнен целиком, в отчёте нет потерянных или лишних сценариев;
- после аварийного падения процесса не было повторного запуска.

Диагностический повтор native crash в старом safety-runner сохранён, но такой
результат не считается чистым успешным CI. Исходная ошибка остаётся в отчёте.

Новый коммит PR отменяет устаревший прогон. Изменение описания или заголовка
дожидается текущего прогона и может использовать его результат **только** при
наличии успешного отчёта `ci-gate` для точно той же проверенной merge-ревизии.
Итоговое задание повторно сверяет ревизию. Если подтверждения нет, отчёт
повреждён или API недоступен, выполняются все группы. Смена базы PR всегда
запускает полный набор. Draft PR проверяется сразу, поэтому отдельный повтор
при `ready_for_review` не нужен. Push в `main` и ручной запуск сохранены.

## Отчёты и время

Результаты находятся в `tmp/ci-reports/<группа>`: полный лог, `result.json`,
JUnit XML и список собранных тестов либо полный `regression.json`.
`--report-dir` позволяет сохранить отдельную серию измерений.
GitHub сохраняет артефакты 14 дней, в том числе при ошибке, и выводит краткую
сводку. У pytest видны 25 наиболее долгих тестов. Тайм-аут процесса — 900 секунд,
у заданий GitHub есть отдельный предел с запасом на подготовку окружения.

Safety-сценарии находятся в `scripts/regression_checks/`; `registry.py` хранит
полный список и исторический порядок. `fast` и `exhaustive` выполняют один и тот
же реестр. Первый распределяет его по отдельным процессам, второй выполняет
последовательно. `scheduling.py` делит реестр на непрерывные группы по оценке
времени и сначала запускает самые тяжёлые; внутри группы порядок сохранён.
Новые сценарии получают консервативную оценку и не исключаются из запуска.

Оценки обновляются вручную по полному успешному отчёту:

```powershell
.\.venv\Scripts\python.exe scripts/update_regression_timings.py tmp/ci-reports/regression/regression.json
```

Изменение оценок требует обычной проверки diff и полного прогона. CI не
перезаписывает оценки автоматически. Для продолжения реорганизации следует
переносить небольшие связные группы, сохраняя идентификаторы сценариев.
Статические проверки архитектурных запретов сохраняются; проверки поведения
предпочтительно писать через результат работы, а не через имена внутренних функций.

## Разбор падений

AssertionError, превышение времени, ошибка подготовки окружения и native crash
рассматриваются отдельно. Прежде чем исправлять приложение, нужно воспроизвести
дефект на исходной ревизии и установить нарушение его контракта. При изменении
фикстуры или ожидания теста сохраняется проверка того же поведения.

Например, тест COMMIT на настоящем SQLite проверяет откат, метрику тайм-аута
и отсутствие повторной записи. Соблюдение предельного времени COMMIT проверяется
управляемыми часами: файловые операции и загрузка GitHub runner не влияют на
это ожидание. Произвольное увеличение лимита или повтор до зелёного результата
не заменяет диагностику.
