## Один контур для всей смены

`Рем Карта` объединяет рабочие места отделения реанимации и интенсивной терапии вокруг общей папки данных.

| Рабочее место | Основные задачи |
|---|---|
| **Врач** | Госпитализации и койки, карта пациента по сменам, назначения и шаблоны, процедуры, исходы, архив, отчёты и калькуляторы. |
| **Медсестра** | Просмотр назначений, отметки о выполнении, сменная динамика, печать и рабочая статистика. |
| **Оперблок** | Экстренная и плановая операционные, быстрые назначения, препараты, этапы и события операции, завершение случая и отчёты. |
| **Администратор** | Состояние текущей и архивных БД, резервные копии, настройки, справочники и диагностика. |

Дополнительно приложение содержит аналитику и графики, печатные формы, МКБ, темы интерфейса, пользовательские обращения с диагностическими логами и ограниченный локальный режим оперблока при проблемах с сетью.

Интерфейс подтверждает сохранение только после успешной записи в БД. Изменения между рабочими местами передаются через `change_log` и специализированные снимки данных. Основной внутренний поток выглядит так: **интерфейс → сервисы → DAO → SQLite**.

## Быстрый запуск из исходников

Проект разрабатывается и проверяется на **Windows с Python 3.11**. Нужны Git и Python; файл `.env` не требуется.

```powershell
git clone https://github.com/Donkiton/rem_card.git
cd rem_card
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python launcher.py
```

`launcher.py` запускает приложение без заранее закреплённой роли. Рабочие места можно открыть напрямую:

```powershell
python run_doctor.py
python run_nurse.py
python run_operblock_emergency.py
python run_operblock_planned.py
```

> [!CAUTION]
> Для разработки и испытаний используйте отдельную папку данных, а не рабочую production-БД. Dev-сеанс не создаёт и не проверяет файловую блокировку роли: транзакционные блокировки SQLite защищают отдельные записи, но не заменяют изоляцию тестовой среды.

<details>
<summary><strong>Как выбирается dev-база</strong></summary>

По умолчанию исходная версия использует стандартную dev-папку данных в родительском каталоге репозитория:

```text
C:\Project\rem_card                 # репозиторий
C:\Project\<стандартная dev-папка> # dev-БД, логи, настройки и тестовый UPD
```

При первом запуске приложение может создать недостающую локальную структуру. Кнопка «Смена базы» позволяет сохранить несколько папок и выбрать активную. Выбор хранится отдельно для каждого checkout в `.remcard/dev_database_paths.json` и применяется после безопасного перезапуска.

Выбранная существующая база проверяется без права незаметно создать пустую БД вместо пропавшего файла. Старый `%LOCALAPPDATA%\RemCard\dev_database_paths.json` используется только для однократного переноса настройки.

</details>

## Установленная версия и обновления

В репозитории нет MSI-установщика или Docker-развёртывания. Рабочая Windows-версия распространяется полной папкой PyInstaller с шестью файлами запуска:

| Файл | Назначение |
|---|---|
| `RemCardDoctor.exe` | Рабочее место врача. |
| `RemCardNurse.exe` | Рабочее место медсестры. |
| `RemCardOperBlockEmergency.exe` | Экстренная операционная. |
| `RemCardOperBlockPlanned.exe` | Плановая операционная. |
| `RemCardPathSetup.exe` | Смена общей папки данных. |
| `RemCardUpdater.exe` | Установка полного обновления. |

При первом запуске ролевого EXE программа просит выбрать общую папку данных, создаёт в ней необходимую структуру и сохраняет рядом с программой `remcard_data_path.json`. Обновления ищутся в `<папка данных>\UPD\releases`.

Проект использует только **полные обновления**. Уровень `PATCH` в SemVer описывает размер изменения версии, а не отдельный формат пакета.

<details>
<summary><strong>Тестовая сборка незакоммиченных изменений</strong></summary>

```powershell
.\.venv\Scripts\python.exe scripts\build_release.py --test-worktree
```

Команда запускает обязательные проверки, PyInstaller и smoke-тест всех шести EXE, но не меняет `VERSION`, `CHANGELOG.md` и `app/release_info.json`, не создаёт коммит, не выполняет `git push` и не публикует пакет в `UPD`. Результат сохраняется в `dist\Prog` с маркером `TEST_WORKTREE_ONLY.txt`, который блокирует случайную production-публикацию.

</details>

<details>
<summary><strong>Сборка и публикация рабочего релиза</strong></summary>

Версия сначала подготавливается отдельным коммитом и попадает в GitHub `main`. Менеджер релизов считывает точные версию и коммит, синхронизирует чистую локальную ветку и запускает:

```powershell
.\.venv\Scripts\python.exe scripts\build_release.py `
  --expected-version <версия GitHub> `
  --expected-commit <40-символьный-коммит GitHub>
```

После приёмки на отдельной тестовой БД пакет явно переносится в сетевую рабочую базу:

```powershell
.\.venv\Scripts\python.exe scripts\publish_full_update.py `
  --source "<локальная папка данных>\UPD\releases\<проверенная версия>" `
  --config "<папка установленной программы>\remcard_data_path.json"
```

Publisher повторно проверяет пакет и наличие исходного коммита в `origin`, поддерживает возобновляемое копирование и создаёт `ready.ok` последним.

> [!IMPORTANT]
> После появления `ready.ok` в рабочем сетевом каталоге версия сразу доступна всем клиентам этой базы. Приёмка должна быть завершена на изолированной тестовой базе **до** публикации.

Подробности: [сборка и публикация](docs/how_to_build_and_update.md) и [автообновление](docs/auto_update.md).

</details>

## Архитектура и хранение данных

Основная медицинская БД находится в `archiv/rao_journal.db`. Справочники, темы, фоны и настройки хранятся в `settings/remcard_settings.db`; JSON-файлы репозитория служат начальными данными и слоем совместимости, но не являются рабочим источником истины установленной версии.

Для сетевой SQLite-БД закреплён защитный профиль:

- `journal_mode=DELETE`, `synchronous=EXTRA`, `mmap_size=0`;
- запись через блокировки, очередь и транзакции;
- резервное копирование через SQLite Backup API, а не копированием открытого файла;
- проверки запуска, миграций, целостности, старых клиентов и восстановления.

Эти механизмы снижают известные риски, но не делают произвольное сетевое размещение SQLite автоматически безопасным. Права, задержки, резервирование и восстановление требуют отдельной эксплуатационной приёмки.

## Проверки для разработчика

Обычные локальные проверки не должны работать с production-БД:

```powershell
python -m pytest -q
python -m compileall app data services ui scripts
python scripts\code_quality_checks.py
python scripts\architecture_safety_check.py
python scripts\regression_safety_checks.py --profile fast --jobs 4
git diff --check
```

Сетевые стенды, restore drill, аварийный режим и offline-режим оперблока читают или изменяют файлы выбранной папки данных. Запускайте их только с осознанно заданной тестовой базой по [регламенту приёмки](docs/operational_acceptance.md) и [инструкции проверки резервных копий](docs/backup_restore_drill.md).

## Карта репозитория

| Путь | Назначение |
|---|---|
| `launcher.py`, `run_*.py` | Запуск из исходников и точки входа ролей. |
| `app/` | Запуск, роли, пути, жизненный цикл БД, аварийный режим, резервирование и обновления. |
| `data/` | DAO, DTO, схемы, импорт и release snapshot настроек. |
| `services/` | Бизнес-логика, координация чтения и записи, отчёты, аналитика и оперблок. |
| `ui/` | Интерфейсы врача, медсестры, оперблока, карты пациента, аналитики и общих компонентов. |
| `scripts/` | Проверки, диагностика, сборка, публикация, резервирование и восстановление. |
| `tests/` | Тесты `pytest`, включая регрессии БД, назначений, интерфейса и release-процесса. |
| `docs/` | Действующие регламенты, отчёты и исторические архитектурные снимки. |
| `icon/`, `procedure_templates/` | Графические ресурсы и шаблоны процедур. |
| `RemCard.spec` | Описание полной onedir-сборки PyInstaller. |
| `VERSION`, `CHANGELOG.md` | Текущая версия и журнал изменений. |
